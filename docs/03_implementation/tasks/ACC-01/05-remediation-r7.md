## 4. The design, item by item

**`account_change_request` status guard (`trg_acc1_change_request_status`).** Immediate, `BEFORE INSERT OR UPDATE OF status, applied_at_utc, applied_xact_id, approval_id, …, result_ref, sec_audit_ref` (the apply-owned fields; a column-list trigger fires when a statement names a column even if the value is unchanged). `INSERT` must be `requested` with apply-owned fields NULL. `UPDATE` of a row that has left `requested` is always refused (`ACC1_CHANGE_REQUEST_STATE_INVALID`): `applied → applied`, `applied → requested \| cancelled`, `cancelled → applied`, `expired → applied` and every other rewrite. From `requested`, only `applied`, `cancelled` or `expired`.

**`applied_xact_id` design.** `account_change_request.applied_xact_id xid8 NULL`, database-owned. On `requested → applied` the trigger sets `NEW.applied_xact_id := pg_current_xact_id()` and `NEW.applied_at_utc := clock_timestamp()`, discarding caller values; NULL otherwise (`CHECK`s). Absent from the runtime `UPDATE` grant; immutable once set because the row is terminal. "Applied in this transaction" ≡ `status = 'applied' AND applied_xact_id = pg_current_xact_id()`, used identically in `trg_acc1_status_transition`, `trg_acc1_recovery_bind`, `trg_acc1_closure_barrier`, `trg_acc1_family_abort_guard` and the abort-set proof. Top-level and savepoint-stable; independent of `xmin`; `xmin` is never compared with an `xid8`.

**Recovery/history reverse-bijection design.** Immediate: `trg_acc1_status_transition` requires this target's own recovery row (see R7-F01(a)). Deferred: the abort-set proof (05 §5.3, S1–S6) from four entry points — recovery-side (`trg_acc1_recovery_scope`), history-side (`trg_acc1_history_abort_scope`, fires with zero recovery rows), request-side (`trg_acc1_abort_apply_complete`, fires with neither) and family-side (`trg_acc1_family_membership`). No direction depends on the other table having a row.

**`closure_recovery.created_xact_id` design.** `xid8 NOT NULL`, stamped `NEW.created_xact_id := pg_current_xact_id()` by `trg_acc1_recovery_bind` (`BEFORE INSERT`); caller value discarded; used for same-transaction correlation (immediate status/barrier checks and the proof); not `xmin`. `account_status_history.created_xact_id xid8 NOT NULL` is stamped likewise by the new `trg_acc1_history_stamp` (no equivalent authoritative transaction field existed to reuse; `occurred_at_utc` is a wall-clock time).

**Approved-payload canonical shape.** Inside the canonical envelope, `parameters` = `{abort_target_type: independent|master, abort_target_id, reason_code, closure_family_id|null, evidence_ref|null, evidence_owner_target_id|null, rejection_approval_request_id|null, rejection_decision_id|null, returned_members: [{target_type, target_id, approved_version, closure_cycle, closure_seal_version, family_role: master|default|master_directed_child|independent_own_abort}]}` (ACC vocabulary, `closure_recovery` column names). Independent: exactly the target. Master family: exactly master, default and every master-directed child; excludes `independent_preserved`. `closure_cycle`/`closure_seal_version` are integers ≥ 0 copied from the stored columns — **never null**; `0` ⇔ never sealed; an earlier-cycle seal's retained positive value is carried (05 §2.4.1).

**Payload-immutability design.** v0.7 had no such trigger (only the §6 column grant). v0.8 adds `trg_acc1_change_request_immutable` (`BEFORE UPDATE`): `payload`, `payload_hash`, `change_type`, targets, `client_id`, `approval_mode`, `requested_by`, `idempotency_key`, `environment`, `expires_at_utc` never change after `INSERT` (i.e. from before approval is requested). `requested → applied` cannot alter target, payload, hash, reason, family, member list, versions or evidence binding; the grant stays as a second layer.

**Recovery-bind payload parsing / stamping.** `trg_acc1_recovery_bind` (05 §5): (1) stamp `created_xact_id`; (2) load the request, require `abort_closure`, `applied`, `applied_xact_id = pg_current_xact_id()`; (3) parse the stored payload, require `abort_target_id` = the request's own target column and `NEW.target_id` exactly once in `returned_members`; (4) stamp from the payload (overwriting the caller); (5) stamp pre-transition facts from the locked account row; (6) compare payload vs live (version, cycle, seal version, family, role) ⇒ `ACC1_CLOSURE_APPROVAL_STALE`; (7) reason-specific validation. A caller cannot cure a stale approval by inserting the live version.

**Four-way family-set equality.** For a master abort at commit: `payload.returned_members` = authoritative current master-directed family set (`master` + `default` + `master_directed_child` in `closure_family_member`) = `closure_recovery` targets = `closure_abort` history transitions in this transaction; each exactly once; `independent_preserved` excluded from all four (05 §5.3 S2). A request approved for F-old cannot operate on F-new (bind (6) and S2).

**Barrier target/cause binding.** `trg_acc1_closure_barrier` requires, for a barrier/pin/family-pointer clear: cause `closure_abort` with `cause_ref = X`; `X` applied in this transaction; exactly one recovery row with `target_id` = this row, `change_request_id = X`, `created_xact_id` = current. Another target's row, another cause's row, or an earlier transaction's row does not satisfy it.

**Family-aborted guard.** `trg_acc1_family_abort_guard` (immediate) refuses `open → aborted` unless `abort_change_request_id` names an abort request applied in this transaction whose stored payload names this family and master, **and** the master's recovery row for this family exists in this transaction. A bare `UPDATE closure_family SET family_status = 'aborted'` fails at the statement; the abort-set proof then proves the complete return at commit.

**Seal-pin `created_xact_id` design.** `closure_seal_pin.created_xact_id xid8 NOT NULL`, stamped by `trg_acc1_pin_stamp` (`BEFORE INSERT`). `trg_acc1_pin_readiness_window` requires the parent pin's `created_xact_id = pg_current_xact_id()` and the target in the legal sealing state (`closing`, no pin id, matching cycle); `trg_acc1_seal` requires the same `created_xact_id` for the pin it consumes. Late rows after commit are refused at insert; no `xmin`. The seal design does **not** rely on the seal request being applied in the sealing transaction (only the pin/readiness window needs a same-transaction bind), so there is one correlation system, not two (05 §5.0).

**Normative abort order (05 §5.1 = 02 §7.7 item 3).** BEGIN → lock (master first, children ascending) → re-read → verify payload bindings → request `applied` (stamps `applied_xact_id`) → INSERT stamped recovery rows → SET LOCAL cause settings; one `UPDATE` per row (no `version`/`closure_cycle`; trigger-owned) → `closure_family` `aborted` (master family) → audit → COMMIT (abort-set proof runs).

**Normative seal order (05 §5.2 = 02 §7.4 item 3).** BEGIN → lock → re-read (status, cycle, version, readiness, dependencies, final checker approval) → seal request `applied` → INSERT `closure_seal_pin` (stamped) → INSERT exact pin-readiness rows → verify approved attester list = pin-readiness set → SET LOCAL cause settings; **one** coherent target `UPDATE` (`status`, `closure_barrier`, `closure_seal_pin_id`, `closure_sealed_at_utc`; no `version`) → history (via trigger) → audit/outbox → COMMIT. Master-family ordering unchanged.

**Version owner.** `trg_acc1_status_transition` (`NEW.version := OLD.version + 1`). The application may add `WHERE version = expected_version` but never sets the stored version. `version_before`/`version_after` on history; the bijection compares them; `closure_sealed_at_version = OLD.version + 1` verified by `trg_acc1_seal`.

**Honest limits (stated in the pack).** The database still cannot prove IAM-02 authorisation of the approval (RF-01 / `IAM2-FIND-002`) or that a cited seal rejection is genuine (DCR-ACC-IAM-08); `checker_rejected_seal` stays hard-unavailable. Reason-specific evidence *sufficiency* is verified by the database only for `closure_initiation_withdrawn`, `family_completion_unattainable` and the `checker_rejected_seal` shape; for the other codes it stays an application check under lock (A4), reconciled by R-9, but every reason and evidence field is the approved payload's. `xid8`/`pg_current_xact_id()` need PostgreSQL ≥ 13, to be verified — not assumed — when the migration is written. The runtime role holds `INSERT` on `account_status_history` (unchanged), so a directly inserted history row is possible; it is refused at commit by `trg_acc1_history_abort_scope` and the live-row assertions (S4).
