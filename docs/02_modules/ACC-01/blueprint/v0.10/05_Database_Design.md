# ACC-01 Account Structure
## 05 Database Design (v0.10)

**Design only. No migration is written or authorised by this pack.** DDL below is illustrative of constraints, not a migration file. The migration number is assigned when the implementation task is approved (head is `071` at baseline `5a4f872`; other modules may take numbers first — do not pre-assign).

## 1. Schema, role, isolation

```txt
schema:      acc1
runtime role: role_acc1_runtime
```

Rules:

1. `role_acc1_runtime` has **zero** grants outside `acc1.*` — none into `clt1`, `led1`, `iam2`, `cfg1`, `sec1`. Same posture as `role_clt1_runtime`.
2. **No cross-schema foreign keys.** `client_id` is a value reference to `clt1.client_profile.client_id`, validated at write time through the CLT-01 seam; precedent: `iam2.user_role.client_id`, `led1.*.client_id`. Reasons: schema-level independence of module roles; no cross-module lock coupling; CLT-01 may legitimately move to a different store. The cost — no DB guarantee the client exists — is paid by reconciliation (file 13 check R-3) and by the write-time and resolve-time CLT-01 reads.
3. **No `DELETE` grant on any table.** Lifecycle is state, never removal.
4. **Column-level `UPDATE` grants** on `master_account` / `subaccount` / `account_restriction` / `account_change_request` exclude ownership and identity columns. **(R8, R8-F01.2)** On `master_account` and `subaccount` they also exclude **every transition-owned counter and pointer** — the one protected set of §2.2.1 — for `UPDATE` **and** for `INSERT`: `role_acc1_runtime` holds no column privilege on `version`, `close_change_request_id`, `closure_family_id`, `closure_seal_pin_id`, `closure_barrier`, `closure_cycle`, `closure_sealed_at_utc`, `closure_seal_version`, `closure_sealed_at_version` or `closed_at_utc`. Only `trg_acc1_counter_guard` (§5.4) assigns them.
5. No column anywhere holds an amount, balance, holding, price, limit value or ledger identifier (ACC-REQ-007). A schema-guard test asserts it (file 10).
6. No column is named `enabled`, `is_enabled`, `active_flag` or similar capability-style boolean (ACC-REQ-036). `is_default` is a structural marker, not a capability.
7. All timestamps `timestamptz`, suffixed `_utc`, matching CLT-01.
8. **(R8, R8-F04.3 — normative) `role_acc1_runtime` is a grantee, never an owner.** It MUST NOT own the `acc1` schema, any `acc1` table, sequence, view or index, or any function — in particular **no security trigger function** (`trg_acc1_*`, the `SECURITY DEFINER` restriction function of §5) — and it MUST NOT be a member (directly or through `INHERIT`) of any role that does. It holds no `TRIGGER`, `REFERENCES` or `TRUNCATE` privilege, no `CREATE` on schema `acc1`, no `SUPERUSER`/`BYPASSRLS`, and no `SET` privilege on the parameter `session_replication_role`. Consequently it **cannot** `ALTER TABLE … DISABLE TRIGGER`, `DROP TRIGGER`, `CREATE OR REPLACE FUNCTION` a trigger function, `ALTER … OWNER`, or `SET session_replication_role = replica` to make triggers inert. Every "regardless of grants" and "the database refuses" claim in this pack presupposes this rule; without it a trigger is a convention, not a control. The platform precedent is the same (`role_clt1_runtime` and the other module runtime roles are grantees; migrations 020…032). **(R9, R9-F01) `TEMPORARY` is deliberately NOT on that list.** `role_acc1_runtime` may hold the database `TEMPORARY` privilege (the PostgreSQL default, through `PUBLIC`) and may create temporary tables, views and sequences; **no ACC-01 correctness property depends on revoking it**, and revoking `TEMPORARY` from `PUBLIC` is a platform-wide choice this module neither makes nor requires. Temporary relations are treated as **attacker-controlled but irrelevant**, because every ACC-01 function pins and qualifies its name resolution (rule 10, §5.7). **This is a P1 (phase-1) implementation acceptance criterion** — asserted by catalogue checks and by attempting each forbidden statement as the runtime role (T-396); it is not left to review. Test-only owner roles used by raw-DB tests are separate roles that never exist in a production role set.
9. **(R8, R8-F01) Two layers, never one.** Ownership of the protected columns (§2.2.1) is enforced by **(1) privilege** — no column `INSERT`/`UPDATE` privilege for the runtime role — **and (2) an immediate database guard**, `trg_acc1_counter_guard` (§5.4), that runs on every `INSERT` and every `UPDATE`, whatever columns the statement names. **Why a `BEFORE` trigger may assign what the caller may not name:** PostgreSQL checks column privileges against the columns *named in the statement* (the `SET` list or the `INSERT` column list); a `BEFORE ROW` trigger assigning `NEW.<column>` is not a privilege check. The runtime role therefore never needs, and never receives, privilege on a protected column, while the guard still sets it — and because the runtime role is a grantee and not the table owner (rule 8) it cannot disable that guard. Neither layer is relied on alone.
10. **(R9, R9-F01 — normative, no exception) Name resolution is pinned for EVERY ACC-01 function, and every ACC-01 relation is schema-qualified. Both, never one.** Every function the migration creates in support of ACC-01 — every `trg_acc1_*` trigger function, the `SECURITY DEFINER` restriction function, and every helper or proof procedure they call — carries the function attribute `SET search_path = pg_catalog, acc1, pg_temp`, with `pg_temp` **explicit and LAST**; and **every `acc1` relation any such function reads or writes is written schema-qualified** (`acc1.master_account`, `acc1.subaccount`, `acc1.account_restriction`, `acc1.account_change_request`, `acc1.account_status_history`, `acc1.closure_recovery`, `acc1.closure_family`, `acc1.closure_family_member`, `acc1.closure_seal_pin`, `acc1.closure_seal_pin_readiness`, `acc1.closure_readiness`, `acc1.closure_attestation`). PostgreSQL searches the session's temporary schema **first** for relation names unless `pg_temp` is listed explicitly, so a runtime-created temporary table named like an `acc1` table would otherwise capture an unqualified reference. v0.9 specified `pg_catalog, acc1` for one function and nothing for the rest (R9-F01). The full rule, the function inventory and the tests are §5.7 and T-401…T-411. **The pinned path and the qualification each suffice on their own against a shadow table (verified on PostgreSQL 17.10); both are required so that a later edit that drops one still leaves the other.**

Constraints / indexes:

- **`FOREIGN KEY (master_account_id, client_id) REFERENCES acc1.master_account (master_account_id, client_id)`** — structural enforcement of ACC-REQ-004: a subaccount whose `client_id` differs from its master's cannot exist.
- `UNIQUE (master_account_id) WHERE is_default` — at most one default per master. It is deliberately **not** status-filtered: with ACC-R3-HD-01 the default is never `closed` while its master is non-`closed`, so "restore a default" never arises and no second default can ever be inserted (R3-F01). The structural invariant (ACC-REQ-050) is enforced by the deferred `trg_acc1_master_default_invariant` (§5).
- `UNIQUE (master_account_id, lower(name)) WHERE status <> 'closed'` — name unique among non-`closed` siblings (`closing` and `closure_sealed` included; RF-02).
- **`UNIQUE (subaccount_id, master_account_id, client_id)`** — the target of the restriction composite FK (RF-06).
- `INDEX (client_id, status)`, `INDEX (master_account_id, status)`.
- The name-uniqueness index above covers every status except `closed`, so `closing` and `closure_sealed` still hold their name and count against limits (RF-02).

#### 2.2.1 Column ownership on `master_account` and `subaccount` — the one protected set (R8, R8-F01.1)

v0.8 gave `role_acc1_runtime` a column `UPDATE` grant on the counters and pointers while the triggers that claim to own them fired only `BEFORE UPDATE OF status`; a statement that did not name `status` — for example `UPDATE … SET version = 10, closure_seal_version = 1` — bypassed every owner (R8-F01). v0.9 closes this by classifying **every** column of both tables (every column of §2.1 and §2.2 was reviewed) into exactly one class:

| Class | Columns | Writer | Enforced by |
|---|---|---|---|
| **I. Identity / creation** — immutable after `INSERT` | master: `id`, `master_account_id`, `client_id`, `client_status_at_creation`, `client_class_at_creation`, `creation_change_request_id`, `opened_at_utc`, `created_at_utc`. Subaccount: `id`, `subaccount_id`, `master_account_id`, `client_id`, `purpose`, `is_default`, `creation_change_request_id`, `opened_at_utc`, `created_at_utc` | `INSERT` only | No `UPDATE` grant; `trg_acc1_ma_immutable` / `trg_acc1_sa_immutable` (v0.9 adds `id` and the master's two creation snapshots to their lists) |
| **B. Business / profile** | master: `display_name`, `description`. Subaccount: `name`, `description` | Runtime `UPDATE` (column grant) | Column grant. Each actual change is **version-relevant** (§5.4 rule A) |
| **S. Status** | `status` | Runtime `UPDATE`, **only as the governed transition path** | The column privilege is kept (the existing design); *what* it may change to, under which cause, is decided by `trg_acc1_status_transition` (legality, cause), `trg_acc1_seal`, `trg_acc1_default_protected`. Naming `status` is not itself a transition (§5.4, "status named but unchanged") |
| **P. PROTECTED — transition-owned counters and pointers** | `version`, `close_change_request_id`, `closure_family_id`, `closure_seal_pin_id`, `closure_barrier`, `closure_cycle`, `closure_sealed_at_utc`, `closure_seal_version`, `closure_sealed_at_version`, `closed_at_utc` | **The database only** — `trg_acc1_counter_guard` (§5.4) | **Layer 1:** no `INSERT` and no `UPDATE` column privilege for `role_acc1_runtime` (§6). **Layer 2:** the immediate guard, on every `INSERT`/`UPDATE` |
| **M. DB-maintained** | `updated_at_utc` | The guard sets `clock_timestamp()` on a real change | No security meaning (never freshness, recency, state or identity — `version` is the freshness value). Not in the runtime grant |

**P is the one protected set** for both tables: nothing in §2.1/§2.2 is a transition-owned counter or pointer that is not in it, and a column added to either table must be placed in exactly one class before it can exist (schema-guard test, T-368). The runtime role's column privileges are exactly **B ∪ {`status`}** for `UPDATE` and the I/B/`status` columns the creation path supplies for `INSERT` (§6); it holds none on P or M.

**Two layers, stated once.** *Layer 1 (privilege):* a statement by `role_acc1_runtime` that names a P column fails with SQLSTATE `42501` before any trigger runs. *Layer 2 (immediate guard):* `trg_acc1_counter_guard` refuses (`ACC1_COUNTER_OWNERSHIP_VIOLATION`) any statement — whatever role issues it, **the owner included** — in which a P column's value differs from what the guard itself computes, so a grant regression, a future migration, a widened role or an owner-context statement does not reopen the gap. The claim "the database refuses a rewind of `version`, `closure_cycle`, `closure_seal_version`, `closure_sealed_at_version`, `close_change_request_id`, `closure_seal_pin_id` or `closure_family_id`" therefore rests on **both** layers, and each is tested on its own (T-367). The guard may assign what the caller may not name because column privileges are checked against the statement's named columns and not against `NEW.<column>` assignments made by a `BEFORE` trigger (§1 rule 9); the runtime role is a grantee, not the owner (§1 rule 8).

**Owner binding (RF-06) — two composite foreign keys:**

1. `FOREIGN KEY (master_account_id, client_id) REFERENCES acc1.master_account (master_account_id, client_id)` — always enforced; a restriction cannot name a master under a different client.
2. `FOREIGN KEY (subaccount_id, master_account_id, client_id) REFERENCES acc1.subaccount (subaccount_id, master_account_id, client_id)` (`MATCH SIMPLE`) — enforced for subaccount targets (`subaccount_id` non-null; skipped for master targets where the first FK suffices). Together with `CHECK ((target_type='subaccount') = (subaccount_id IS NOT NULL))`, a restriction **cannot pair client A / master A with client B's subaccount**.

`INDEX (master_account_id, status)`, `INDEX (subaccount_id, status)`, `INDEX (effective_from_utc, effective_until_utc)` (time-effective resolution). Append-oriented: only `status`, `lifted_*`, `lift_evidence_ref`, `cancelled_*`, `cancel_evidence_ref` are updatable. Housekeeping updates are permitted; enforcement never depends on them (file 06 §3).

**Maker-only evidence is scoped to the `applied` state (R8, R8-F03.2).** The `maker_only` evidence requirements are **conditional row `CHECK`s**, never unconditional `NOT NULL`s — row `CHECK`s are immediate, so an unconditional rule would refuse the `requested` `INSERT` that §2.4.2 mandates and, implemented literally, would refuse **every** closure initiation (the v0.8 inconsistency R8-F03):

```txt
CHECK (NOT (approval_mode = 'maker_only' AND status = 'applied') OR (
         entitlement_evidence_ref     IS NOT NULL   -- the IAM-02 attested entitlement evaluation (DCR-ACC-IAM-07/-06)
     AND actor_assertion_authority    IS NOT NULL   -- the authority IAM-02 verified the actor against
     AND sec_audit_ref                IS NOT NULL   -- the pre-allocated Critical audit reference (fail closed without audit)
     AND result_ref                   IS NOT NULL   -- the initiated target / family id
     AND approval_id IS NULL AND approval_id_source IS NULL            -- no checker (ACC-R3-HD-02); (R9, R9-F03.5) approval_id_source added
     AND approver_user_id IS NULL AND approval_policy_id IS NULL ))    -- no checker (ACC-R3-HD-02)
```

The **maker actor evidence** is the existing `requested_by` (the IAM-01-authenticated session principal, `NOT NULL` from the `INSERT`) together with `actor_assertion_authority`; no new column is introduced. For `status = 'requested'` every one of those apply-owned columns may — and, by the `INSERT` rule of §2.4.2, must — be NULL. **No checker-only field is required for `maker_only`** — and **(R9, R9-F03.5) each of the four is required to be NULL by the `CHECK` above, not merely described as NULL**: `approval_id`, `approval_id_source`, `approver_user_id` and `approval_policy_id` (no approval exists; the schema, this prose, file 02 §7.1 and T-390/T-391/T-428 now say the same thing). The corresponding rule for `maker_checker` rows is unchanged: `approval_id_source`, `entitlement_evidence_ref` and `actor_assertion_authority` are required, in an `applied` row, when `approval_id_source = 'iam2_attested'`.

#### 2.4.1 The canonical stored `abort_closure` payload (R7, R7-F01(c))

**The stored approved payload is the authority.** The database does not treat `target_version_approved`, `reason_code`, the evidence references, or the family/cycle/member data as caller assertions: `trg_acc1_recovery_bind` (§5) reads them from the immutable stored `payload` (§2.4.2) of the applied request. The checker's approval is bound to that immutable payload/hash by the existing maker-checker contract (IAM-02; unchanged — no IAM redesign here). The database proof is therefore exactly: **the account transitions and the `closure_recovery` rows agree with THE STORED APPROVED REQUEST PAYLOAD** (it does not, and cannot, prove IAM-02 authorisation — that stays RF-01 / `IAM2-FIND-002`).

Inside the canonical envelope `{change_request_id, change_type: "abort_closure", client_id, target ids, parameters, requested_by}`, `parameters` has exactly this shape (ACC vocabulary; the names are the `closure_recovery` column names of §2.8):

```json
{
  "abort_target_type": "independent | master",
  "abort_target_id": "sac_… | mac_…",
  "reason_code": "<the closed set of §2.8>",
  "closure_family_id": "acr_… | null",
  "evidence_ref": "… | null",
  "evidence_owner_target_id": "… | null",
  "rejection_approval_request_id": "… | null",
  "rejection_decision_id": "… | null",
  "returned_members": [
    {
      "target_type": "master_account | subaccount",
      "target_id": "mac_… | sac_…",
      "approved_version": 0,
      "closure_cycle": 0,
      "closure_seal_version": 0,
      "family_role": "master | default | master_directed_child | independent_own_abort"
    }
  ]
}
```

- **Independent abort:** `abort_target_type = "independent"`, `closure_family_id = null`, and `returned_members` contains **exactly one** entry — the independent target itself, `family_role = "independent_own_abort"`.
- **Master-family abort:** `abort_target_type = "master"`, `abort_target_id` = the master, `closure_family_id` = the master's current family id (non-null), and `returned_members` contains **exactly** the master (`master`), the default (`default`) and every master-directed child (`master_directed_child`) of that family. It **excludes** every `independent_preserved` member (they are never returned — ACC-R4-HD-01/ACC-R5-HD-01).
- `abort_target_id` equals the request's own immutable `target_master_account_id` / `target_subaccount_id` column; the same fact is stored twice and compared by the bind trigger.
- **Canonical `closure_cycle` / `closure_seal_version` representation (stated once).** Each is an **integer ≥ 0 copied from the actual stored column** — never JSON `null`, never omitted. `closure_seal_version = 0` **iff** the member has never been sealed. A member that is `closing` in a later cycle after sealing in an earlier, aborted cycle carries that **retained positive** seal version (an abort never resets it, §2.1). A null, omitted or non-integer value makes the payload malformed (`ACC1_CLOSURE_ABORT_INVALID`).
- `approved_version` is the member's `version` when the checker approved (R5-F03). `reason_code`, `evidence_ref`, `evidence_owner_target_id` and, for `checker_rejected_seal` only, `rejection_approval_request_id` / `rejection_decision_id` are the approved values (`rejection_*` non-null iff `checker_rejected_seal`, the §2.8 `CHECK`).
- No PII and no free text beyond reason/evidence references, like every canonical payload.

#### 2.4.2 Request status guard, `applied_xact_id` and payload immutability (R7, R7-F01(b)/(c))

v0.7 had **no** database guard on this table: its status was protected only by a value `CHECK`, and payload immutability only by the column `UPDATE` grant of §6 (a privilege rule, silent against a role that holds the grant on another column). v0.8 adds two triggers; the CLT-01/CFG-01 request tables that ACC-01 mirrors have neither, so there is no pattern to defer to.

**`trg_acc1_change_request_status`** — immediate, `BEFORE INSERT OR UPDATE OF status, applied_at_utc, applied_xact_id, approval_id, approval_id_source, authenticated_apply_actor_id, approver_user_id, approval_policy_id, session_principal_id, actor_assertion_authority, entitlement_evidence_ref, attested_credential_scope, result_ref, sec_audit_ref` (the **apply-owned fields**). Because it is a column-list trigger it fires whenever the statement **names** any of them, even to write the value already there.

- `INSERT`: `status` must be `requested` and every apply-owned field NULL. (A `maker_only` closure initiation is `INSERT`ed `requested` and then `UPDATE`d `applied` inside its one transaction, so it acquires `applied_xact_id` exactly as any other request.)
- `UPDATE` when `OLD.status <> 'requested'`: **always refused** (`ACC1_CHANGE_REQUEST_STATE_INVALID`). `applied`, `cancelled` and `expired` are terminal, so none of `applied → applied`, `applied → requested`, `applied → cancelled`, `cancelled → applied`, `expired → applied`, or any other rewrite, is possible — and a **no-op** `UPDATE … SET status = 'applied' WHERE status = 'applied'` is refused because it names a governed column. It therefore can never re-stamp `applied_xact_id` or `applied_at_utc`.
- `UPDATE` when `OLD.status = 'requested'`: `NEW.status` must be `applied`, `cancelled` or `expired` (or stay `requested` with every apply-owned field unchanged).
- On `requested → applied`: **`NEW.applied_xact_id := pg_current_xact_id()`** and **`NEW.applied_at_utc := clock_timestamp()`**; whatever the caller wrote in either column is discarded. On `requested → cancelled | expired` both are forced NULL.
- `applied_xact_id` is absent from the runtime `UPDATE` grant (§6): the application cannot even name it. The trigger is the only writer.

**`trg_acc1_change_request_immutable`** — immediate, `BEFORE UPDATE` (every `UPDATE`): refuses (`ACC1_CHANGE_REQUEST_STATE_INVALID`) any change to **`id`** (the internal key — **(R8, R8-F04.5)** an immutable identity column from `INSERT`), `change_request_id`, `change_type`, `approval_mode`, `target_master_account_id`, `target_subaccount_id`, `client_id`, **`payload`**, **`payload_hash`**, `requested_by`, `idempotency_key`, `environment`, `expires_at_utc`, `created_at_utc`. The action-relevant payload is immutable **from `INSERT`** — which is before the approval is requested — so a `requested → applied` transition cannot change the target, payload, hash, reason, family, member list, versions or evidence binding. There is no "approve payload A, apply payload B". (The column grant of §6 is kept as a second layer.)

**Terminal apply-owned fields and pre-allocated references (R8, R8-F04.4).** Once a request is `applied`, **every** apply-owned field — `approval_id`, `approval_id_source`, `authenticated_apply_actor_id`, `approver_user_id`, `approval_policy_id`, `session_principal_id`, `actor_assertion_authority`, `entitlement_evidence_ref`, `attested_credential_scope`, **`result_ref`**, **`sec_audit_ref`**, `applied_at_utc`, `applied_xact_id` — is immutable (the status guard refuses any later write, even of the same value). Therefore **all of them must be available when the single `requested → applied` `UPDATE` is issued**, and the `UPDATE` writes them in that one statement. For a field that references something written later in the same transaction, the reference is **pre-allocated** before the apply and the later write is made *with that reference*:

- **`sec_audit_ref`** — the application generates the Critical audit reference `A` before step 4 of the §5.1/§5.2/§5.6 orders. It is written to the request at the apply, to every recovery row (`closure_recovery.sec_audit_ref`, §5.1 step 5) and history row (via the `acc1.sec_audit_ref` cause setting) the transaction writes, and the Critical audit/outbox record written later (§5.1 step 8; §5.2 step 10; §5.6 step 7) **uses the same `A`**. The audit write failing rolls back the whole transaction, request included (fail closed); an `UPDATE` of `sec_audit_ref` after the apply is **never** attempted and would be refused.
- **`result_ref`** — a `seal_closure` request's `result_ref` is the pre-allocated `seal_pin_id` (§2.9, §5.5); an `abort_closure` request's is the `abort_target_id`; a maker-only initiation's is the initiated target (a master initiation: the master id, the family id being the request id itself); a `create_*` request's is the pre-allocated new account id; an `apply_restriction` request's the pre-allocated restriction id. Each is known before the apply.
- The same principle applies to **every** request type whose audit or result reference is terminal: nothing is "filled in later" on an applied row.

**`updated_at_utc` (R8, R8-F04.6).** On a request — including a terminal one — `updated_at_utc` may remain writable only because it is **DB-maintained** (set to `clock_timestamp()` by `trg_acc1_change_request_immutable` on every `UPDATE`; the runtime grant of §6 no longer lists it) and carries **no security meaning**. It is never used to decide approval freshness, same-transaction state, payload identity, request terminality or any recency; those are decided by `status`, `applied_xact_id`, the immutable payload and the live-row bindings only.

**Maker-only initiation lifecycle (R8, R8-F03.1/.3).** A `maker_only` closure initiation is a request like any other: **(1)** `INSERT` with `approval_mode = 'maker_only'`, `status = 'requested'`, every apply-owned field NULL — the `INSERT` rule above; **(2)** the maker entitlement / actor-binding verification of file 02 §7.1 items 1–2 (DCR-ACC-IAM-07/-06, performed before the local transaction per A3 discipline) is complete; **(3)** one `UPDATE requested → applied` **in the same transaction**, writing `entitlement_evidence_ref`, `actor_assertion_authority`, the pre-allocated `sec_audit_ref` and `result_ref`; `trg_acc1_change_request_status` stamps `applied_xact_id` and `applied_at_utc`; the maker-only `CHECK` above is then satisfied; **(4)** the account transition into `closing` runs under that applied request (§5.4 rule E, §5.6); **(5) (R9, R9-F02)** the transaction cannot commit unless that transition — and, for a master, its `closure_family` and the immutable member snapshot — actually exists: the deferred completeness proof `trg_acc1_initiation_apply_complete` (§5.6.1) refuses an applied initiation that has no initiation effect, whatever happened to a subtransaction in between. A direct `INSERT` with `status = 'applied'` is refused by this guard's `INSERT` rule; a `requested → applied` `UPDATE` without the maker-only evidence is refused by the scoped `CHECK`; no approval token, checker or IAM-02 approval route exists in this path.

#### 2.4.3 The canonical stored `seal_closure` payload (R8, R8-F02.1)

As for `abort_closure` (§2.4.1), **the stored approved `seal_closure` payload is the authority** for every approval fact on the seal pin. It is immutable from `INSERT` (`trg_acc1_change_request_immutable`) and is **read by the database** (`trg_acc1_seal_pin_bind`, §5.5). It uses the existing ACC vocabulary (file 04 §2.1.1 lists the same members in prose; this is their exact stored shape). Inside the canonical envelope, `parameters` is exactly:

```json
{
  "target_type": "master_account | subaccount",
  "target_id": "mac_… | sac_…",
  "approved_version": 0,
  "closure_cycle": 0,
  "closure_change_request_id": "acr_…",
  "closure_family_id": "acr_… | null",
  "required_attesters": [
    {
      "attester_module": "LED-01",
      "authenticated_service_identity": "…",
      "attester_contract_id": "…",
      "attester_contract_version": "…",
      "readiness_id": "crd_…",
      "readiness_seq": 0,
      "journal_watermark": "…",
      "readiness_payload_hash": "sha256:…"
    }
  ],
  "required_attester_set_hash": "sha256:…",
  "family_set_hash": "sha256:… | null"
}
```

- `approved_version` is the target's `version` when the checker approved; `closure_cycle` and `closure_change_request_id` (the closure **initiation** id, = `close_change_request_id` of the target) are the cycle and initiation the approved readiness belongs to. `closure_family_id` is non-null for a master or a master-directed child (the default included) and null for an independent target. `family_set_hash` is non-null **only** for a master (the set hash of immutable seal facts, §2.10) and null otherwise.
- `required_attesters` is the checker-approved pinned required attester set: **non-empty** (an empty list is malformed — `ACC1_CLOSURE_ATTESTERS_UNCONFIGURED` at submit, and unrepresentable in the database, §2.9), one element per attester, each carrying the strong identity of R5-F04 and its pinned readiness identifiers. `required_attester_set_hash` is the checker-approved fingerprint of that list; the database compares it for **string equality only**, beside the normative **relational equality** of the list with the pin-readiness rows (§5, `trg_acc1_seal`) — it never recomputes a fingerprint.
- **(R9, R9-F03.4) `required_attesters` is a set with EXACTLY-ONCE semantics, and equality with the database is BIDIRECTIONAL.** The stored list is valid only if it is **non-empty**, has **no duplicate `attester_module`**, and has **no duplicate `readiness_id`**; a payload with a duplicated element (e.g. `[A, A]`) is malformed and is refused with `ACC1_SEAL_PIN_INVALID` by `trg_acc1_seal_pin_bind` (§5.5 step 9) — it can never become a pin. The relational proof of `trg_acc1_seal` and `trg_acc1_seal_pin_complete` then requires **all** of: (i) the row count of `closure_seal_pin_readiness` for the pin equals `jsonb_array_length(required_attesters)` and `pinned_required_attester_count`; (ii) **payload → database:** every payload element (`attester_module`, `authenticated_service_identity`, `attester_contract_id`, `attester_contract_version`, `readiness_id`) matches **exactly one** pin-readiness row; (iii) **database → payload:** every pin-readiness row matches **exactly one** payload element. A one-directional check would accept the payload `[A, A]` against the rows `[A, B]`; (i) with the distinctness rule and (ii)+(iii) together form a bijection, so it cannot. `required_attester_set_hash` is compared for string equality as **evidence only** — hash equality is never the relational proof, and a set that differs from the payload is refused even when the hashes are equal.
- `target_type` and `target_id` equal the request's own immutable `target_master_account_id` / `target_subaccount_id` column (stored twice and compared). A missing, null or ill-typed field (`jsonb_typeof` is tested; nothing is cast) makes the payload malformed (`ACC1_SEAL_PIN_INVALID`).
- No PII and no free text; the database does **not** attest that IAM-02 authorised the approval (RF-01 / `IAM2-FIND-002`, unchanged) — it proves only that the pin, the account transition and the readiness set **agree with the stored approved payload**.

### 2.8 `acc1.closure_recovery` (governed abort; append-only) — **(R2, ACC-R2-HD-03)**

**(R7, R7-F01(c) — supersedes the R6 intro) The approved payload is the authority, and there is one model: STAMPING.** The application apply path constructs the `INSERT`, but it names only `target_id`, `change_request_id`, `to_status` (the recomputed operational projection), `sec_audit_ref` and `occurred_at_utc`. **Every other column is written by `trg_acc1_recovery_bind` (§5), never by the caller:** the *approval facts* — `abort_target_type`, `abort_target_id`, `reason_code`, `evidence_ref`, `evidence_owner_target_id`, `rejection_approval_request_id`/`rejection_decision_id`, `closure_family_id`, `family_role`, `target_type` and `target_version_approved` — are stamped **from the immutable stored payload** of the applied `abort_closure` request (§2.4.1); the *pre-transition facts* — `from_status`, `abort_target_from_status`, `closure_cycle_before/after`, `closure_seal_version_at_abort`, `barrier_cleared` — from the locked account rows; and `created_xact_id` from `pg_current_xact_id()`. **Pre-seal `CHECK` — scoped to the abort target (R5, ACC-R5-HD-01, R5-F01; replaces the v0.5 per-row `CHECK`).** `CHECK (reason_code NOT IN ('checker_rejected_seal','closure_initiation_withdrawn') OR abort_target_from_status = 'closing')`. v0.5 applied `from_status = 'closing'` to **every returned row**, which made both grounds unreachable in a master family once any member had sealed (R5-F01); that per-row reading is **withdrawn**. The structural rule is now:

- **Independent target:** its own row is the target row, so `from_status = abort_target_from_status = 'closing'` — a pre-seal ground is never legal once that target is `closure_sealed`.
- **Master family:** a pre-seal ground requires (a) the abort target is the **master** (`abort_target_type = 'master'`); (b) the master's own `from_status = 'closing'` at the time of the abort (so (c) the master has no successful seal in the current cycle — `closing → closure_sealed` is the only seal and only a governed abort, which bumps the cycle, leaves `closure_sealed`); (d) every returned member belongs to the **current** family (`closure_family_id`, current `closure_cycle`); (e) each returned member's `from_status` is `closing` **or** `closure_sealed`; (f) no returned member is already `closed` (the `from_status` `CHECK`). Non-target rows (the default, master-directed children) **may** carry `from_status = 'closure_sealed'`: their barriers are cleared **only** inside this governed master-family abort transaction (ACC-R3-HD-01 item 8, ACC-R5-HD-01) and never by any independent reopening.
- **Converse (unchanged by ACC-R5-HD-01):** once `master.status = closure_sealed`, neither pre-seal ground is legal for the family; a sealed master family is recoverable only on an evidence-conditioned ground (§2.8 `reason_code`, 1a of file 02 §7.7).

`closure_barrier` being false on the target row is implied by the existing `CHECK (closure_barrier = (status IN ('closure_sealed','closed')))`.

**(R6, R6-F01) This `CHECK` and the converse it encodes are now true of the database's own record of the target's status**, because `abort_target_from_status` is stamped by `trg_acc1_recovery_bind` from the locked target row itself (above), not written by the caller. A row asserting `abort_target_from_status = 'closing'` for a master whose actual stored `status` is `closure_sealed` cannot be constructed: the trigger overwrites the caller's value with `'closure_sealed'` before the `CHECK` ever runs, and the `CHECK` then refuses the pre-seal `reason_code`. v0.6's text calling this "structurally impossible" was accurate in intent but premature in fact (R6-F01, attack (a)); it is accurate now.

Append-only (same trigger). One row per **returned** target (a master abort writes one per returned row: the master, the default and every master-directed child). **Independent closures preserved by a master abort get no row — including one whose evidence was cited as the abort's ground** (R4-F02, R5-F02): the row set written is exactly the family's returned membership, never the independent member. **(R5, R5-F01; R7)** The **abort-set proof** (§5.3), evaluated from four deferred entry points (at commit, or earlier under `SET CONSTRAINTS … IMMEDIATE` — correct whenever it fires, R8-F04.1), enforces this: the rows of one abort share one `abort_target_id`, `abort_target_type`, `abort_target_from_status`, `reason_code` and `change_request_id`; exactly one row is the target's own; and, for a master abort, the **four sets are equal** — the stored payload's `returned_members`, the authoritative current `master`+`default`+`master_directed_child` members of `closure_family_id`, the `closure_recovery` targets, and the `closure_abort` `account_status_history` transitions written in this transaction. **(R6, R6-F01C/D; R7, R7-F01(a))** The same proof requires a **two-way bijection** between recovery rows and same-transaction history rows, so "no partial family recovery" is a property of the account rows that **actually transitioned**, and neither direction depends on the other table having at least one row first.

**`closure_seal_pin_readiness` is the pinned REQUIRED ATTESTER SET for this seal, not merely a readiness copy (rewritten, R4-F01/R4-F04).** `(seal_pin_id, attester_module)` primary key **and, (R9, R9-F03.4), `UNIQUE (seal_pin_id, readiness_id)`** (a readiness row is pinned at most once per pin); `readiness_id` **FK → `closure_readiness.readiness_id`**, `readiness_seq`, `journal_watermark`, `readiness_payload_hash` (copied at seal, so the pin is self-contained). **(R5, R5-F04) The pinned attester identity is a real identity, not a module label:** each row also carries, copied from its readiness row, `authenticated_service_identity`, `attester_contract_id` and `attester_contract_version` (NOT NULL). The readiness row and **every later attestation row** must record the **same** authenticated peer identity and contract identity; `binding_ok` (§2.7) and completion (§5 `trg_acc1_seal`) verify equality to this pin row, so a changed base URL, endpoint, deployment or service instance can never silently substitute a different security identity for a pinned attester. Its row set — one row per attester **configured at the moment of seal** — is, from the seal onward, the **authoritative, immutable list of attesters completion must have a clear latest attestation from**. It **replaces "every configured attester" as the completion criterion**: an attester later **removed** from configuration does not reduce what completion requires (its pinned row stays, and its last-known attestation, or the absence of a fresh one, still governs); an attester **added** to configuration after this seal is **not** required for this already-sealed family or target unless a new, governed reseal binds it. Both tables are append-only (`trg_acc1_append_only`); the pin is **never edited**, an abort leaves it as evidence and clears only the target's `closure_seal_pin_id`, and a later seal writes a **new** pin at a strictly higher `closure_seal_version` with its own, freshly derived required attester set.

**Re-attestation after the seal is expected and changes nothing pinned (R4-F01).** A member's attestation may be re-collected any number of times after its own seal (a prior `clear` row aged past `ACC1_ATTESTATION_MAX_AGE_SECONDS`, or a prior `blocked`/`unavailable` row later recovering) without touching `closure_seal_pin`, `closure_seal_pin_readiness`, `family_set_hash`, `closure_cycle` or `closure_seal_version`. Completion always reads the **latest** row per pinned attester at the member's current seal version (file 05 §2.7, §5) — never the row current at seal time. This is unchanged from v0.4 for an **independent** target; the R4-F01 correction is that the **master's** family-level check must do the same (§2.10).

## 5. Triggers (all in the migration, all tested)

### 5.0 Transaction identity — ONE meaning (R7, R7-F01(b))

**Normative.** ACC-01 has exactly **one** notion of "the same transaction": the value of **`pg_current_xact_id()`** (type `xid8`), the identity of the current **top-level** transaction. Every "in this transaction" property in this pack is an equality against it, held in a first-class, database-stamped column:

| Column | Stamped by | Records |
|---|---|---|
| `account_change_request.applied_xact_id` | `trg_acc1_change_request_status`, on `requested → applied` | the transaction that applied the request |
| `closure_recovery.created_xact_id` | `trg_acc1_recovery_bind` (`BEFORE INSERT`) | the transaction that wrote the recovery row |
| `account_status_history.created_xact_id` | `trg_acc1_history_stamp` (`BEFORE INSERT`) | the transaction that wrote the history row |
| `closure_seal_pin.created_xact_id` | `trg_acc1_pin_stamp` (`BEFORE INSERT`) | the transaction that wrote the pin |

- **"Applied in this transaction"** means, and only means: `request.status = 'applied' AND request.applied_xact_id = pg_current_xact_id()`. Every abort path uses this one predicate — `trg_acc1_status_transition`, `trg_acc1_recovery_bind`, the abort branch of `trg_acc1_counter_guard` (v0.8's `trg_acc1_closure_barrier`, folded in, §5.4), `trg_acc1_family_abort_guard` and the deferred abort-set proof (§5.3). The v0.7 wording that left the choice between `xmin` and `pg_current_xact_id()` to an "established pattern" is **withdrawn**: no such pattern exists (no migration on `main` uses either), and the two are not alternatives.
- **Database-owned.** No caller can supply or override any of these columns. Each is assigned inside a trigger (`NEW.<col> := pg_current_xact_id()`); the runtime role has no `UPDATE` grant on `applied_xact_id` (§6); the request table is guarded (§2.4.2) and the other three tables are append-only.
- **Independent of `xmin`.** ACC-01 never reads `xmin`/`xid` row-version attributes and never compares one with an `xid8`. `xmin` names the transaction that last wrote a row *version* — so an old applied request that is merely rewritten would carry the current `xmin`; that is not the property required. `applied_xact_id` records the *applying* transaction itself and is immutable once set (§2.4.2).
- **Savepoint-stable.** `pg_current_xact_id()` returns the top-level transaction id even inside a subtransaction (`SAVEPOINT`, or an ORM/retry helper's nested block); the identity does not change when a savepoint is opened, released or rolled back to. A legitimate transaction is therefore never refused merely because it used a subtransaction. (A write made inside a subtransaction that is rolled back is undone with it, so a stamp exists only if its row write survived.)
- **Same value at statement time and at commit.** Immediate triggers evaluate the predicate at their statement; deferred constraint triggers evaluate it at commit, inside the same top-level transaction, where it is the same value.
- **Platform requirement.** `xid8` and `pg_current_xact_id()` exist from PostgreSQL 13. The migration task must confirm the platform's PostgreSQL major version supports them and fail loudly if not (this pack does not assume the version; it is verified when the migration is written, §8). Nothing here branches on the environment.
- **Seal (R8, R8-F02 — rewritten; v0.8's "the seal design does not require the seal request to have been applied in the sealing transaction" is withdrawn).** The seal request **is** applied in the sealing transaction (§5.2 step 4), and the seal pin is legal **only** if `trg_acc1_seal_pin_bind` finds that request `status = 'applied' AND applied_xact_id = pg_current_xact_id()` — the same predicate as every abort path, paired with the live-row bindings of §5.5. The pin's own `created_xact_id` remains the window for `trg_acc1_seal` and `trg_acc1_pin_readiness_window`. There is one correlation mechanism, not two.
- **Correlation only, never identity (R8, R8-F04.2).** `applied_xact_id` and `created_xact_id` are **CURRENT-TRANSACTION CORRELATION values only**. They are **not** permanent, globally unique transaction identifiers. After a logical dump/restore, or a logical-replication migration into another cluster, an old stored `xid8` may eventually coincide with a *future* `pg_current_xact_id()` of the new cluster; `pg_upgrade` carries the transaction epoch and state differently again. Therefore **no long-term security decision relies on `xid8` uniqueness**: every same-transaction predicate in this pack is **paired with authoritative live bindings** — the target row, its `version`, `closure_cycle`, `closure_seal_version`, `close_change_request_id`, the pin pointer, the request `status`, the pin/recovery/history state and the **cause** (`cause_ref`) — so a recurring `xid8` value cannot by itself ground a new action (an `xid8` match with a stale version, cycle, seal version or request state is refused by the live binding). A request once used as a cause is also consumed by a live-state fact independent of `xid8` (a `closure_initiation` history row for that target and request; a pin with that `seal_change_request_id`; the moved cycle and version after an abort). Reconciliation (file 13) may **display** an `xid8` as audit metadata only; no reconciliation or authorisation rule uses its uniqueness.
- **Name resolution is pinned (R9, R9-F01).** Every "the trigger refuses" and "the database reads" statement in this section also presupposes §1 rule 10: each function resolves relations only through `SET search_path = pg_catalog, acc1, pg_temp` **and** schema-qualified names (§5.7), so a temporary table created by the runtime role can neither feed a trigger forged evidence nor capture a trigger's write.
- **Runtime role is not an owner (R8, R8-F04.3).** Every statement in this section that a trigger "refuses" presupposes §1 rule 8: `role_acc1_runtime` owns none of the `acc1` objects and cannot disable a trigger, replace a trigger function or set `session_replication_role`.

### 5.1 Normative abort statement order (R6-F02; amended R7)

**(R6, R6-F02)** v0.6's narrative order (02 §7.7 item 3: mutate, then clear the barrier, then write history and a recovery row) contradicted the immediate triggers above, which require the recovery row and the applied request to already exist when the account `UPDATE` runs. This is the **one normative order** for `abort_closure` — restated in 02 §7.7 item 3, which this section and that one must not diverge from. **It overrides the generic A4 wording of file 02 §2 ("mutate; write history; set request applied") for `abort_closure`** (R7-F02.1); an ordinary change type keeps its own specific apply order.

```txt

 0. BEGIN.
 1. Lock the abort target and every returned family member, master row first, then children
    in ascending internal id (the established lock order, §7 rule 5h).
 2. Re-read target status, versions, family, cycle, seal versions, evidence, dependency state.
 3. Verify the maker-checker approval and that every binding of the STORED payload (version,
    closure_cycle, closure_seal_version, family id, role, exact returned set) still holds
    (application, A3/A4). The stored payload is the only source of approved values.
    Pre-allocate the Critical audit reference A (R8, §2.4.2): it is generated now, before the
    request is applied, and used at steps 4, 5, 6 and 8.
 4. Move the abort_closure change request requested -> applied in ONE UPDATE that writes every
    apply-owned field at once (R8, R8-F04.4): sec_audit_ref = A, result_ref = abort_target_id
    and the attested approval fields. Nothing apply-owned is written after this statement (the
    row is then terminal). trg_acc1_change_request_status stamps applied_xact_id =
    pg_current_xact_id() and applied_at_utc. ("Applied in this transaction" = status 'applied'
    AND applied_xact_id = pg_current_xact_id(), §5.0 — paired with the live bindings.)
 5. INSERT one closure_recovery row per payload.returned_members entry, BEFORE any account
    mutation. The caller names only target_id, change_request_id, to_status, sec_audit_ref (= A)
    and occurred_at_utc. trg_acc1_recovery_bind (immediate) reads the stored payload, stamps every
    other column and created_xact_id, and refuses a stale or foreign row (§2.8).
 6. SET LOCAL the acc1.cause_type = 'closure_abort' / cause_ref = <request id> /
    sec_audit_ref = A / actor settings (trg_acc1_status_history needs them), then, for each
    returned target, ONE UPDATE per row that names ONLY status (the recomputed operational
    projection) — R8, R8-F01: the statement names no protected column. trg_acc1_counter_guard

 7. Master-family abort only: closure_family.family_status: open -> aborted with
```

**Master-family sealing is unchanged (ACC-R3-HD-01):** every master-directed child (the default included) seals first, on its own request and its own pin, in its own transaction following this order; the master seals last, in a transaction that additionally re-reads every child at step 3 under the master-then-children lock order and satisfies `trg_acc1_seal`'s master conditions at step 8 (every master-directed member `closure_sealed` with barrier, intact pin and a latest `clear` `binding_ok` attestation; every `independent_preserved` member `closed`; `family_set_hash` equal to the recomputed set hash). No rule of the family design is changed by this section.

**Savepoints (R8, R8-F02.5):** the two structures that matter are specified in §5.5 and tested (T-378, T-379); in short — a pin and its readiness rows created **after** a `SAVEPOINT` roll back together with a seal `UPDATE` that fails and is rolled back to that savepoint, whereas a pin created **before** the savepoint and left without its seal is refused by the deferred pin proof at `COMMIT`.

### 5.3 The abort-set proof — one deferred procedure, four entry points (R7, R7-F01(a)/(c))

**Timing (R8, R8-F04.1 — replaces v0.8's "evaluated at commit, once per distinct abort request `X`").** PostgreSQL queues a constraint-trigger event **per row/event**; each queued event fires separately. An event fires at `COMMIT` — **or earlier**, if any role executes `SET CONSTRAINTS … IMMEDIATE` (which fires the queued events at that point; it does not re-fire them at commit). The proof is a **read-only, idempotent** procedure, so it may run several times for one abort request `X` (once per queued row event) and repeated evaluation is harmless; ACC-01's runtime apply flows do **not** issue `SET CONSTRAINTS … IMMEDIATE`, **but correctness does not depend on that.** The normative property is: **the proof is correct whenever it fires** — a premature firing can only refuse (it sees a state the transaction has not finished building) and can never admit a violation, and **every later mutation of a fact the proof asserts either queues a fresh relevant constraint-trigger event or is refused immediately** — the account counters and pointers, the one class of fact for which that was not true in v0.8, are now closed by `trg_acc1_counter_guard` (§5.4, R8-F01): no statement can change them outside their owning transitions, and each owning transition is itself an `UPDATE` whose events are queued. The proof is evaluated for `X` from any of four `DEFERRABLE INITIALLY DEFERRED` constraint triggers: **(E1)** `trg_acc1_recovery_scope` — `AFTER INSERT` on `closure_recovery` (`X = NEW.change_request_id`); **(E2)** `trg_acc1_history_abort_scope` — `AFTER INSERT` on `account_status_history` `WHEN (NEW.cause_type = 'closure_abort')` (`X = NEW.cause_ref`); **(E3)** `trg_acc1_abort_apply_complete` — `AFTER UPDATE OF status` on `account_change_request` for an `abort_closure` moved `requested → applied`; **(E4)** `trg_acc1_family_membership` — when a `closure_family` becomes `aborted` (`X = NEW.abort_change_request_id`). **No direction depends on the other table already holding a row**: E2 fires with zero recovery rows, E1 with zero history rows, E3 with neither, E4 with neither. Let `P` be `X`'s stored payload (§2.4.1) and `M_t` its `returned_members` entry for target `t`. The proof requires:

- **S1 — the request.** `X` is an `abort_closure`, `status = 'applied'`, `applied_xact_id = pg_current_xact_id()`.
- **S2 — set equality (four-way).** `PAY` = the `target_id`s of `P.returned_members` (non-empty); `FAM` = the `master`, `default` and `master_directed_child` members of `P.closure_family_id` in `closure_family_member` (master abort only); `REC` = the `target_id`s of `closure_recovery` rows with `change_request_id = X`; `HIS` = the `target_id`s of `account_status_history` rows with `cause_type = 'closure_abort'`, `cause_ref = X` and `created_xact_id = pg_current_xact_id()`. **Master abort: `PAY = FAM = REC = HIS`. Independent abort: `PAY = REC = HIS = {abort_target_id}`.** Each element occurs **exactly once** in `REC` and in `HIS`. An `independent_preserved` member is in none of the four sets. A request approved for family F-old cannot operate on F-new: F-old's membership rows are not the current `FAM`, and `trg_acc1_recovery_bind` (6) compared `P.closure_family_id` with the live family.
- **S3 — pairwise fact match for every target `t`** (recovery row `R_t`, history row `H_t`, payload entry `M_t`): `R_t.created_xact_id = H_t.created_xact_id = pg_current_xact_id()`; `R_t.from_status = H_t.from_status`; `R_t.to_status = H_t.to_status`; `H_t.version_before = R_t.target_version_approved = M_t.approved_version`; `H_t.version_after = H_t.version_before + 1`; `R_t.closure_cycle_before = M_t.closure_cycle` and `R_t.closure_cycle_after = R_t.closure_cycle_before + 1`; `R_t.closure_seal_version_at_abort = M_t.closure_seal_version`; `R_t.family_role = M_t.family_role`; `R_t.closure_family_id` equals (null-safe) `P.closure_family_id`; and the stamped payload-level columns of `R_t` (`abort_target_type`, `abort_target_id`, `reason_code`, `evidence_ref`, `evidence_owner_target_id`) equal `P`'s. **The payload is one side of every comparison; a caller value is never compared with itself.**
- **S4 — live-row assertions** (a deferred trigger sees the transaction's own pending writes): the live row of each `t` has `closure_cycle = R_t.closure_cycle_after`, `closure_seal_version = R_t.closure_seal_version_at_abort`, `closure_barrier = false`, `closure_seal_pin_id IS NULL`, `closure_family_id IS NULL` and a `status` outside (`closing`, `closure_sealed`, `closed`). A history row inserted without an actual account transition cannot satisfy it.
- **S5 — one abort.** The rows of `X` share one `abort_target_id`, `abort_target_type`, `abort_target_from_status` and `reason_code`; exactly one row has `target_id = abort_target_id` and its `from_status` equals `abort_target_from_status`; for `checker_rejected_seal` / `closure_initiation_withdrawn`, `abort_target_from_status = 'closing'` (the §2.8 `CHECK`, restated across rows).
- **S6 — the family.** For a master abort, the `closure_family` row `P.closure_family_id` has `family_status = 'aborted'`, `abort_change_request_id = X` and `aborted_at_utc` set, in this transaction.

Together with the immediate checks (a)/(b) of `trg_acc1_status_transition` this makes **recovery row ⇔ actual status transition** hold in **both** directions: no direction needs the other table to hold at least one row first, an applied abort request with nothing behind it cannot commit (E3), and the bare-`UPDATE` family abort is refused at the statement (`trg_acc1_family_abort_guard`).

**Immediate vs. deferred, restated in one place (amended R7):** `trg_acc1_status_transition`, `trg_acc1_recovery_bind`, `trg_acc1_default_protected`, `trg_acc1_seal`, `trg_acc1_readiness_insert`, `trg_acc1_attestation_bind`, `trg_acc1_restriction_version_ins` / `_upd`, `trg_acc1_status_history_ins` / `_upd`, `trg_acc1_pin_readiness_window`, **`trg_acc1_change_request_status`, `trg_acc1_change_request_immutable`, `trg_acc1_family_abort_guard`, `trg_acc1_history_stamp`, `trg_acc1_pin_stamp`, and (R8) `trg_acc1_counter_guard` and `trg_acc1_seal_pin_bind`** are **immediate** (ordinary `BEFORE`/`AFTER` row triggers, evaluated at the statement that fires them, with every prerequisite row already present under the orders of §5.1/§5.2). `trg_acc1_recovery_scope` (E1), **`trg_acc1_history_abort_scope` (E2), `trg_acc1_abort_apply_complete` (E3)**, `trg_acc1_family_membership` (E4), **`trg_acc1_seal_pin_complete` (R8)**, **the three initiation-completeness entry points `trg_acc1_initiation_apply_complete` (I1), `trg_acc1_initiation_family_scope` (I2) and `trg_acc1_initiation_history_scope` (I3) (R9, §5.6.1)**, `trg_acc1_closure_family` and `trg_acc1_master_default_invariant` are **`DEFERRABLE INITIALLY DEFERRED` constraint triggers**, whose queued events fire **at `COMMIT` — or at an earlier `SET CONSTRAINTS … IMMEDIATE`; each is correct whenever it fires, may fire more than once per request and is read-only, so repetition is harmless (R8-F04.1; no trigger is "evaluated once at commit")** — deferral exists because only the finished transaction can prove the family consistent as a whole: the family is deliberately inconsistent mid-transaction (a member already updated, its sibling not yet). **(R9, R9-F03.3) One deferred check is NOT of that kind:** `trg_acc1_restriction_cancel_recheck` (the cancel-time recheck of R3-F07.2) is **clock-based** — it compares `effective_from_utc` with `clock_timestamp()` when its event fires — so it is **not** "correct whenever it fires": an early `SET CONSTRAINTS … IMMEDIATE` evaluates it at an earlier clock. The statement-time check in `trg_acc1_restriction_terminal` is authoritative; the deferred recheck is best-effort narrowing that can only refuse more, never admit what the statement-time check refused (§5 table). No ACC apply path issues `SET CONSTRAINTS`. No trigger not listed here needs a timing declaration beyond PostgreSQL's row-`CHECK` default (immediate, non-deferrable).

The four-member reconstruction of `04-review-r6.md` §9 (master `closing`, default `closure_sealed`, child A `closure_sealed`, child B `closing`) commits under this design: the request is applied (`applied_xact_id` stamped), the four recovery rows are inserted and stamped from the stored payload before any of the four accounts is updated; each account `UPDATE` (naming only `status`) then finds its own recovery row and the applied request (and `trg_acc1_counter_guard`, not the application, increments `version` and `closure_cycle` exactly once and clears barrier/pin/family); the family becomes `aborted` with the master's recovery row already present; at commit the abort-set proof finds `PAY = FAM = REC = HIS` and every pairwise fact equal, and the family/default invariants hold.

### 5.4 `trg_acc1_counter_guard` — the database owner of the protected columns (R8, R8-F01)

**Normative.** `trg_acc1_counter_guard` is the **one** database owner of the class-P columns of §2.2.1 on `master_account` and `subaccount`, and the one owner of `version` (R7-F02.3's single-owner rule is preserved and moved here from `trg_acc1_status_transition`). Exactly one `OLD.version + 1` expression exists in the schema, in this function.

**Definition.** `BEFORE INSERT OR UPDATE`, `FOR EACH ROW`, on both tables, with **no `OF <column>` list and no `WHEN` clause**: it runs on **every** `INSERT` and **every** `UPDATE`, including a statement that names no protected column, one that names only `status`, and `SET status = status`. (v0.8's owners were `BEFORE UPDATE OF status` triggers, which never ran for a statement that did not name `status` — the gap of R8-F01.) The function is owned by the owner role, is **not** `SECURITY DEFINER` (it runs as the invoker and needs no privilege of its own), and carries `SET search_path = pg_catalog, acc1, pg_temp` with every relation it reads schema-qualified (**(R9, R9-F01)** v0.9 said only "a fixed `search_path`" and gave no value; §1 rule 10, §5.7). It reads only `OLD`, `NEW.status`, the class-B columns of `NEW`, the transaction-local `acc1.cause_type`/`acc1.cause_ref` settings — treated as **claims, validated against database rows, never trusted** — and database rows (change requests, `closure_family`, `closure_family_member`, `closure_seal_pin`, `closure_recovery`, `account_status_history`). **It never reads a caller-written value of a class-P column as an input.**

**Rule 0 — no caller-written protected value.** On entry, for every class-P column `c`: if `NEW.c IS DISTINCT FROM OLD.c` on `UPDATE` (or, on `INSERT`, `NEW.c` is not the column's initial value of the rule below), **the statement wrote it** — no other trigger assigns a class-P column — and the guard raises `ACC1_COUNTER_OWNERSHIP_VIOLATION`. For `role_acc1_runtime` Layer 1 normally refuses earlier (`42501`, a column it cannot name); Rule 0 is Layer 2, and it binds **every** role including the owner (§2.2.1). The guard then **computes** every class-P `NEW.c` from the rules below, so any later assignment by it is the only value that can reach the row. Because the statement can neither name nor persist a protected value, no trigger, `CHECK` or deferred proof in this pack ever compares a protected column with a value the caller could have chosen.

**Classification (computed once).** `status_changed := (NEW.status IS DISTINCT FROM OLD.status)`. The transition kind `T` is `INSERT`; or, when `status_changed`: **`CLOSING_ENTRY`** (operational → `closing`), **`SEAL`** (`closing → closure_sealed`), **`ABORT`** (`closing`/`closure_sealed` → operational), **`COMPLETE`** (`closure_sealed → closed`), **`OPERATIONAL`** (operational → operational); any other `(OLD.status, NEW.status)` pair is not drawn in file 06 §1 and raises `ACC1_STATUS_TRANSITION_INVALID`; or, when not `status_changed`, **`NONE`**.

**Status named but unchanged (R8, R8-F01.4 — defined once).** `UPDATE … SET status = status` — any statement whose `NEW.status = OLD.status` — is **not** a status transition. The presence of the `status` column in the SQL text is not sufficient: transition logic depends on `OLD.status IS DISTINCT FROM NEW.status`, and the guard, `trg_acc1_status_transition`, `trg_acc1_seal`, `trg_acc1_default_protected` and `trg_acc1_status_history` each carry that test. Such a statement does not increment `closure_cycle`, does not touch the seal version, the pin or the family pointer, writes no `account_status_history` row, needs no cause setting and performs no closure-transition semantics. Its version behaviour is rule A: no synthetic bump merely because `status` was named; one bump if a class-B column genuinely changes in the same statement.

**The rules (A–H).**

- **A — `version`.** `version_relevant := status_changed OR (a class-B column IS DISTINCT FROM OLD) OR restriction_touch`. If `version_relevant`: `NEW.version := OLD.version + 1` — **exactly one increment per row mutation**, never two, whatever combination of the three is present in the one statement; otherwise `NEW.version := OLD.version` (no synthetic bump: not for a named-but-unchanged `status`, not for a statement that changes nothing). On `INSERT`, `NEW.version := 1`. A **restriction touch** is the one version event that is not a column change: it is an `UPDATE` issued by `trg_acc1_restriction_version` in its `SECURITY DEFINER` **owner context** (`current_user` equals the table's owner, `pg_class.relowner` — a context `role_acc1_runtime` can neither assume nor impersonate, because it is not a member of the owner role, §1 rule 8) that changes **only** `updated_at_utc`; an owner-context statement that changes anything else is processed by the ordinary rules. The caller can never supply, and no statement can lower, `version`. The application's profile `PATCH` and every status `UPDATE` name no `version`; they may add `WHERE version = <expected>` as an optimistic **read** predicate.
- **B — `closure_cycle`.** Changes **only** on the two owning transitions — `CLOSING_ENTRY` and `ABORT` — each `NEW.closure_cycle := OLD.closure_cycle + 1`; in every other statement `NEW.closure_cycle := OLD.closure_cycle`. It can never decrement, rewind or be caller-selected. `INSERT`: `0`.
- **C — `closure_seal_version`.** Monotonic, never decremented, never caller-selected. Changes **only** on `SEAL`: `NEW.closure_seal_version := OLD.closure_seal_version + 1`, which must equal the verified pin's `closure_seal_version` (§5.5). Retained by `ABORT`. `INSERT`: `0`.
- **D — `closure_sealed_at_version`, `closure_sealed_at_utc`.** Assigned **only** by `SEAL`: `closure_sealed_at_version := OLD.version + 1` (= the `NEW.version` of rule A; equal to the pin's stamped value, else `ACC1_SEAL_PIN_INVALID`) and `closure_sealed_at_utc := clock_timestamp()`. No direct rewrite; retained, not cleared, by `ABORT`. `INSERT`: NULL.
- **E — `close_change_request_id`.** May be established or replaced **only** by the closure-initiation lifecycle — `CLOSING_ENTRY` — and then only to the initiation `R` that the guard has verified. **Verification (all required):** the session cause is `closure_initiation` with `cause_ref = R`; `R` is an `account_change_request` with `status = 'applied' AND applied_xact_id = pg_current_xact_id()`, `approval_mode = 'maker_only'`; **and** one of — (i) *independent subaccount:* `R.change_type = 'close_subaccount'`, `R.target_subaccount_id` = this row; (ii) *master:* `R.change_type = 'close_master_account'`, `R.target_master_account_id` = this master, and a `closure_family` row `closure_family_id = R` (`open`, this master) exists; (iii) *family member (the default or a master-directed child):* the same `R` and `closure_family` of this row's master, and a `closure_family_member (R, this id)` with membership `default` or `master_directed_child` exists. **And** (iv) the live pairing: `R` has never before been the cause of a `closure_initiation` history row for this target (a live-state fact, independent of `xid8`, §5.0). Then `close_change_request_id := R` — for a family member this is the master's initiation under which it entered `closing` (the natural reading of §2.1; no design change). In every other statement `NEW.close_change_request_id := OLD.close_change_request_id`. An **old** initiation can never be restored by a raw `UPDATE` (Layers 1 and 2) and can never be accepted on the legitimate path (it is not applied in this transaction, and it has already been a cause for this target). `INSERT`: NULL. An `ABORT` retains it as the last initiation; it is evidence for `closing`/`closure_sealed`/`closed` rows only (every consumer reads it only with the closure statuses).
- **F — `closure_seal_pin_id`, `closure_family_id`.** Each may be **set, cleared or re-pointed only by its own owning lifecycle**: set at `CLOSING_ENTRY` (`closure_family_id := R` for cases (ii)/(iii) of rule E, NULL for (i)) and at `SEAL` (`closure_seal_pin_id := the one pin` with `target_id` = this row, `closure_seal_version = OLD.closure_seal_version + 1`, `created_xact_id = pg_current_xact_id()` and `seal_change_request_id` = the seal request in `cause_ref`; zero or several ⇒ `ACC1_SEAL_PIN_INVALID`); **cleared** only at `ABORT`; retained by `COMPLETE`. A **non-null → different non-null** re-point is unrepresentable (the legitimate paths only ever move NULL → value → NULL), and a raw one fails by Rule 0. **The abort branch** (identical to — and the same shared predicate as — `trg_acc1_status_transition` (1)(a)(b), preserved verbatim from v0.8's `trg_acc1_closure_barrier`) clears `closure_barrier`, `closure_seal_pin_id` and `closure_family_id` only when the session cause is `closure_abort` with `cause_ref = X`, `X` is an `abort_closure` request `applied` with `applied_xact_id = pg_current_xact_id()`, and **exactly one `closure_recovery` row** with `target_id` = THIS row, `change_request_id = X`, `created_xact_id = pg_current_xact_id()` already exists; otherwise `ACC1_CLOSURE_RECOVERY_INTEGRITY`; **and (R9, R9-F02) the request named by `OLD.close_change_request_id` was not applied in this transaction** (`applied_xact_id <> pg_current_xact_id()`; else `ACC1_CLOSURE_ABORT_INVALID`) — the same predicate as `trg_acc1_status_transition` (1)(c): an initiation is never aborted in the transaction that applied it.
- **G — `closure_barrier`.** Structurally tied to the status transition: `NEW.closure_barrier := (NEW.status IN ('closure_sealed','closed'))`, computed by the guard. It becomes `true` only with `SEAL` (the only way into `closure_sealed`) and `false` only with `ABORT` (rule F's recovery binding); there is no direct or arbitrary toggle, and `CHECK (closure_barrier = (status IN ('closure_sealed','closed')))` is the backstop. `INSERT`: `false`.
- **H — `closed_at_utc`.** Assigned **only** by `COMPLETE`, `closed_at_utc := clock_timestamp()` (the cause `closure_complete` / `closure_family_complete` is validated by `trg_acc1_status_transition`); never otherwise. `INSERT`: NULL.
- **`updated_at_utc` (class M)** `:= clock_timestamp()` whenever the row actually changes (including a restriction touch); it carries no security meaning (§2.2.1).

**`INSERT`.** The guard fixes the initial protected values listed above (`version = 1`, `closure_cycle = 0`, `closure_seal_version = 0`, every pointer and timestamp NULL, `closure_barrier = false`) and requires `NEW.status` to be the creation status of file 06 §1.1 (`active`), so a row can never be *created* in a closure state, with a chosen counter or with a pointer — the privilege layer's `INSERT` column list (§6) already excludes them.

|---|---|---|---|---|---|---|---|---|
| `INSERT` (creation) | `:= 1` | `0` | `0` / NULL | NULL | NULL | NULL | `false` | NULL |
| `CLOSING_ENTRY` | `+1` | `+1` | unchanged | `:= R` | `:= R` (family) or NULL | NULL | `false` | NULL |

| `ABORT` | `+1` | `+1` | unchanged (retained) | unchanged (retained) | `:= NULL` | `:= NULL` | `false` | NULL |

**Firing order is immaterial.** PostgreSQL fires `BEFORE` row triggers in name order, but the guard computes every protected `NEW` value from `OLD`, `NEW.status`, the validated cause and database rows, and the other `BEFORE` triggers on these tables (`trg_acc1_status_transition`, `trg_acc1_seal`, `trg_acc1_default_protected`, the immutables) read `OLD`, `NEW.status`, the pin, the recovery rows and the history — **never a class-P `NEW` value** — and **none assigns a class-P column** (source-guard test: the guard is the only function that assigns them, T-370). So no ordering of these triggers changes any outcome.

**The R8-F01 attacks, each refused.** (1) *Rewind `version`* (stale approval cured, RF-08 evidence rewound): `UPDATE … SET version = 10` → `42501`; as owner → `ACC1_COUNTER_OWNERSHIP_VIOLATION`; a status/profile statement ends at `OLD.version + 1`, never lower. With a stored approval at `approved_version = 10` and a restriction having moved the live row to `11`, no statement can restore `10`; the abort's `trg_acc1_recovery_bind` (6) still sees `11` and raises `ACC1_CLOSURE_APPROVAL_STALE` (T-363). (2) *Decrement `closure_seal_version`* / (3) *rewind `closure_cycle` or `close_change_request_id`*: refused by Layers 1 and 2; an old attestation at seal version 1 can never again be "at the current seal version" (T-364), and aborted-cycle readiness can never become "latest for the current cycle" at the database level. (4) *Re-point `closure_seal_pin_id`* between non-null pins, or *set / re-point `closure_family_id`* outside entry into `closing`: refused (rule F).

### 5.5 `trg_acc1_seal_pin_bind` and `trg_acc1_seal_pin_complete` — a seal pin is legal only inside its seal (R8, R8-F02)

v0.8 protected abort rows strongly but left the `closure_seal_pin` `INSERT` unguarded: an orphan pin (a seal `UPDATE` failing inside a swallowed `SAVEPOINT`, or a raw `INSERT`) could commit without its seal and then occupy `UNIQUE (target_id, closure_seal_version)` permanently, and the pin's approval facts were caller-written, compared only with the live row. v0.9 applies the abort's standard to the pin: stored payload as the authority (§2.4.3), one stamping model (§2.9.1), a bind trigger at `INSERT` and a deferred completeness proof.

**`trg_acc1_seal_pin_bind` — immediate, `BEFORE INSERT` on `closure_seal_pin`.** For each `NEW`, in order; any failure ⇒ `ACC1_SEAL_PIN_INVALID` unless stated:

1. Identify `NEW.seal_change_request_id` and load that request `FOR SHARE`.
2. Require `change_type = 'seal_closure'`.
3. Require `status = 'applied'`.
4. Require `applied_xact_id = pg_current_xact_id()` — the normative seal order (§5.2 step 4) applies the request in the same transaction, so a request applied earlier, in another transaction, or only `requested`, can never ground a pin (paired with the live bindings below, §5.0).
5. Parse the stored payload (§2.4.3): a missing, null or ill-typed field, a `target_id` that differs from the request's own immutable target column, or `NEW.target_id` ≠ the payload's `target_id` is invalid; require `NEW.seal_pin_id = request.result_ref` (the pre-allocated id).
6. **Lock and read the actual target** (master row first for a subaccount, the §7 rule 5h order) and require `status = 'closing'` **and** `closure_seal_pin_id IS NULL`.
7. Require the proposed `NEW.closure_seal_version = target.closure_seal_version + 1` (a future, past or repeated seal version is refused).
8. **Stamp, overwriting whatever the caller supplied (caller values are discarded, never compared)** — from the **stored payload**: `target_version_approved := approved_version`, `closure_sealed_at_version := approved_version + 1`, `closure_cycle`, `closure_change_request_id`, `closure_family_id`, `family_set_hash`, `required_attester_set_hash`, `pinned_required_attester_count := jsonb_array_length(required_attesters)`; from the **request row**: `seal_payload_hash := payload_hash`, `approval_id`, `approver_user_id`, `approval_policy_id`; from the **live row**: `target_type`.
9. **Compare the stamped payload facts with the live locked target; any difference ⇒ `ACC1_CLOSURE_APPROVAL_STALE`:** `approved_version = live version`; `closure_cycle = live closure_cycle`; `closure_change_request_id = live close_change_request_id`; `closure_family_id` equals (null-safe) the live `closure_family_id`; `payload.target_type` = the live row's table; for a master, `family_set_hash` is non-null (its equality with the recomputed set hash is verified by `trg_acc1_seal`), otherwise NULL; `pinned_required_attester_count >= 1`.

A stale seal request therefore **cannot be cured by the caller writing current values into the pin** (its values were discarded in step 8 and the payload's values are what is compared in step 9); a raw `INSERT` with no applied seal request, for a future seal version, for another target, cycle, initiation or family, or in a transaction that did not apply the request, is refused at the statement (T-371…T-377, T-382). `trg_acc1_pin_stamp` (`created_xact_id`) is unchanged.

**`trg_acc1_seal_pin_complete` — deferred, `DEFERRABLE INITIALLY DEFERRED` constraint trigger, `AFTER INSERT ON closure_seal_pin`, `FOR EACH ROW`.** For **every** pin created in the transaction it requires, whenever the event fires (§5.3 timing — normally at `COMMIT`; a premature firing before the seal `UPDATE` can only refuse):

- the target row exists with `status = 'closure_sealed'`, `closure_seal_pin_id = this pin's seal_pin_id`, `closure_seal_version = this pin's closure_seal_version`, `closure_cycle` = the pin's, `closure_sealed_at_version` = the pin's, `closure_barrier = true`, `close_change_request_id` = the pin's `closure_change_request_id`, and `closure_family_id` equal (null-safe) to the pin's;
- the **expected same-transaction status-history transition exists**: exactly one `account_status_history` row for this target with `from_status = 'closing'`, `to_status = 'closure_sealed'`, `cause_type = 'closure_seal'`, **`cause_ref = this pin's seal_change_request_id`**, `created_xact_id = pg_current_xact_id()`, `version_before = target_version_approved` and `version_after = closure_sealed_at_version` — i.e. the status history is bound to the same seal request/cause;
- the seal request is still `seal_closure`, `applied` and `applied_xact_id = pg_current_xact_id()`;
- **the exact approved pin-readiness set exists**: the number of `closure_seal_pin_readiness` rows of this pin equals `pinned_required_attester_count` (≥ 1) and, element by element, the rows equal the stored payload's `required_attesters` (identity and `readiness_id`), with the pin's `required_attester_set_hash` equal to the payload's (string equality);
- **the pin/readiness transaction binding remains valid**: the pin's `created_xact_id = pg_current_xact_id()`, and every pin-readiness row's parent pin is a pin of this transaction (`trg_acc1_pin_readiness_window` made a later insert impossible; this re-proves the set is complete and unaltered at proof time).

Failure ⇒ `ACC1_SEAL_PIN_ORPHAN`; the transaction cannot commit. So *pin `INSERT` → failed seal `UPDATE` → `SAVEPOINT` rolled back only for the `UPDATE` → `COMMIT`* cannot leave an orphan pin: the deferred proof refuses at `COMMIT`.

**Savepoint behaviour, precisely (R8, R8-F02.5; T-378, T-379).**

- *Pin and readiness created **after** the `SAVEPOINT`:* `SAVEPOINT s; INSERT pin; INSERT readiness; <seal UPDATE fails>; ROLLBACK TO s` — the pin and its readiness rows roll back with the subtransaction, and so do their queued deferred events; the target is unchanged, no pin exists, and the transaction may continue or commit with no orphan.
- *Pin created **before** the `SAVEPOINT`, seal `UPDATE` after it, only the `UPDATE` rolled back (an application error):* `INSERT pin; SAVEPOINT s; <seal UPDATE fails>; ROLLBACK TO s; COMMIT` — the pin survives and its queued event survives; at `COMMIT` the deferred proof finds the target still `closing` and **refuses**, so the transaction does not commit and no pin is left behind.
- A pin readiness row added after a *committed* seal is refused at `INSERT` by `trg_acc1_pin_readiness_window` (unchanged; T-381).

**Unique slot (R8-F02.6).** `UNIQUE (target_id, closure_seal_version)` remains valid and `UNIQUE (seal_change_request_id)` is added. The safety requirement is met because **only a pin attached to an actual committed seal can survive a commit**: an orphan pin cannot commit, so it can never be a permanent blocker of a target's next seal (T-384).

### 5.6 Normative closure-initiation statement order (R8, R8-F03; completeness proof added R9, R9-F02)

The abort (§5.1) and seal (§5.2) orders are normative; the initiation order is the third and is stated once here (file 02 §7.1 item 3 points to it). **Initiation is maker-only (ACC-R3-HD-02, unchanged): no checker, no approval token.** The final seal still has its checker.

```txt
CLOSURE INITIATION (independent subaccount, or master + default + every operational child) — one transaction
 0. (Before the local transaction, per A3 discipline.) Permission check; the attested maker-initiation decision
    from IAM-02 (DCR-ACC-IAM-07/-06): entitlement_evidence_ref and actor_assertion_authority. Pre-allocate the
    initiation request id and the Critical audit reference A (§2.4.2).
 1. BEGIN. Lock in the §7 rule 5h order: master FOR UPDATE then every non-closed child in ascending internal
    id (master initiation), or the master FOR SHARE then the subaccount (independent). Re-derive the family
    set; a difference => ACC1_CLOSURE_FAMILY_SET_CHANGED, nothing changes.
 2. INSERT the account_change_request: change_type close_*, approval_mode 'maker_only', status 'requested',
    EVERY apply-owned field NULL, requested_by = the authenticated actor, payload, payload_hash,
    expires_at_utc, idempotency_key. (trg_acc1_change_request_status INSERT rule; the maker-only evidence CHECK
    is scoped to 'applied', §2.4, so this row is valid.)
 3. The maker entitlement / actor-binding verification of step 0 has completed successfully. It must precede
    step 4; the INSERT of step 2 needs none of its results.
 4. UPDATE the request requested -> applied in this SAME transaction, in ONE statement that writes every
    apply-owned field: entitlement_evidence_ref, actor_assertion_authority, sec_audit_ref = A, result_ref
    (§2.4.2). approval_id / approver_user_id / approval_policy_id stay NULL (no checker).
    trg_acc1_change_request_status stamps applied_xact_id and applied_at_utc; the maker-only CHECK now holds.
 5. Master initiation only: INSERT the closure_family row (family id = this request id, status 'open') and one
    immutable closure_family_member row per participant. (R9) trg_acc1_family_member_window (immediate) refuses a
    member row once the master has left the operational statuses, so the snapshot is complete BEFORE step 6.
 6. SET LOCAL acc1.cause_type = 'closure_initiation' / cause_ref = <this request id> / sec_audit_ref = A / actor,
    then ONE UPDATE per participant (master first, then members in ascending internal id) that names ONLY
    status = 'closing'. trg_acc1_counter_guard (§5.4 rules A, B, E, F) verifies the applied request of this
    transaction and assigns close_change_request_id, closure_family_id, closure_cycle + 1 and version + 1.
 7. Write the Critical audit acc1.account_closure_initiated and the outbox record using reference A
    (audit failure => the whole transaction rolls back, request included).
 8. COMMIT. Deferred: the initiation-completeness proof via its three entry points (R9, §5.6.1) — an applied
    initiation with no initiation effect cannot commit — and trg_acc1_closure_family,
    trg_acc1_master_default_invariant, trg_acc1_family_membership. (They normally fire here; correctness does not
    depend on that, §5.3, §5.6.1.)
```

The request is **never** `INSERT`ed `applied`. After step 8 the target(s) are `closing` under that applied request; the maker cannot seal them — the `seal_closure` request remains maker-checker with its own final checker (ACC-REQ-044; T-393).

### 5.6.1 The initiation-completeness proof — one deferred procedure, three entry points (R9, R9-F02)

**Why.** The abort has a completeness proof (E1–E4, §5.3) and the seal has one (`trg_acc1_seal_pin_complete`, §5.5); v0.9's initiation had none. v0.9 deliberately treats savepoint-swallowing helpers as legitimate (§5.0, §5.5, T-378/T-379), so a helper that rolled back to a savepoint around step 6 (the closing `UPDATE`s) and then committed left an `applied` maker-only request — and, for a master, an `open` `closure_family` with its immutable member snapshot — with **no account in `closing`**: inert, but dangling, never completable, never abortable, and a replay of the same idempotency key would find an `applied` request whose effect never happened. **04-review-r9 option (a) is adopted: a dangling applied initiation is not tolerated.** A maker-only `close_master_account` / `close_subaccount` request that reaches `requested → applied` **cannot commit** unless its initiation effect exists.

**Entry points** — all `DEFERRABLE INITIALLY DEFERRED` constraint triggers (§5 table), all running ONE read-only procedure `acc1.fn_acc1_initiation_proof(X)` (illustrative name; §5.7 applies to it): **(I1) `trg_acc1_initiation_apply_complete`** — the request moves `requested → applied` (`X = NEW.change_request_id`); **(I2) `trg_acc1_initiation_family_scope`** — a `closure_family` `INSERT` (`X = NEW.closure_family_id`); **(I3) `trg_acc1_initiation_history_scope`** — an `account_status_history` `INSERT` with `cause_type = 'closure_initiation'` (`X = NEW.cause_ref`). **No direction needs the other table to hold a row first:** I1 fires with no family or history row; I2 and I3 fire when no request was applied. The runtime role holds `INSERT` on `closure_family` and `account_status_history` (§6), so I2 and I3 are the only refusals for a family or history row that did not come from a real initiation.

**The proof for `X`** (`R` = the `account_change_request` with `change_request_id = X`; the *initiated targets* `T` = the one target of an independent initiation, or the master, the default and every master-directed member of a master initiation). Any failed requirement ⇒ `ACC1_CLOSURE_INITIATION_INCOMPLETE`:

- **I-1 — the request.** `R` exists; `change_type IN ('close_master_account','close_subaccount')`; `approval_mode = 'maker_only'`; `status = 'applied'`; `applied_xact_id = pg_current_xact_id()` (§5.0 — correlation only, paired with the live bindings below); the maker-only evidence `CHECK` of §2.4 holds; `result_ref` is the initiated target (the subaccount id, or the master id). `T` is non-empty.
- **I-2 — the target(s) really entered `closing` under THIS request.** For every `t` in `T` the live row has `status IN ('closing','closure_sealed','closed')` (`closing`, or a valid later state *under this initiation*), **`close_change_request_id = X`**, and `closure_family_id = X` for a master or a family member (NULL for an independent subaccount). The target is the one `R` names (`target_subaccount_id` / `target_master_account_id`).
- **I-3 — authoritative history for THIS cause.** For every `t` in `T`: **exactly one** `account_status_history` row with `target_id = t`, `cause_type = 'closure_initiation'`, **`cause_ref = X`**, an operational `from_status`, `to_status = 'closing'` and `created_xact_id = pg_current_xact_id()`; **version coherence:** `version_after = version_before + 1`, and the live `version >= version_after` (a later same-transaction restriction touch may only raise it).
- **I-4 — the family (master initiation only).** A `closure_family` row exists with **`closure_family_id = X`** (the family id **is** the initiation request id), `master_account_id` = `R.target_master_account_id`, the same `client_id`, and `family_status IN ('open','completed')` (never `aborted`). The master is bound to it (`closure_family_id = X`, I-2). An **immutable member snapshot** exists: exactly one `master` and one `default` member, all rows carrying `closure_family_id = X`.
- **I-5 — every master-directed member actually entered, under this exact family (master initiation only).** Let `SNAP` = the `target_id`s of the family's members with membership `master`, `default` or `master_directed_child`; `HIS` = the `target_id`s of the I-3 history rows for `X`; `LIVE` = the master and subaccounts of the master whose live row has `closure_family_id = X` **and** `close_change_request_id = X` and a status in I-2's set. **`SNAP = HIS = LIVE`**, each element exactly once. And **every non-`closed` subaccount of the master is in the snapshot** (any membership), so a child cannot be omitted from the snapshot and left behind.
- **I-6 — `independent_preserved` members keep their approved semantics (master initiation only; ACC-R3-HD-01, ACC-R4-HD-01).** For every member with membership `independent_preserved`: the live row has `closure_family_id IS NULL`, `close_change_request_id = independent_initiation_id` (its **own** initiation, never `X`), and it is **not** in `HIS`. It is never turned into a master-directed member, and it is required to be in none of `SNAP`/`HIS`/`LIVE`.

**Why every asserted fact stays true once the proof has passed (so an early firing cannot be undone later).** The proof is read-only and correct whenever it fires (§5.3), and **each fact it asserts is either unchangeable for the rest of the transaction, or its change is refused immediately, or its change queues a fresh event**:

| Asserted fact | Why it cannot silently regress after an early pass |
|---|---|
| `R` applied (I-1) | Terminal: `trg_acc1_change_request_status` refuses every later write, even of the same value (§2.4.2); `trg_acc1_change_request_immutable` freezes the rest |
| History rows (I-3) | Append-only (`trg_acc1_append_only`). They can disappear only with the subtransaction that wrote them — and **rolling that subtransaction back re-queues this proof's event** (below) |
| `close_change_request_id`, `closure_family_id` (I-2, I-5) | Class-P columns (§2.2.1): Layer 1 + Layer 2 refuse any raw write; the owning transitions only move them on a `CLOSING_ENTRY` (needs a prior exit from `closing`) or `ABORT` |
| Status leaving `closing` / `closure_sealed` / `closed` (I-2) | Only an `ABORT` leaves that set, and **an initiation cannot be aborted in the transaction that applied it** — refused immediately by `trg_acc1_status_transition` (1)(c) and the guard's abort branch (rule F). Forward progress (`closing → closure_sealed → closed`) stays inside the asserted set |
| Family `open → aborted` (I-4) | Its own `UPDATE` queues the abort-set proof (E4), whose live-row assertion S4 cannot hold for a target still `closing`; the family cannot commit `aborted` |
| Snapshot rows (I-4, I-5) | Append-only, **and** `trg_acc1_family_member_window` (immediate) refuses a member row once the master has left the operational statuses, so none can be added after the closing `UPDATE`s |
| Children of the master (I-5) | `trg_acc1_sa_owner` refuses a new subaccount under a master that is not `active`/`restricted` |
| `version` coherence (I-3) | Monotone: only the guard writes it, only upward |

**Cases the proof is specified and tested to survive (T-412…T-423; the mechanics were verified on PostgreSQL 17.10).**

| Sequence | Outcome |
|---|---|
| `INSERT`; `UPDATE` applied; closing `UPDATE`s; `COMMIT` | Commits (normal) |
| `UPDATE` applied; **no** closing `UPDATE`; `COMMIT` | **Refused** at `COMMIT` (I1). Nothing persists; the request stays `requested` |
| `UPDATE` applied; `SAVEPOINT s`; closing `UPDATE`s; `ROLLBACK TO s`; `COMMIT` | **Refused** at `COMMIT`: the event was queued by the apply `UPDATE`, which precedes `s`; the satisfying facts are gone |
| `SAVEPOINT s`; `UPDATE` applied; …; `ROLLBACK TO s`; `COMMIT` | Commits with **no** initiation, no request applied and no event: the apply was undone with `s` and its queued event was discarded with it. The request is `requested` again |
| `UPDATE` applied; `SAVEPOINT s`; closing `UPDATE`s; `SET CONSTRAINTS … IMMEDIATE` (**passes inside `s`**); `ROLLBACK TO s`; `COMMIT` | **Refused** at `COMMIT`. PostgreSQL un-marks an event that *fired* inside a subtransaction that is then rolled back, so it fires again at `COMMIT` and finds the target not in `closing` — **an early pass that is undone by a rollback is re-queued** |
| `UPDATE` applied; `SET CONSTRAINTS … IMMEDIATE` **before** the closing `UPDATE`s | Refused **at the `SET`** (fail closed; a premature firing can only refuse) |
| complete initiation; `SET CONSTRAINTS … IMMEDIATE` (passes); then an `ABORT` of the same target | **Refused immediately** by (1)(c) / rule F — otherwise PostgreSQL would not re-fire the event and an applied initiation over an operational target would commit (reproduced on PostgreSQL 17.10 with the refusal disabled; this is why the refusal exists) |
| a closing `UPDATE` fails inside `SAVEPOINT s`, `ROLLBACK TO s`, the application retries it, `COMMIT` | Commits (the facts exist at proof time) |
| raw `INSERT` of a `closure_family` / `closure_initiation` history row with no applied request (or citing a request applied in an **earlier** transaction) | **Refused** at `COMMIT` (I2 / I3; I-1 `applied_xact_id`) |

**Replay and double application.** The request is terminal once applied, so it cannot be applied twice; an idempotent replay of the same key finds an `applied` request **whose effect is guaranteed to exist**, because the proof refused every commit in which it did not. A request applied in an earlier transaction can never be the cause of a new initiation history row or closing entry (I-1 `applied_xact_id`; rule E (iv); T-420). The initiation proof is **independent** of the abort and seal proofs: each is tested with the others disabled by the test-only owner (T-423).

### 5.7 Function and name-resolution hardening — one rule for every ACC-01 function (R9, R9-F01)

**Threat model** (the one the pack adopts, 10 §22/§23 preambles): raw `role_acc1_runtime` writes with application validation bypassed. PostgreSQL resolves an unqualified relation name by searching the session's temporary schema `pg_temp_N` **first**, unless `pg_temp` is listed explicitly in `search_path`. The runtime role may create a temporary table named like an `acc1` table (it may hold `TEMPORARY`, §1 rule 8) and may `GRANT` access on it, because it owns it. A function that names an `acc1` relation unqualified, under a path that omits `pg_temp`, would then read forged rows (every evidence read in §5) or write to the shadow (the restriction touch, the history insert). Reproduced on PostgreSQL 17.10 against v0.9's specification (04-review-r9 §19: version 4 → 4; a forged temporary `closure_recovery` row accepted by the guard's abort branch) and again for this pack (shadow bypass with the v0.9 form; no bypass with a pinned path alone, nor with qualification alone, nor with both).

**Normative rule — no exception.**

1. **N1 — pinned search path, on every function.** Every function and procedure the ACC-01 migration creates — every `trg_acc1_*` trigger function (every trigger named in §5, including each of a split pair), the `SECURITY DEFINER` restriction function, and every helper or proof procedure called by them (`acc1.fn_acc1_abort_set_proof`, `acc1.fn_acc1_initiation_proof`, the shared abort-branch predicate) — is created with the function attribute **`SET search_path = pg_catalog, acc1, pg_temp`**: exactly these three elements, in this order, **`pg_temp` explicit and LAST**, and nothing else (no `public`, no `"$user"`). The set is stored in `pg_proc.proconfig`, so it is catalogue-checkable. Whether a function is `SECURITY DEFINER` or not makes no difference: v0.9 pinned only the definer function and gave no value for the others.
2. **N2 — schema-qualified relations, on every function.** Every `acc1` relation a function reads, writes, locks or declares a row variable for is written **`acc1.<name>`** — in `FROM`, `JOIN`, `INSERT INTO`, `UPDATE`, `DELETE`, `SELECT … FOR SHARE/UPDATE`, `LOCK TABLE`, `%ROWTYPE` and every subquery. The only unqualified identifiers a function body may use are `NEW`, `OLD`, the `TG_*` variables, its own variables and parameters, the columns of the relation being referenced, and `pg_catalog` built-ins. A temporary table of the same name also creates a composite type of that name, so a row variable is declared `acc1.<name>%ROWTYPE`, never by an unqualified type name.
3. **N3 — both, not either.** A function that is pinned but unqualified, or qualified but unpinned, **does not conform**. Each control is sufficient against a shadow table on its own (verified on PostgreSQL 17.10); both are required so that a later edit that drops one still leaves the other (04-review-r9 R9-F01, correction 1).
4. **N4 — calls and dynamic SQL.** Every call to an ACC helper is `acc1.`-qualified. Built-in functions and operators resolve through `pg_catalog`, which is first on the path, and PostgreSQL never searches `pg_temp` for function or operator names — but no ACC function relies on that: it calls no user-defined function or operator unqualified. **No dynamic SQL** (`EXECUTE`) in any ACC-01 function, so no name is assembled at run time (source guard, T-402).
5. **N5 — `SECURITY DEFINER` specifically.** `trg_acc1_restriction_version()` is the only definer function. It is owned by the migration's owner role (never `role_acc1_runtime`, §1 rule 8), carries N1, writes only `acc1.master_account` / `acc1.subaccount` (N2), has `EXECUTE` revoked from `PUBLIC` and not granted to the runtime role, and `acc1` has no schema `CREATE` for the runtime role, so it cannot plant a same-named function. The path never contains `public`.
6. **N6 — temporary relations are attacker-controlled but irrelevant.** ACC-01 does **not** depend on revoking `TEMPORARY` from `PUBLIC` or from `role_acc1_runtime`, and does not require the platform to. Correctness must hold with the privilege granted (the default) — and also with it revoked: the tests run both (T-408).
7. **N7 — row `CHECK`s and defaults.** They run under the caller's path. Every `CHECK` and column default in ACC-01 uses only the row's own columns and `pg_catalog` built-ins (`gen_random_uuid()`, `clock_timestamp()`, `pg_current_xact_id()`); none calls a function that resolves a relation name (source guard, T-402).
8. **N8 — the session cannot override it.** A function's `SET search_path` attribute applies for the duration of each call and replaces whatever the runtime role set for its session. The transaction-local `acc1.cause_type` / `acc1.cause_ref` / `acc1.actor` / `acc1.sec_audit_ref` settings are **claims validated against database rows**, never trusted (§5.4); they are not a name-resolution input.

**Test method (T-401…T-411).** The raw-DB shadow tests have one fixed shape: *in a FRESH database session, before the first execution of the trigger under test*, `role_acc1_runtime` creates temporary tables named after **every** relation the inventory lists, `GRANT`s them to `PUBLIC`, and fills them with forged evidence; it then runs the attack. The shadows must exist **before** the first execution because PL/pgSQL caches its plans per session: in a session where a trigger already ran, a later shadow is not picked up, and a test that creates its shadows late would pass **vacuously** (observed by `04-review-r9.md` §19 on PostgreSQL 17.10). Every test asserts the outcome on the **authoritative `acc1.*` rows**, and runs once with `TEMPORARY` granted and once revoked (T-408).

## 7. Data rules

1. Ownership immutable from creation (blueprint §9).
2. Status changes only through legal transitions; each one writes history with a cause in the same transaction.
3. A subaccount can only be created under a master whose own status permits it; its owner is derived, never supplied.
4. Restriction rows are never deleted; a lift is a state change with evidence.
5. `version` increments **exactly once** for every version-relevant mutation of `master_account` / `subaccount` — a status transition, a profile edit, **and every restriction change against it** — and not at all for a statement that changes nothing; consumers store it (with `applied_restriction_ids`) as decision evidence. **(R8, R8-F01)** The increment is made by `trg_acc1_counter_guard` **alone** on every one of these (rule 5r); no application SQL and no other trigger writes `version`.
5a. Stored restriction lifecycle state is housekeeping; resolution **and the legality of lift/cancel** are evaluated **by time** (file 06 §3).
5c. **(R2)** `closure_barrier` is an independent stored fact; it is never derived at read from `effective_status`, and `resolve` returns it beside the closure/seal versions (file 04 §3.1).
5d. **(R2)** Closure evidence is keyed to `closure_cycle` (readiness) and `closure_seal_version` (attestation); only the latest row per target + attester + key counts; abort bumps `closure_cycle`, never resets `closure_seal_version`.
5e. **(R3)** From the seal on, the reference for completion and attestation is the immutable **seal pin**, never "the latest readiness"; a readiness row cannot be inserted once the target has left `closing`.
5f. **(R3)** A `closed` default under a non-`closed` master is unrepresentable (`trg_acc1_master_default_invariant`); a master-directed subaccount reaches `closed` only inside its master's completion transaction.
5g. **(R3, R3-F07.2)** Every time-effective evaluation (restriction in force, lift/cancel legality, projection recompute at abort) uses the **database `clock_timestamp()`** evaluated in the statement or locked check — never the application clock, never `now()` (transaction start).
5h. **(R3)** Lock order for every operation touching a master or its children: master row first (`FOR SHARE` for child-level work, `FOR UPDATE` for master/family work), then children in ascending internal id.
5i. **(R4, R4-F01)** The required attester set for completion is the seal's own `closure_seal_pin_readiness` row set, fixed at that seal — never "currently configured attesters". Re-attestation after any seal is expected, is read fresh at completion, and never changes `family_set_hash`, which binds only immutable seal facts (never an attestation id).
5j. **(R4, R4-F02)** `closure_family_member` rows are scoped to exactly one `closure_family_id` and are never read as live membership by a later family; each new master initiation takes a fresh, current snapshot (§2.10).
5k. **(R4, ACC-R4-HD-01; rescoped R5, ACC-R5-HD-01, R5-F01)** `checker_rejected_seal` and `closure_initiation_withdrawn` are legal governed-abort grounds only while the **abort target** is `closing` — never once the target has reached `closure_sealed` (enforced by the target-scoped `CHECK` on `closure_recovery.abort_target_from_status`, §2.8, and by `trg_acc1_recovery_scope`). For a master-family abort the target is the master; returned default and master-directed members may be `closing` or `closure_sealed`, and a sealed member's barrier is cleared only inside that governed family transaction. (v0.5 applied the condition to every returned row; that reading is withdrawn.)
5l. **(R5, R5-F03)** Every `abort_closure` binds, and apply re-checks under lock, the target's current `version` — for a master abort, each returned member's target id, `version`, `closure_cycle`, `closure_seal_version` and family role; `closure_recovery.target_version_approved` records it — **(R7) stamped from the stored payload, not caller-supplied (§2.8, rule 5q)**. `checker_rejected_seal` rows carry the IAM-02-attested `rejection_approval_request_id` and `rejection_decision_id` (`CHECK`), so none can be written while `DEP-IAM-SEAL-REJECTION-EVIDENCE` is hard-unsatisfied.
5m. **(R5, R5-F04)** A pinned attester is identified by `attester_module` **plus** `authenticated_service_identity`, `attester_contract_id` and `attester_contract_version`, recorded identically on the readiness row, the pin row and every counting attestation row; a seal pin always has `pinned_required_attester_count >= 1` equal to its pin-readiness row count and to the checker-approved attester list.
5n. **(R6, R6-F01; rewritten R7, R7-F01)** `closure_recovery` is a record of what the database itself observed and read, never of what a caller asserted. Its pre-transition facts (`from_status`, `closure_cycle_before/after`, `closure_seal_version_at_abort`, `abort_target_from_status`, `barrier_cleared`) are **stamped from the locked account rows**; its approval facts (`abort_target_type`, `abort_target_id`, `reason_code`, `evidence_*`, `rejection_*`, `closure_family_id`, `family_role`, `target_version_approved`) are **stamped from the immutable stored payload** of the applied `abort_closure` request and then compared with the live rows (`trg_acc1_recovery_bind`); `created_xact_id` is stamped from `pg_current_xact_id()`. The recovery rows, the same-transaction `account_status_history` rows and the stored payload are proven equal at commit (four-way for a master family) by the abort-set proof (§5.3), from four entry points, none of which needs another table to have a row first; and every exit from `closing`/`closure_sealed` under `closure_abort` is refused **at the `UPDATE`** unless this target's own recovery row already exists (`trg_acc1_status_transition`). "Applied in this transaction" is `applied_xact_id = pg_current_xact_id()` (rule 5p).
5o. **(R6, R6-F03(d); rewritten R7, R7-F01(b))** `closure_seal_pin_readiness` — the immutable pinned required-attester set — may be inserted only in the same top-level transaction as its parent `closure_seal_pin` (`closure_seal_pin.created_xact_id = pg_current_xact_id()`) and only while the target is still in the legal sealing state (`trg_acc1_pin_readiness_window`); no row may be appended after that transaction commits. Ordinary post-seal `closure_attestation` rows remain appendable at any time (§2.7) and are not affected.
5p. **(R7, R7-F01(b))** **Transaction identity has one meaning:** `pg_current_xact_id()` (`xid8`, top-level, savepoint-stable), stamped by the database into `account_change_request.applied_xact_id`, `closure_recovery.created_xact_id`, `account_status_history.created_xact_id` and `closure_seal_pin.created_xact_id`; `xmin` is never used and never compared with an `xid8` (§5.0). `account_change_request` has a status guard: only `requested → applied | cancelled | expired`, everything else terminal, no re-stamp (§2.4.2).
5q. **(R7, R7-F01(c))** **The stored approved payload is the authority.** The `abort_closure` payload is immutable from `INSERT` (`trg_acc1_change_request_immutable`), has the exact shape of §2.4.1, and is the only source of the approved version, cycle, seal version, family id, role, member set, reason and evidence; the recovery writer cannot alter any of them. `abort_target_type`/`abort_target_id` are **stamped** (one model, everywhere).
5r. **(R7, R7-F02.3; refined R8, R8-F01.5)** **One version owner on every version-relevant mutation:** `trg_acc1_counter_guard` (`NEW.version := OLD.version + 1`, the single `OLD.version + 1` in the schema). `trg_acc1_status_transition` no longer assigns anything. The application never sets `version` in any `UPDATE` (status, profile or restriction path); the restriction path bumps it through the guard's *restriction touch* (§5). `account_status_history.version_before/after` are `OLD.version`/`NEW.version`; the recovery bijection uses them. A statement that names `status` without changing it is not a transition and bumps nothing by itself (§5.4).
5s. **(R8, R8-F01)** **Protected columns have one database owner.** `version`, `close_change_request_id`, `closure_family_id`, `closure_seal_pin_id`, `closure_barrier`, `closure_cycle`, `closure_sealed_at_utc`, `closure_seal_version`, `closure_sealed_at_version` and `closed_at_utc` (the protected set, §2.2.1) are assigned **only** by `trg_acc1_counter_guard`, on every `INSERT`/`UPDATE`, and `role_acc1_runtime` holds no column privilege on them — **two layers, neither relied on alone** (§1 rule 9). `closure_cycle`, `closure_seal_version` and `version` never decrease; the cycle and seal version change only on their owning transitions; no old initiation, pin or family pointer can be restored or re-pointed by a raw `UPDATE` (§5.4).
5t. **(R8, R8-F02)** **A seal pin is legal only inside its own seal.** `trg_acc1_seal_pin_bind` (immediate) requires an applied `seal_closure` request of this transaction for this target, a `closing` target with no pin and `closure_seal_version = current + 1`, and stamps every approval-owned pin column from the stored seal payload (§2.4.3, §2.9.1); `trg_acc1_seal_pin_complete` (deferred) refuses a commit that leaves a pin which is not the committed seal pin of a `closure_sealed` target. No orphan pin can occupy `UNIQUE (target_id, closure_seal_version)`.
5u. **(R8, R8-F03)** **Maker-only initiation is `INSERT requested → UPDATE applied` in one transaction** (§5.6); the maker-only evidence `CHECK`s are scoped to `status = 'applied'`; a direct `INSERT` with `status = 'applied'` is refused. ACC-R3-HD-02 is unchanged — no checker at initiation.
5v. **(R8, R8-F04.3)** `role_acc1_runtime` is a grantee, never an owner of any `acc1` object, and holds no way to disable a trigger or set `session_replication_role` (§1 rule 8; P1 acceptance criterion).
5w. **(R8, R8-F04.2)** `applied_xact_id` and `created_xact_id` are **current-transaction correlation only**, never a permanent or global transaction identity; every same-transaction check is paired with live bindings (§5.0).
5x. **(R8, R8-F04.4)** Every apply-owned field of a request — `sec_audit_ref` and `result_ref` included — is written in the single `requested → applied` `UPDATE`; references to later-written objects are pre-allocated (§2.4.2). **(R8, R8-F04.6)** `updated_at_utc` carries no security meaning anywhere.
5y. **(R8, R8-F04.1)** Deferred constraint-trigger proofs are read-only and correct **whenever** they fire (at `COMMIT` or earlier under `SET CONSTRAINTS … IMMEDIATE`); they may fire more than once; none is "evaluated once at commit" (§5.3).
5z. **(R9, R9-F01)** **Every ACC-01 function pins and qualifies its name resolution.** Each function — every `trg_acc1_*` trigger function, the `SECURITY DEFINER` restriction function and every helper or proof procedure — carries `SET search_path = pg_catalog, acc1, pg_temp` (`pg_temp` explicit and **last**) **and** names every `acc1` relation schema-qualified; both, not either (§1 rule 10, §5.7). Temporary relations are attacker-controlled but irrelevant: no ACC-01 property depends on revoking `TEMPORARY`. The shadow tests create their shadow tables in a fresh session before the trigger's first execution (T-401…T-411).
5aa. **(R9, R9-F02)** **An applied maker-only initiation always has its initiation effect.** `trg_acc1_initiation_apply_complete` (I1), `trg_acc1_initiation_family_scope` (I2) and `trg_acc1_initiation_history_scope` (I3) run one read-only proof (§5.6.1) that refuses a commit in which a `close_master_account` / `close_subaccount` request is `applied` without its target(s) in `closing` under that request, its same-transaction `closure_initiation` history and — for a master — its `closure_family`, immutable member snapshot and master-directed members; `independent_preserved` members are never turned master-directed. It is correct under `COMMIT`, `SET CONSTRAINTS … IMMEDIATE`, `SAVEPOINT` and `ROLLBACK TO SAVEPOINT`, because a later change of any proven fact is refused immediately or re-queues the event, and an initiation is never aborted in the transaction that applied it.
5b. Retention: **no hard deletion of any row**; the platform/client-record retention policy applies once formally defined (DCR-ACC-GOV-06); ACC-01 defines no retention period.
6. Direct DB edits of status/owner **and of every protected column (rule 5s)** are prohibited by grants **and** triggers; break-glass DB access is outside this module and logged per platform rules. Disabling a trigger (`ALTER TABLE … DISABLE TRIGGER`, `session_replication_role`) is an owner/superuser action that the runtime role cannot perform (§1 rule 8).
