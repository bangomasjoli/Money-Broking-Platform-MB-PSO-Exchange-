## 2. Human decisions requested

Each has a **recommendation** (adopted as the working default in this pack) and the consequence of declining. Until decided, the default applies and always errs toward denial.

| ID | Decision | Recommendation (working default) | If declined |
|---|---|---|---|
| **HD-1** | **Fiat currencies in the registry.** Doc 00 §12A's three outcomes describe *digital assets*; a fiat currency is not one | Register fiat as `instrument_form = FIAT` reference records; AST-01 derives `INELIGIBLE` for all six products; settlement/payout currency handling stays with `PAY-01`/`LED-01`. (`LED-RULE-005` rule 2 needs fiat precision, so fiat must be *registered*.) | Alternative: a master-level outcome `NOT_APPLICABLE_FIAT` (DCR-AST1-008) — cleaner but a master change; or force fiat through the gate (awkward). Until decided fiat is never eligible for a product, which fail-closes |
| **HD-2** | **`product_admission` is a conjunct, not an independent eligibility flag** (01 §5.6). It records Compliance review, can exist only while the matrix says `PERMITS`, binds to the classification record, and can only narrow | Approve this reading. It satisfies `AST-SRS-002` req 1 and `ASSET-RULE-001` rule 7 without creating a flag that can contradict classification | If declined, drop `product_admission`: `PERMITS` becomes `ELIGIBLE` directly, which violates "may be considered … subject to every other requirement" and removes the compliance review step |
| **HD-3** | **`synthetic_emulates`** on synthetic instruments (which real outcome the test instrument behaves as) | Approve — it is the only way to test end-to-end that a security-like instrument can never reach Spot, and Spot flows against a non-security-like one | Synthetic derives class-permitted only for RWA/secondary/Exchange, never Spot/OTC/Pay; loses negative testing of the hard rule end-to-end (unit and DB tests remain) |
| **HD-4** | **Presumptively securities-featured classes** (`SECURITY`, `SECURITY_TOKEN`, `TOKENISED_DEBT`, `TOKENISED_FUND`) cannot be given `NON_SECURITY`. Changing class requires a *new* instrument | Approve — fail-closed; mis-declared class is corrected by retire-and-recreate | Classifier could mark a tokenised fund non-security on the strength of one record; more flexible, materially less safe |
| **HD-5** | **Pay eligibility for security outcomes** | Deny — no master authorises a securities-featured instrument as a payment instrument (`PAY-SRS-009` restricts to "instruments eligible for Pay in AST-01") | Would need an explicit master statement before AST-01 could permit it |
| **HD-6** | **Who may place a hold**, single actor | `COMPLIANCE_OFFICER`, `MLRO`, `INSTRUMENT_CLASSIFIER`, plus `system` (DCR-AST1-006) | If none approved, holds are M+C only, losing the immediate fail-closed lever (`SYS-RULE-008` precedent argues for single actor) |
| **HD-7** | **Meaning of `RWA` eligibility** = "instrument is an object of the RWA lifecycle". A stablecoin used as the *payment currency* for an RWA subscription is a Pay/ledger-currency question | Approve | If `RWA` eligibility must also cover payment instruments, define it in the RWA blueprints; AST-01 would gain a "payment instrument for RWA" subject |
| **HD-8** | **Elevated approval** for `SECURITY → NON_SECURITY`: Compliance Officer **and** MLRO, with a fresh evidence bundle | Approve — the most dangerous loosening (a real determination is being reversed) | Single checker as any other change |
| **HD-9** | **Classification granularity: per instrument, not per asset** (01 §3.1) | Approve — wrapped/bridged variants are different contracts; evidence may be shared by reference, approval may not | Per-asset classification is less work but lets a variant inherit an approval it never earned |
| **HD-10** | **Decision token TTL 60 s** and **every** evaluate writes a log row (allow and deny) | Approve — pre-trade evidence (DEC-012 cl. 1 rule 7); volume handled by partitioning at implementation | Sampling allow-decisions would break reconstructability of admissions |
