## 4. The design, item by item

**R8-F01 — database ownership of the version / closure counters.** *Root cause (confirmed against `04-review-r8.md` §7, §19 P7):* the owner triggers fired only `BEFORE UPDATE OF status` while `role_acc1_runtime` held the column `UPDATE` privilege on the counters, so a statement that did not name `status` bypassed every owner. *Fix — both layers, neither relied on alone:*

1. **One protected set** (05 §2.2.1): `version`, `close_change_request_id`, `closure_family_id`, `closure_seal_pin_id`, `closure_barrier`, `closure_cycle`, `closure_sealed_at_utc`, `closure_seal_version`, `closure_sealed_at_version`, `closed_at_utc`. Every column of both tables was reviewed and placed in exactly one class (I identity, B business/profile, S status, P protected, M DB-maintained `updated_at_utc`); no other counter or pointer exists.
2. **Layer 1 — privilege.** `role_acc1_runtime` has no `INSERT` and no `UPDATE` column privilege on class P or M; it may `UPDATE` only class B and name `status` **only as the governed transition path** (the existing design: `trg_acc1_status_transition` decides legality and cause). **The distinction is stated explicitly:** PostgreSQL checks column privileges against the statement's named columns, so a `BEFORE` trigger may assign `NEW.<protected>` even though the caller cannot name it; the runtime role is a grantee, not the owner.
3. **Layer 2 — `trg_acc1_counter_guard`** (immediate, `BEFORE INSERT OR UPDATE`, no `OF`, no `WHEN` — every statement). Rule 0 refuses (`ACC1_COUNTER_OWNERSHIP_VIOLATION`) any statement, from any role, that wrote a protected value; the guard then computes every protected value. Rules A–H are the review's A–G plus `closed_at_utc`: **A** version (exactly one increment per version-relevant mutation; none for a no-op); **B** `closure_cycle` only on closing entry and abort, `+1`; **C** `closure_seal_version` only on seal, `+1`, monotonic; **D** `closure_sealed_at_version`/`_utc` only on seal; **E** `close_change_request_id` only on closing entry, to a request the guard verified (applied in this transaction, `maker_only`, right target/family, and never before used as a cause for this target — a live-state fact independent of `xid8`); **F** pin/family pointers set, cleared or re-pointed only by their owning lifecycle (a non-null → different non-null re-point is unrepresentable); **G** `closure_barrier` computed from `status`; **H** `closed_at_utc` only on completion. The abort branch preserves v0.8's target-/cause-/transaction-bound recovery-row check verbatim (v0.8's `trg_acc1_closure_barrier`, folded in).
4. **`SET status = status` is not a transition** (defined once, 05 §5.4): transition logic depends on `OLD.status IS DISTINCT FROM NEW.status`; no cycle, seal, pin, family or history effect; no synthetic version bump; one bump if a class-B column genuinely changes in the same statement.
5. **Version owner (R8-F01.5).** The R7-F02 single-owner rule is **preserved and moved**: `trg_acc1_counter_guard` is the one owner; `trg_acc1_status_transition` no longer contains `OLD.version + 1` (exactly one such expression remains in the schema). No double increment: history `version_after = version_before + 1`.
6. **Restriction version (R8-F01.6).** `trg_acc1_restriction_version` is `SECURITY DEFINER` (owner ≠ runtime) and *touches* the target row; the guard recognises the owner-context, `updated_at_utc`-only statement as the restriction touch and performs the one increment. No application SQL sets `version = version + 1`; all workflows (02 A4/§5/§7.4/§7.6/§7.7/§9), the prompt (11) and tests were aligned. A restriction after approval makes any old closure approval stale and no raw statement can rewind `version` to cure it (T-363).
7. **Tests:** T-357…T-370 cover every R8-F01 case of the instruction (version/seal-version/cycle rewinds, initiation re-point, pin re-point, family raw set/re-point, the stale-approval raw-rewind end to end, the old-attestation seal-version case, `status` named but unchanged, one-increment-per-transition, each layer alone, schema guard, restriction path, source guard).

**R8-F02 — a seal pin is legal only inside its seal.** *Stored payload* (05 §2.4.3): `target_type`, `target_id`, `approved_version`, `closure_cycle`, `closure_change_request_id`, `closure_family_id`, `required_attesters[]` (the strong identity list plus pinned readiness identifiers), `required_attester_set_hash`, `family_set_hash` — existing ACC vocabulary, immutable from `INSERT`. *`trg_acc1_seal_pin_bind`* (immediate `BEFORE INSERT`, 05 §5.5): loads the stored request; requires `change_type = seal_closure`, `status = applied`, `applied_xact_id = pg_current_xact_id()` (the §5.2 order applies the request in the same transaction; paired with live bindings); locks the target and requires `closing` and `closure_seal_pin_id IS NULL`; requires the proposed `closure_seal_version = current + 1`; **stamps** every approval-owned pin column from the stored payload (and the request row and the live row), then compares payload with live — a stale seal cannot be cured by the caller writing current values into the pin. *Ownership* (05 §2.9.1), one class per column: caller-named and verified (`seal_pin_id` = the request's pre-allocated `result_ref`, `target_id`, `closure_seal_version`, `seal_change_request_id`, the apply-verified watermark/as-of); stamped from the payload; stamped from the request row; stamped from the live row (`target_type`); DB-generated. The runtime `INSERT` privilege is column-level (six columns). *`trg_acc1_seal_pin_complete`* (deferred): for every pin created in the transaction, the target is `closure_sealed` on this pin/version/cycle with the matching same-transaction `closing → closure_sealed` history row bound to the same seal request, and the exact approved pin-readiness set exists with the transaction binding intact — so *pin `INSERT` → failed seal `UPDATE` → `SAVEPOINT` rolled back only for the `UPDATE` → `COMMIT`* is refused at commit. *Savepoints* are specified for both structures (pin after the savepoint rolls back with it; pin before the savepoint is refused at commit). `UNIQUE (target_id, closure_seal_version)` stays; `UNIQUE (seal_change_request_id)` is added; only a pin attached to a committed seal can occupy the slot. Tests T-371…T-385.

**R8-F03 — maker-only initiation matches the request state machine.** `INSERT requested` (apply-owned fields NULL) → maker entitlement/actor-binding verification → `UPDATE requested → applied` in the same transaction (the guard stamps `applied_xact_id`/`applied_at_utc`; the one `UPDATE` writes the evidence, the pre-allocated `sec_audit_ref` and `result_ref`) → the account enters `closing` under that applied request (05 §5.6, enforced by guard rule E). The maker-only `NOT NULL`s became an `applied`-scoped conditional `CHECK` (05 §2.4); no checker-only field is required; all text saying maker-only initiation is `INSERT`ed `applied` was removed (02 §7.1 item 3 rewritten; 05 §2.4 and §2.4.2 aligned). ACC-R3-HD-02 unchanged; the final seal keeps its checker. Tests T-386…T-393.

**R8-F04 — precision.** (1) Deferred-proof timing corrected everywhere: events are queued per row/event, fire at `COMMIT` or earlier under `SET CONSTRAINTS … IMMEDIATE`, the proof is read-only and correct whenever it fires, repetition is harmless, and every later mutation of a proven fact queues a fresh event or is refused immediately — the counter exception closed by R8-F01; the apply paths issue no `SET CONSTRAINTS`, and correctness does not depend on that. (2) `applied_xact_id`/`created_xact_id` are current-transaction correlation only, never global identity; no decision relies on `xid8` uniqueness; every same-transaction check is paired with live bindings (05 §5.0, §5.4 rule E(iv), §5.5). (3) `role_acc1_runtime` is a grantee, never an owner — normative (05 §1 rule 8), a **P1 acceptance criterion** (T-396); T-092's wording corrected. (4) Every apply-owned request field, `sec_audit_ref` and `result_ref` included, is written in the single `requested → applied` `UPDATE`; references to later-written objects (audit, seal pin, created ids) are pre-allocated and the later write uses them (05 §2.4.2, §5.1/§5.2/§5.6). (5) `id` added to the immutable request columns. (6) `updated_at_utc` is DB-maintained and meaning-free. Tests T-394…T-399.
