## 10. Request-time contract (C-14) — resolved from accepted code where possible
Derived from the 24 IAM-02 redemption call sites (rev-2 re-read of the argument lists) and the consumers' payload functions. **The code is the authority; this section is a map.** A mismatch fails safe because the token binds action, resource, entity, client and payload hash (`decision-token.ts:230-235`).

### 10.1 Binding rules (apply to every pair)
1. `action` = the exact registered permission code the consumer redeems (a constant, or derived: `cfg1.feature.enable|disable` from `to_state`, `cfg1.licence_profile.activate|suspend|revoke` from `to_status`, `clt1.client_profile.suspend|reactivate|close`, `aml1.match.confirm|dismiss`).
2. `resource` = the consumer's literal; it equals `iam2.permission.resource` for the 32 pairs (E-5; rev-1 and Opus reported, rev-2 not re-run for all 32; the focused Opus verification reports re-checking all 32 against a freshly migrated database — *Opus reported*, not re-run by Sonnet in rev 3).
3. `entity_id` = the consumer's literal entity (table below). Token matching is exact; a null token value matches only a null presented value.
4. `client_id`: **CLT-01, KYC-01, AML-01 and CFG-01 present no `clientId`**, so the IAM-02 approval **must be created without `client_id`** (bound null). WLT-01 presents `body.client_id`; SEC-01 presents `preview.client_id` only when the alert carries one.
5. Maker = the actor the token is bound to: CLT-01/KYC-01/AML-01/CFG-01 present the **stored** `requested_by`; WLT-01 and SEC-01 present `body.actor_id`. Under C-2 B this maker must hold the redeemed permission at request **and** execution.
6. `payload` = the exact object the consumer's function builds; the operator supplies it to IAM-02's create endpoint, which hashes it with `fingerprint()` (`fnd-fp-v1`) and must equal the consumer's `currentPayloadHash`. An approval with no payload mints no token.

### 10.3 WLT-01 maker/checker execution-role implications (P4)
- **Verified:** WLT-01's `approve/request` route only evaluates an advisory baseline and writes a local audit event; it creates **no IAM-02 approval and stores no requester**. The `approve/apply` route (and evidence-export apply) passes `body.actor_id` to execute-verify, and the token is bound to the **IAM-02 maker** (`approvals.ts:391`, `issueDecisionToken({ actorUserId: approval.maker_user_id })`). Migration `056` describes `approve_apply` as "the checker's actual whitelist-approval execution … the sole real gate" and `approve_request` as "the maker's baseline-eligibility preflight".
- **Consequence under C-2 B and Q1:** the person who calls WLT-01 *apply* is the IAM-02 **maker**. They must (i) hold `wlt1.destination.approve_apply` (resp. `wlt1.evidence_export.apply`) at **request** and **execution**, and (ii) hold `iam2.approval.create`. A **different** person is the IAM-02 approver, holding `iam2.approval.approve` and any snapshot checker role, with a bound step-up. WLT-01's "checker" is thus a *WLT-layer role that is the IAM-02 maker*, not the IAM-02 checker; role design (OD-4) must not assume otherwise. Holding only `approve_request` is not sufficient.
- **UNVERIFIED (V-7):** whether WLT-01 intends any constraint between the preflight actor and the apply actor; none is checked in the code read.
- **Gating change:** these two WLT-01 routes run **no** baseline today (E-5), so central enforcement (AZ-02) is their only maker-entitlement gate.
