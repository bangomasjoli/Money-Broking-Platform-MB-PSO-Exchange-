# WLT-01 — Wallet Screening / Payout-Destination Whitelist — Implementation Notes

## 0. Module selection

**WLT-01 was selected as the next runtime module** immediately after CLT-01/KYC-01 Phase 4A.2B
reached acceptance and D1 (authorised-party-roster-completeness) closed. Reasoning (full analysis
in the accepted "AIX Platform — Next Approved Module Selection" roadmap review):

- The authoritative build order (`02_Build_Order_And_Dependency_Map.md`,
  `11_Go_Live_Implementation_Roadmap.md`) places WLT-01 immediately after AML-01 and immediately
  before LED-01: `WLT-01 → LED-01 → DEP-01 → WDR-01 → TRD-01 → E2E-01 → REC-01 → INC-01 → PRT-01`.
  This corrects an earlier assumed ledger-first ordering — **WLT-01 is not a sub-ledger**. Its own
  blueprint §2: *"WLT-01 does not custody assets, hold keys, post ledger entries, or execute
  transfers. It only provides destination eligibility and whitelist status."*
- Every upstream dependency (FND-01, IAM-01, IAM-02, SEC-01, CFG-01, CLT-01, KYC-01, AML-01) has an
  accepted implementation baseline with the seams WLT-01 needs. AML-01's pause after Phase 3D does
  not block WLT-01 — WLT-01 consumes AML-01 via a receive-side seam
  (`POST /internal/wlt1/aml-revocations`, Phase 5), the same receipt-only pattern that let CLT-01
  and KYC-01 proceed while AML-01 was still mid-build.
- WLT-01 is the **sole remaining blocker on the entire money tier**: LED-01 v1.1 §5.8 requires
  *"LED-01 must consume WLT-01 execution-time destination decision, not only trust a prior token"*
  and *"fail closed if WLT-01 unavailable."* LED-01, DEP-01, WDR-01 and TRD-01 all sit behind it.
- WLT-01 v1.2 is the controlling blueprint. The v1.1→v1.2 delta is documentation-only — direct
  file-by-file diff confirmed 12 of 16 files byte-identical; the four that differ
  (`01_Module_Blueprint.md`, `11_Claude_Prompt.md`, `14_Go_Live_Checklist.md`, `README.md`) change
  only the Document Control version cell, a "Final Verification Note" restating what v1.1 already
  resolved, and Go-Live gate status wording. No route, table, state-machine, permission, error,
  audit-event, test-case, or integration-contract changed. v1.2 is the clean cosmetic rollup the
  accepted `WLT-01_..._v1.1_Review.md` itself requested (§4 Verdict: *"Recommend: accept WLT-01 at
  v1.1 (a clean v1.2 rollup can fix the version-cell nit)"*). No additional blueprint review was
  required before Phase 0/1 planning.

### 2.4 Shared helper architecture

`tests/helpers/module-import-boundary.ts` — a plain helper module, zero `describe`/`it`/hooks, no
database/environment/global side effects. Uses `ts.createSourceFile` + structural AST traversal
(`ts.forEachChild`) rather than regex matching, so comments and unrelated string literals are
structurally invisible to the walk — this is what eliminates both proven false-positive classes,
not a pattern patch.

**AST forms inspected:** `ImportDeclaration` (static, `import type`, side-effect), `ExportDeclaration`
(`export {} from`, `export type {} from`, `export * from`), `ImportEqualsDeclaration`
(`import x = require(...)`), dynamic `import(...)`, `require(...)`, `require.resolve(...)`.

**Dynamic-specifier policy (fail closed):** a `StringLiteral` or `NoSubstitutionTemplateLiteral`
argument is treated as static and resolved normally. Any other shape — interpolated template,
identifier, call expression — is `unresolvable_dynamic_specifier`, never silently skipped.

**Sibling-relative detection:** the specifier is resolved to an absolute path against the
*importing file's own directory* (not string-matched against the raw specifier text), backslashes
normalized to `/` first (Windows-separator specifiers detected identically on any host OS), then
checked by exact path **segment** equality against `services/<other>` — never substring matching,
so `notservices/clt1`/`services2/clt1` cannot false-positive.

**Package-alias detection:** the alias→package-name map is derived from each sibling's own
`services/<other>/package.json` `name` field (read once, relative to the helper's own fixed
location, independent of whatever `serviceSourceDir` a caller passes), with a documented
`@aix/service-<other>` fallback only when a package.json can't be read. Real names confirmed:
`@aix/service-fnd`, `@aix/service-iam`, `@aix/service-iam2`, `@aix/service-sec1`,
`@aix/service-cfg1`, `@aix/service-clt1`, `@aix/service-kyc1`, `@aix/service-aml1`,
`@aix/service-wlt1` — **not** `@aix/service-fnd1`/`@aix/service-iam1`. Both the exact alias and
any subpath beneath it are rejected.

**Foundation exception:** bare `@aix/foundation` permitted. Allowed subpaths are read from
`packages/foundation/package.json`'s own `exports` map (currently `{"."}` only), not hard-coded.
Any subpath or relative traversal into `packages/foundation/src/...` is `foundation_internal_import`.

**Violation contract:** `{file, line, column, kind, specifier, targetModule?}` — bounded, no source
contents, no secrets. `kind` ∈ `sibling_relative_import | sibling_package_alias |
foundation_internal_import | unresolvable_dynamic_specifier | malformed_module_specifier`. Sorted
deterministically by file → line → column → kind → specifier. 1-based line/column indexing.

### 7.1 Scope implemented

- **P2CA-MED-1 remediation (Gate 2C-B-1)**: `sourceAuthenticated`/`payloadHash` removed from
  `NormalizedScreeningResult` entirely — a provider adaptor has no honest way to assert whether its
  own caller was authenticated or to manufacture receipt-payload evidence for a call with no
  receipt. Both moved to a new application-owned `ScreeningEvidenceEnvelope` discriminated union:
  `synchronous_provider` (`{sourceKind, providerId, providerAdaptorVersion}`) persists
  `source_authenticated = NULL`/`payload_hash = NULL`; `provider_receipt` (adds `payloadHash`)
  persists `source_authenticated = TRUE`/`payload_hash = <caller value>`. The stub's fake
  `sha256:stub:*` placeholder is removed entirely. Provider result now carries screening facts
  only: `providerResultId`, `riskStatus`, `riskScore`, `riskCategories`, `directExposure`,
  `indirectExposure`, `sanctionsExposure`, `clusterRef`, `issuedAtUtc`, `validUntilUtc`.
- **Migration 051 — destination-lifecycle CHECK activation (Gate 2C-B-2)**:
  `infra/migrations/051_wlt1_screening_lifecycle.cjs` widens `wlt1.destination.status`'s CHECK from
  the Phase 1B two-state set (`draft`/`revoked`) to the accepted four-state Phase 2C set
  (`draft`/`pending_screening`/`pending_review`/`revoked`) under an explicit stable constraint name
  (`chk_wlt1_destination_status`, replacing PostgreSQL's auto-named `destination_status_check`).
  Baseline verified via a real `pg_constraint` query before touching anything (fails the whole
  migration closed on an unexpected schema). Also widens `status` from `varchar(16)` to
  `varchar(32)` — discovered empirically (not assumed): `'pending_screening'` is 17 characters, one
  over the Phase 1B column width. **Approved migration-051 schema compatibility correction**:
  migration 049 sized the column for the two Phase 1B values only; the widening is a necessary
  precondition of the approved four-state CHECK, not a scope extension. `down()` refuses (raises,
  whole migration rolls back) if any destination is currently `pending_screening`/`pending_review`
  — independently proven for both states separately — and restores the exact prior
  `destination_status_check`/`varchar(16)` only when safe. No new table, index, foreign key, or
  column.
- **`applyNormalizedScreeningResult` — the one-way result-application service (Gate 2C-B-3)**:
  `services/wlt1/src/lib/screening-application.ts`. Owns its own transaction (no caller-supplied
  connection); lock order is the `wlt1.destination:<id>` advisory lock, then `SELECT ... FOR UPDATE`
  on both the destination and target screening rows. Enforces P2B-LOW-1's one-way
  `pending → exactly one terminal state` gate application-side: rejects any screening row not
  currently `risk_status = 'pending'`, verifies it is still the current/latest version via
  `MAX(screening_result_version)`, and verifies the evidence envelope's `providerId`/
  `providerAdaptorVersion` against the pending row's own immutable binding (never self-asserted by
  the result). Computes effective validity as
  `min(providerValidUntil ?? +Infinity, issuedAtUtc + screeningMaxValidityHours)` — clipping a
  far-future provider expiry rather than rejecting it, rejecting an already-expired effective
  validity, and rejecting an `issuedAtUtc` more than 120 seconds in the future (fixed module
  constant, one authoritative `now` captured once per call). Publishes 1–3 audits inside the same
  transaction as the terminal update: `wlt1.wallet_screening_completed` always;
  `wlt1.wallet_high_risk_detected` when `riskStatus === "high_risk"`;
  `wlt1.wallet_sanctions_exposure` when `sanctionsExposure === true`. A publish failure rolls back
  the whole transaction (screening row remains `pending`, destination remains
  `pending_screening`, zero audits committed).

## 10. Phase 2C-C3 — ACCEPTED implementation baseline after independent Opus final
review — durable same-row/version `pending_screening` resume, 30-second `updated_at_utc`
CAS retry claim, C2 stranded-pending dead-end removed

### 10.1 Scope implemented

Reuses the existing accepted route — `POST
/internal/wlt1/wallet-destinations/:destination_id/screen` — as BOTH the C2 draft-path
initiation entry point (unchanged) AND the new C3 `pending_screening` resume entry
point. No `/retry` route added; a second route would split one idempotency contract
across two endpoints and the caller cannot know server-side lifecycle state in advance.

The lifecycle branch on `destination.status` was widened from a binary
`draft`-else-reject check to a three-way branch: `draft` → unchanged C2 initiation;
`pending_screening` → new C3 resume; `pending_review`/`revoked` → unchanged
`WLT1_DESTINATION_INVALID_STATE` for a NEW key (a same-key replay of any state still
rehydrates first, before this branch is reached).

The C3 resume path reuses the SAME `screening_result_id`/`screening_result_version` —
no INSERT, no `MAX(version)+1` allocation, no `destination_status_version` increment, no
re-emitted `wlt1.wallet_screening_requested` audit. A durable 30-second
compare-and-set retry claim is taken against the pending row's own `updated_at_utc`:

```sql
UPDATE wlt1.wallet_screening_result
   SET updated_at_utc = now()
 WHERE screening_result_id = $1
   AND risk_status = 'pending'
   AND updated_at_utc <= now() - interval '30 seconds'
RETURNING screening_result_id
```

`rowCount = 1` → this request wins the claim and invokes the provider (transaction
depth 0, strictly after commit, identical to the C2 path). `rowCount = 0` → throttled:
`provider_attempt: "throttled"`, `reason_code: "retry_cooldown_active"` (a route-internal
bounded reason, deliberately kept OUT of `KNOWN_PROVIDER_REASON_CODES` — it names the
disposition of THIS request's own attempt to obtain the claim, never a provider
response), HTTP 202, no provider call, no state mutation other than the idempotency
completion. A throttled key's idempotency record still completes — it can never later
gain provider-call ownership; the caller must submit a NEW key after the cooldown.

**COOLDOWN STORAGE — architecture decision, not a schema change.** The retry-claim
timestamp is `wallet_screening_result.updated_at_utc` itself, already `NOT NULL DEFAULT
now()` at INSERT time and already covered by `role_wlt1_runtime`'s existing
column-scoped UPDATE grant — no migration 053, no new column. This is sound ONLY
because exactly two production code paths ever UPDATE this table today, and the other
(`screening-application.ts`) only ever transitions a row AWAY from `pending` — never
back into it — a fact enforced at compile time (`RISK_STATUSES` structurally excludes
`"pending"`) and guarded by a new committed source-scan test,
`tests/unit/wlt1-screening-pending-row-mutation-boundary.test.ts`, which fails loudly
the moment a future phase (most plausibly Phase 2C-D's receipt/inbox processing) adds
any other production UPDATE against this table — at which point a dedicated
`last_provider_attempt_at_utc` column (migration 053) becomes mandatory, not before.

**PROVIDER/ADAPTOR IDENTITY FREEZE (fail-closed, both new).** Before any claim or
provider call on resume: if the CURRENT `chain_coverage.provider_id` has drifted since
initiation from the pending row's own frozen `provider_id`, or if the resolved registry
adaptor's `adaptorVersion` has drifted from the pending row's own frozen
`provider_adaptor_version`, the resume fails closed to `WLT1_SERVICE_UNAVAILABLE` — no
provider call, no state mutation, thrown before any `completeIdempotent` so the whole
transaction rolls back. Recovering a drifted screening requires a future new-version
rescreen workflow, explicitly out of Phase 2C-C3 scope. Destination-data correlation
(pending row `chain`/`network`/`address_hash` vs. current `wallet_destination`) is also
checked and fails closed to an internal integrity error on divergence — a condition
unreachable through any ordinary runtime grant, since `wallet_destination` carries no
UPDATE grant.

No new migration, grant, audit event type, error code, or route. Time authority is
PostgreSQL `now()` exclusively — no `Date.now()`, no `TimeService`, no environment
variable, no CFG-01, no caller input; the 30-second cooldown is a fixed module constant.

## Phase 2C-D2 — first candidate: replay/tamper integrity, BLOCKED on receipt provenance

Phase 2C-D2 implemented the receipt replay/tamper model that remains
unchanged today: durable replay identity `(provider_id,
provider_result_id)`, immutable content identity `payload_hash`,
`INSERT ... ON CONFLICT (provider_id, provider_result_id) DO NOTHING
RETURNING` (never `DO UPDATE`, never an inbox overwrite), same-hash replay
classified an idempotent EXACT DUPLICATE, different-hash replay classified a
genuine CONFLICT → new error `WLT1_RECEIPT_CONFLICT` (409) and a new
security audit `wlt1.provider_receipt_conflict_detected` committed
transactionally BEFORE the 409 response is surfaced, audit-persistence
failure fails closed to `WLT1_AUDIT_REQUIRED` rather than a silently-dropped
conflict claim, and deterministic no-sleep concurrency proofs for both
identical/identical and identical/conflicting replay races. This same
candidate also attempted to close P2CB-MED-2 by removing the standalone
`mintAuthenticatedReceiptProvenance` factory: the brand and its constructor
were moved to be module-private inside `receipt-auth.ts`, and the only
exported operation became `authenticateProviderReceipt(secrets,
claimedProviderId, providedToken)` — a function that performs the real
`timingSafeEqual` comparison and returns an authenticated capability only on
success.

**Independent Opus review of this Phase 2C-D2 candidate → PHASE 2C-D2
ACCEPTANCE BLOCKED.** The D2 replay/tamper mechanics themselves (the SQL,
the exact/conflicting-duplicate semantics, the audit atomicity, the
concurrency proofs, the row-immutability proofs) were independently reviewed
and found sound — **and were explicitly never reopened by any later
review.** The block was entirely about receipt provenance: the review proved
empirically, via a compiled foreign production module, that
`authenticateProviderReceipt`'s exported signature accepted the credential
`secrets` map as an ORDINARY CALL ARGUMENT — any production module could
fabricate its own secrets object (with zero relationship to the real
`WLT1_PROVIDER_RECEIPT_SECRETS` configuration) and a matching fake token,
and the function would mint a real, brand-matching
`AuthenticatedReceiptProvenance` from it, indistinguishable from a
genuinely-authenticated value. This finding is **H-D2-1**. It left
**M-D1-1 OPEN** (the underlying provenance-forgery defect first raised
against D1 was not actually closed, merely relocated into a differently-
shaped API) and **P2CB-MED-2 criterion 5 FAILING** (provenance was still
freely forgeable through an ordinary production API, without the legitimate
configured receipt secret).

## Phase 2C-D2R — credential-authority remediation

A narrowly-scoped remediation task (Phase 2C-D2R) fixed H-D2-1 without
touching D2's replay/tamper engine. The unbound `authenticateProviderReceipt`
export was removed entirely. In its place: `receipt-auth.ts` now exports
`createWlt1ProviderReceiptAuthenticator(config: Wlt1Config)` — a BOUND
factory, called EXACTLY ONCE per app boot, in `server.ts`'s own `buildApp`,
from the SAME validated `Wlt1Config` instance (produced by `config.ts`'s
`loadWlt1Config`, never hand-assembled) that configures the rest of the
running application — mirroring `lib/screening-application.ts`'s own
already-accepted `createScreeningApplication(config)` composition pattern
(P2CC1-MED-1) exactly. The returned `Wlt1ProviderReceiptAuthenticator`
closes over `config.providerReceiptSecrets` in a private closure; its ONLY
method, `.authenticate(claimedProviderId, providedToken)`, takes NO secrets
argument at all — there is no call-site slot through which a caller can
substitute a different credential authority. `provider-receipt.ts` receives
only the already-bound authenticator instance via a new
`RegisterProviderReceiptRoutesDeps` dependency-injection parameter (mirroring
`registerScreeningRoutes`'s own `RegisterScreeningRoutesDeps.screeningApplication`
shape) and never itself imports `Wlt1Config`, `loadWlt1Config`, or the
factory. Misleading "UNFORGEABLE"/"requires a REAL credential match" wording
from the D1/D2-era comments and test titles was corrected (**M-D2-1**) to an
explicit "HONEST SCOPE" disclosure of exactly what the new binding does and
does not guarantee, and a reflective (arity/name-inventory-based, not
text-scan-based) source guard replaced the old name-based text scan that an
earlier probe had defeated via renaming/method-aliasing.

## Narrow Opus re-review — fake-`Wlt1Config` residual and the final threat-boundary decision

A second, narrow independent Opus re-review confirmed the originally
demonstrated attack (an arbitrary caller-supplied secrets map) was now
closed — reproducing Opus's own original attack shape against the new
architecture and confirming it fails. But the review did not stop there: it
adversarially asked whether a foreign production module could instead
construct a structurally-valid `Wlt1Config`-SHAPED object literal (since
`Wlt1Config` carries no nominal/private branding, and is an ordinary exported
TypeScript interface) and pass THAT to `createWlt1ProviderReceiptAuthenticator`.
**This compiled with zero casts and, at runtime, produced a value with the
IDENTICAL real brand symbol as genuinely-authenticated provenance —
deep-equal to it.** The review further tested whether nominal config
branding (the fix direction it had itself suggested) would have closed this,
and proved it would NOT: `loadWlt1Config` is itself exported and accepts a
caller-supplied env object, so an attacker can call the REAL loader with
their own fabricated env and receive a genuinely loader-produced config
carrying their own secrets, satisfying any conceivable brand. The review
then asked the more fundamental question — whether a code-injecting actor
even NEEDS receipt provenance at all — and found that `@aix/foundation`
exports `query`/`withTransaction` via `export * from "./db.js"`, already
freely imported throughout `services/wlt1/src`, so a module able to add
production source could simply `INSERT ... source_authenticated = true`
directly, bypassing the provenance brand entirely. **The receipt-provenance
brand can therefore never be the binding constraint against an adversary who
can add production source — no achievable API design closes that, which is
precisely why the D2R remediation's own fix direction did not (and could
not) fully close it either.**

**The final, ratified threat-boundary decision**: the receipt-provenance
control's accepted scope is to prevent forging authenticated provider-
receipt evidence THROUGH THE SUPPORTED RUNTIME INGRESS/API PATH (the real
HTTP route, using only the server-bound authenticator), and to prevent
UNTRUSTED REQUEST INPUT from choosing the credential authority,
`source_authenticated` value, or payload hash. It does NOT, and structurally
CANNOT, defend against an actor who can already inject and execute arbitrary
trusted WLT production source — that broader threat is governed by
repository/code-review/CI-CD/deployment/production-access controls, not by
this receipt-provenance type. Under that ratified boundary: **P2CB-MED-2 is
CLOSED (10/10 criteria pass — criterion 5, "provenance cannot be freely
forged through ordinary production API," is read as governing the ordinary
external/runtime attack surface an untrusted caller can reach, not a
hypothetical actor who has already achieved arbitrary trusted code
execution inside the service's own source tree). H-D2-1 CLOSED. M-D1-1
CLOSED. M-D2-1 CLOSED.**

The theoretical residual is tracked, deliberately, as an OPEN non-blocking
finding rather than erased: **M-D2R-1** — `createWlt1ProviderReceiptAuthenticator
(config)` accepts the structural `Wlt1Config` object supplied at application
composition; a malicious production module capable of constructing its own
`Wlt1Config` and executing trusted source could construct its own
authenticator. Accepted disposition: NON-BLOCKING, because closing it
requires arbitrary trusted production-code execution, which is outside the
WLT receipt-provenance runtime threat boundary and already permits direct
bypass through platform DB primitives regardless of any fix to this
specific type.

## Phase 2C-D3A — exact-version normalization / permanent stale classification (no terminal application)

## Phase 2C-D3B — terminal application, `received`→`processed` lifecycle, terminal-evidence reconciliation, TX-B/TX-C crash-window closure

Phase 2C-D3B replaced D3A's temporary 503 subgate with real terminal
application through the EXISTING, unmodified `ScreeningApplicationService`
(the same authority `wallet-screening.ts`'s synchronous path uses, injected
into the receipt route via dependency injection, constructed exactly once in
`server.ts` — P2CC1-MED-1's single-construction-site invariant preserved).
The route duplicates none of the service's own locking (destination advisory
lock → destination `FOR UPDATE` → `wallet_screening_result FOR UPDATE`),
pending-only/highest-version/provider-binding revalidation, terminal
`UPDATE`s, or audit publication. A shared `reconcileOrApplyReceivedReceipt`
pipeline handles BOTH a fresh `received` row and a same-hash `received`
duplicate replay: it performs its OWN fresh, race-tolerant, unlocked re-read
of the target screening/destination state and either (a) reconciles against
already-committed terminal evidence, (b) classifies newly-discovered
permanent stale, or (c) terminally applies via the service. Terminal-evidence
reconciliation requires an EXACT five-field match — same target
`screening_result_id`, `source_authenticated = TRUE`, `screening.payload_hash
= inbox.payload_hash`, `screening.provider_result_id =
inbox.provider_result_id`, `screening.provider_id = inbox.provider_id` — the
ONLY basis for inferring "this receipt caused it," never a terminal-status-
only shortcut; a match transitions `received → processed` with NO
re-normalization, NO second service call, NO second terminal audit. This is
precisely how the TX-B (service commits)/TX-C (inbox `received → processed`)
crash window closes: if TX-C is lost, the next exact-byte replay reconciles
cleanly. L-D3A-1 was closed by routing every `received`-originating
transition through one `transitionInboxFromReceived` helper — a conditional
`UPDATE ... WHERE processing_status = 'received' RETURNING ...`, with a
zero-row result triggering an authoritative re-read rather than an assumed
outcome. M-D3A-1 was closed with a permanent committed regression test. No
migration, grant, route, error, or audit type was added; inventories held at
head `052`, 6 tables, 6 routes, 14 errors, 8 audits, 0 WLT IAM-02
permissions, 0 WLT `role_permission` rows, 9 grant files.
