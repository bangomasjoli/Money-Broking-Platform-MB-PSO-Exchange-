## Deliberate choices and departures — for the re-reviewer

1. **F33's fix is the trigger, not a second application check.** The review's required correction offered the trigger-level lock as the primary fix; v1.5 implements exactly that (`trg_asset_class_frozen` branch (b) calling `lock_asset_instruments` itself) rather than adding a second, independent application-side assertion, because only the trigger-level fix removes the dependency on writer discipline that F33 identified as the actual gap. The application's own step-3 lock is unchanged and remains the normal path; the trigger's call is a no-op re-lock on that path and the actual enforcement on any other.
2. **F33's record-insert trigger is restated as "one ordered function," not split into a numbered new trigger object.** The review's required correction offered either "state this, or state one trigger function with a fixed step order." v1.5 states the latter explicitly, because §5.1's steps already read as a fixed sequence in prose; making that explicit (and noting PostgreSQL's alphabetical-by-name firing order for genuinely separate triggers, which the design must not rely on) is the minimal correction that removes the ambiguity without renumbering or restructuring the section.
3. **F34's tracker keeps `set_config` as the transaction-local mechanism**, as the review's required correction specified, rather than introducing a new mechanism (e.g. a temp table). `set_config(..., true)` is already used by v1.4 for the (under-specified) tracker; v1.5 keeps the same primitive and specifies its data model and rules exactly, because the primitive itself was never the problem — the missing specification was.
4. **F34 does not add a lock-mode-upgrade path.** The review's required correction states "no in-transaction lock upgrade is permitted by AST-01's protocol" and "writers must request the strong mode first." v1.5 keeps upgrade refused (`AS006`) rather than inventing a safe upgrade protocol, because every documented path in 05 §7A can be — and per the "who takes what" table already is — ordered to take the strong mode first; no path in the pack actually needs an upgrade.
5. **F35(a) is enforced as a plain existence check, not a new SQLSTATE.** A `WITHDRAWN`-then-`ADMITTED` refusal is mapped to the existing `AST1_ATTESTATION_INVALID` (422) rather than inventing a new database error code, because it is the same class of condition (an attestation insert that does not satisfy the table's binding rules) `AST1_ATTESTATION_INVALID` already covers, and inventing a dedicated SQLSTATE for one additional business rule on one table would not earn its own operational distinction (contrast `AS007` in round 4, which was a genuinely different failure class — pool misconfiguration versus contention).
6. **F35(b)'s exclusion rule is the stricter of the review's two offered options.** The review said: "Preferably, exclude the bundles of every real SECURITY record in SEC(G) for every G ∈ B(X): strictly tighter, and no recency choice is needed." v1.5 takes this option (rather than "state explicitly: max(global_seq)" for a single newest record) because it needs no additional ordering key at all and is safety-equivalent or stricter in every case.
7. **F35(c) keeps the current database design** (marker draws from the shared `ast1.classification_global_seq`) rather than switching to a dedicated marker sequence, exactly as the review instructed ("Keep the current database design... Do not describe a separate marker sequence if none exists"). Only the prose (01 INV-21) was wrong; no schema change was needed or made.
8. **The two editorial items are corrected in the same pass**, per the review's "Required before the next re-review" §2: the affected-set-derivation reasoning (05 §7A, and the identical phrasing in 02 W11) is restated to say what actually makes the set stable (newcomers are record-less; re-derivation catches growth) rather than the overbroad "the gate excludes every writer" claim; `trg_lineage_merge_apply`'s description now states that `lineage_merge` stores the **resolved roots**, not the caller's original (possibly non-root) arguments, which is what the table's own constraints and the audit trail actually need.
