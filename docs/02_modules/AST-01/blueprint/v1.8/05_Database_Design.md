## 1. Design rules

1. **No column matching `/eligib/i` exists outside the decision-log and token tables** (INV-03); those hold derived *outputs* for evidence and are never read as inputs.
2. **No `UNRESOLVED`-defaulting column.** UNRESOLVED is absence of a valid record.
3. Identity-critical columns are immutable after `IDENTITY_LOCKED`; **`instrument_code`, `declared_synthetic`, `synthetic_emulates` are immutable from `INSERT`** [F09].
4. `CHECK` enums on `varchar`; timestamps `timestamptz` UTC; wire ids `varchar(64)` beside `uuid` PKs.
5. `reason_code varchar(48)` (the longest master code is exactly 48 characters).
6. **[F04] The security backstop never trusts application-supplied denormalised columns.** Any column on the log/token tables that repeats a derived value (`effective_outcome`, environment, emulation) is an *audit copy*. Enforcement reads the ledger (§7).
7. **[F05] Approver identities are stored only as IAM-02-attested values** (DCR-AST1-001(d)); the DB constrains the stored values, it does not claim to verify them independently.
8. **[v1.2: F18] One lock order, one consumption transaction.** Every path that can change an eligibility input takes the **instrument row lock first** (§7A). Token consumption is a single transaction. The SQL backstop runs at token **mint and at token consumption**, and token binding columns are immutable after mint.
9. **[v1.2: F19] Lineage-critical identity is immutable from `INSERT`**: `asset.lineage_id`, the predecessor fields, `instrument.asset_id` and the on-chain identity keys. The only lineage-changing operation is the governed, irreversible lineage merge.
10. **[v1.2: F19/F20] A canonical on-chain identity is registered once, ever** (unique over all statuses). A `SECURITY` determination narrows its lineage siblings through a **derived conjunct**, never by rewriting their classifications.
11. **[v1.2: F24] Key columns of conjunct rows are immutable from `INSERT`.** A change of target is a new row, never an `UPDATE`.
12. **[v1.3: F27, F28.b] One ordering domain, no wall clock.** Classification records, lineage merges and classification evidence draw their ordering value from the **same** sequence, `ast1.classification_global_seq`, only after the locks of §7A are held. Every ordering decision that affects security (record vs record, record vs merge, evidence vs event, the lineage conjunct, the elevated-evidence rule) compares these sequence values. **No timestamp, and no application-supplied value, participates in any security ordering**; every `*_at_utc` on the ledger, evidence and merge tables is filled by trigger and is audit-only.
13. **[v1.3: F27] A lineage merge is a ledger event.** It carries a DB-assigned `merge_global_seq` and narrows every affected instrument **in the merge transaction**, by the same derived predicate (`lineage_review_required`, §7) that a newer `SECURITY` record uses. Safety never waits for a sweep.
14. **[v1.3: F26] The record's identity binding is visible to SQL.** `authoritative_state()` derives `record_fingerprint_matches` from stored values; backstop rule **B12** denies on a mismatch. `ASSET_CLASS_CORRECTION` is a governed, locked, token-revoking writer, never an implicit side effect.
15. **[v1.3: F28.a] The database rejects a non-canonical contract identity.** The unique identity index therefore operates only on values the database itself has validated (§2.1).
16. **[v1.3: F28.c] `lineage` rows are insert-only.** `lineage.synthetic` cannot be edited by any role.
17. **[v1.4: F29] The class binding is visible to SQL independently of any cached value.** Every classification record stores the asset class it was written against (`asset_class_at_record`, trigger-filled from the live `asset` row under the instrument's own lock, immutable). Backstop rule **B12** denies whenever that stored class no longer equals the asset's **current, live** `asset_class` — a comparison that does not depend on the correction writer having recomputed the cached fingerprint correctly, because `asset.asset_class` is not a cache: it is the row `ASSET_CLASS_CORRECTION` is defined to change.
18. **[v1.4: F30] Ordering safety is enforced, not assumed, and its scope is exact.** Every lock helper and `authoritative_state()` itself assert the session runs `READ COMMITTED` and fail closed (`AS007`) otherwise, because the sequence-order guarantee depends on a lock holder seeing every commit that happened while it waited. Sequence order is proven to equal commit order **only** for a pair of events that (i) lock a common instrument, or (ii) are both serialised by the exclusive lineage gate — never for an unrelated pair, and a caller-skipped lock order is itself fail-closed (rule 19).
19. **[v1.4: F31] Lock acquisition within level 2 is strictly ascending, enforced, and never self-first.** A lineage-wide writer derives its full affected set — including its own triggering instrument — **before** locking any of it, then locks the whole set ascending in one pass; the lock-level tracker additionally rejects a lower `instrument_id` acquired after a higher one in the same transaction (`AS006`), so an out-of-order caller fails closed instead of risking a deadlock.
20. **[v1.4: F32; mechanism v1.5: F32.a; corrected v1.6: F36; re-based v1.7: F41] A referenced canonicalisation version is immutable, and "newest" is always a DB-assigned sequence.** Once any instrument references an `(address_format, canonicalisation_version)` pair, that pair's rule never changes and is never dropped; new behaviour is a new version, implemented as its **own, separate, immutable, self-contained function** (§2.2). **What is enforced, exactly (v1.7 trust boundary, rule 25):** (1) the freeze machinery — digest helper, assertion, registration/immutability/readiness triggers, the dispatcher, the DDL event trigger — is **owned by a bootstrap role** the ordinary AST migration and runtime roles cannot act as — **bound to the actual deployment migration identity, rule 27** (role separation is the boundary, not self-hashing); (2) each registered pair maps to exactly one migration-owned version-specific rule function — identified by a stable **textual** schema-qualified signature, never a stored `regprocedure` — whose **registration is refused** unless its **stored parsed body** references only approved immutable primitives (§2.2.3; `pg_depend` alone is not the dependency list); (3) the database-computed digest freezes that function's definition and the stored dependency closure freezes what it may call, the expected values being selected for the running PostgreSQL major by the exact-key rule of §2.2.10; (4) the frozen vector corpus — classified by `vector_class` against an insert-only per-format requirement table — reproduces **directly against the registered rule function and through the dispatcher, with equal results**; (5) every stored identity remains a fixed point under its own stored version, and is re-validated on the final stored row by an `AFTER` backstop so a later `BEFORE` trigger cannot leave a non-canonical value (§2.2.12); (6) no collision appears. This is **not** a claim to freeze PostgreSQL engine semantics across a major-version upgrade (§2.2.10) and **not** a claim of semantic freeze over every input the vectors do not exercise (§2.2.11). Every "newest/latest" comparison in this pack — records, merges, evidence, correction markers, and securities-market attestations (`attestation_seq`) — is a DB-assigned sequence value, never an application-suppliable timestamp. `class_correction_marker.marker_global_seq` is drawn from the **same shared** sequence as records/merges/evidence (`ast1.classification_global_seq`, §5.3), not a sequence of its own; `attestation_seq` alone is a dedicated sequence, because the attestation domain is unrelated to classification/lineage ordering (01 INV-21).
21. **[v1.5: F33] `ASSET_CLASS_CORRECTION`'s instrument-locking precondition is enforced by the trigger that changes the class, not only by application discipline.** `trg_asset_class_frozen` branch (b) itself calls the same lock helper the application calls (`ast1.lock_asset_instruments`) — enumerating and locking **every** instrument of the asset, including record-less ones, ascending — **before** it permits `asset_class` to change. A raw or defective correction writer that skips the application's own locking therefore still cannot change the class ahead of every instrument being locked; the property F29/INV-24 rests on no longer depends on writer discipline.
22. **[v1.5: F34; restored v1.6: F38; made real v1.7: F38; re-scoped v1.8: F42] The lock-order tracker is a defined, transaction-local, **advisory ordering structure** — never proof that PostgreSQL granted a row lock — with no in-transaction upgrade, and every governed lock on levels G–3 goes through it.** It holds the **set** of keys held per level with their mode, not only "the last id"; **[v1.8: F42] it is written with `set_config('ast1.…', …, true)`, which any session can call, so it is not tamper-proof and no security decision reads it as evidence of possession. The PHYSICAL-LOCK-ALWAYS rule:** a request for a key the tracker shows at the same or a stronger mode (1) skips the level/order check, (2) does not add or advance tracker state, (3) raises no `AS006` — **but (4) still issues the PostgreSQL row-lock statement for the requested key at the requested mode.** If the transaction genuinely holds a lock of that strength PostgreSQL returns immediately (no wait, no new conflicting lock); if the tracker entry was forged, the helper has genuinely acquired the lock. A request for a stronger mode on a key the tracker shows at a weaker mode fails closed (`AS006`) before any statement — a refusal, never a way to skip a lock; the state is `set_config(..., true)` (transaction-local), so it — together with the row locks taken in the same subtransaction — reverts automatically and identically at `ROLLBACK TO SAVEPOINT`, `ROLLBACK` and `COMMIT`, with no reliance on `BEGIN` or on any pooler behaviour (§7A). **[v1.7: F38] The governed-lock rule, one normative statement:** *every* AST-01 governed protocol lock — **G** (governed change), **0** (lineage gate), **1** (asset), **2** (instrument), **3** (token) — is acquired **only** through a named AST lock helper (the complete family and its levels are defined once, in §7A "Lock helper family"). **No application writer and no AST trigger may directly issue a governed `SELECT … FOR SHARE` / `SELECT … FOR UPDATE` against these protocol objects outside a helper's own implementation.** Every normative step in this pack that acquires such a lock is therefore written as a helper call with its mode (e.g. `lock_instrument(id, SHARE)`), never as raw SQL; the only places raw row-lock SQL appears are the helper implementations, and the static scan T-LOK-07(m) enforces this over implementation files and AST migration function bodies once they exist (the blueprint states only its acceptance condition and claims no implementation code exists). This is what makes the tracker's ordering and upgrade decisions decidable at all: a lock the tracker never saw is a lock the ordering logic cannot reason about (§7A). **[v1.8: F42] It is also why the tracker's bookkeeping can be wrong — because a raw writer forged it — without ever removing a security-bearing lock: runtime safety rests on the actual PostgreSQL row locks plus database constraints and triggers, never on the tracker (§7A "The tracker is advisory").**
23. **[v1.6: F37; enforced in SQL v1.7: F40] An `INSTRUMENT` underlying link may target only an instrument whose own link set is already frozen, and this is a database rule, not application discipline.** The **source** rule is unchanged: the linking instrument must be `DRAFT`, and once it leaves `DRAFT` its underlying set is immutable (§4.3). The **target** rule: the row named by `instrument_underlying.underlying_instrument_id` must be `IDENTITY_LOCKED` or `RETIRED`, never `DRAFT`. **[v1.7: F40] Both are checked by one ordered `BEFORE INSERT` trigger function, `trg_underlying_insert_guard` (§4.3), whose *first* security-relevant act is to lock both endpoint instruments strongly through `lock_instruments({instrument_id, underlying_instrument_id}, UPDATE)`; only after both locks are held does it read either lifecycle status.** A raw `INSERT` that bypasses the application protocol is therefore serialised against a concurrent identity lock of either endpoint exactly as the protocol path is. Recursively: a `DRAFT` instrument may add links; every instrument it points to is already non-`DRAFT`; every non-`DRAFT` target's own link set is therefore already frozen; so the full transitive underlying/basis tree of a classified instrument cannot later grow through a late link on some still-`DRAFT` intermediate (§4.3, §7, §7A).
24. **[v1.7: F40, new] A classification record can exist only for an `IDENTITY_LOCKED` instrument, as a SQL invariant.** The record-insert trigger, after it holds the instrument's row lock and before it evaluates any classification semantics, refuses the insert unless `lifecycle_status = 'IDENTITY_LOCKED'` (`AST1_INSTRUMENT_NOT_IDENTITY_LOCKED`, `AS004`; §5.1 step 2A). `DRAFT` is refused because a `DRAFT` instrument has not passed the identity lock; `RETIRED` is refused because a retired instrument is terminal and ineligible for any new classification (06 SM-1; no governed historical-classification action exists in this blueprint, and v1.7 does not create one). Together with the SM-1 rule that no instrument returns to `DRAFT`, this makes "a classified instrument is non-`DRAFT`" a **database invariant**, on which the recursive basis-tree proof of rule 23 now rests (§4.3).
25. **[v1.7: F41, new] Bootstrap trust boundary for the address-rule freeze.** The machinery that decides whether the canonicaliser freeze is valid is owned by a dedicated privileged **bootstrap role** (`role_ast1_bootstrap`, or the project's equivalent — a controlled **superuser** identity, rule 27), which sits **outside** the ordinary AST migration threat boundary. The ordinary AST migration and runtime roles must not own, `CREATE OR REPLACE`, `ALTER`, `DROP`, or change the ownership of that machinery, and cannot disable, drop, replace or alter the DDL event trigger that guards it (§2.2.1, §2.2.9). The design deliberately does **not** try to solve infinite self-reference by having the digest helper prove its own digest: **the security boundary is role separation**, and P1 acceptance must prove the privilege model **as the actual deployment migration identity** (T-ADR-24; rule 27).
26. **[v1.7: F41, new] No table-reading function sits inside a `CHECK` constraint.** PostgreSQL does not support `CHECK` constraints that reference table data other than the row being checked: such a constraint is not re-validated when the other table changes, and a dump/restore can fail on load order. v1.6's `instrument` canonical-address `CHECK` (calling the registry-reading dispatcher) and `network_registry` `CHECK` (calling a registry-reading existence function) are **removed**. Cross-table enforcement is done by a composite foreign key plus `BEFORE` triggers (§2, §2.1, §2.2), which are true database enforcement because they execute inside PostgreSQL.
27. **[v1.8: F43, new] The freeze boundary is bound to the identity that actually runs AST migrations.** `AST_MIGRATION_IDENTITY` — the actual connection identity `platform migrate:up` uses for AST migrations in every environment — must not be a superuser, a direct or indirect member of `role_ast1_bootstrap`, the owner of schema `ast1`, or hold any path (`SET ROLE`, a role grant, `GRANT SET` on `session_replication_role`/`event_triggers`, ownership of a bootstrap object) that bypasses the boundary (§2.2.0). `role_ast1_bootstrap` must create and own PostgreSQL event triggers and is therefore a controlled **superuser** identity; it is used only by a separate reviewed bootstrap install/maintenance procedure (`AST-P1-BOOTSTRAP-INSTALL`) and **never by routine `migrate:up`**. The repository's current single-superuser migration identity is an **external platform dependency (DCR-AST1-010)**, not assumed solved; **P1 STOPS** at `AST-P1-MIGRATION-IDENTITY-GATE` if the actual deployment cannot satisfy it (no silent fallback; the fallback is a separate architecture review).
28. **[v1.8: F44, new] Bootstrap functions resolve names only through pinned paths; rule functions are judged by their stored parse tree; the address identity is validated on the final stored row; no durable `reg*` column.** (a) Every bootstrap-owned function is declared `SET search_path = pg_catalog`, schema-qualifies every non-`pg_catalog` reference, states SECURITY INVOKER/DEFINER explicitly (none is DEFINER in v1.8) and has `PUBLIC` `EXECUTE` revoked; assertion step 0 verifies the exact `proconfig` (§2.2.1a). (b) The dispatcher resolves the frozen **textual** identity through `pg_catalog.to_regprocedure`, verifies the resolved `pg_proc` row and invokes only that OID-derived, schema-qualified identity (§2.1). (c) A rule function must be `LANGUAGE SQL` with an SQL-standard body of a narrow allowed form; registration inspects its **stored parsed body** — `pg_depend` records no edge to pinned built-ins and is only a secondary check (§2.2.3). (d) An `AFTER` final-row backstop re-validates the stored `contract_address_canonical` after every `BEFORE` trigger, and a bootstrap-owned trigger inventory covers the identity tables (§2.2.12). (e) The registry stores `rule_function_identity text`, never a `regprocedure` (`pg_upgrade`, §2.2.13). (f) After a PostgreSQL major upgrade the assertion compares against the exact-key `(format, version, pg_major)` rebaseline digest (§2.2.10).
29. **[v1.8: F45, new] No AST row lock and no open apply transaction is ever held across the IAM-02 `execute-verify` call.** Every governed apply runs in two phases: **Phase A** outside any database transaction (unlocked read, local prechecks, recompute the immutable payload hash, IAM-02 `execute-verify`, capture `verified_payload_hash` and the attested evidence) and **Phase B** in one apply transaction whose **first** lock is `lock_governed_change(change_id)` (level G), followed by a locked re-read of every authoritative precondition — including `recomputed payload_hash = verified_payload_hash` — and only then levels 0 → 1 → 2 → 3 → writes. A change of state between verification and the locked re-read fails closed; a retry needs fresh IAM-02 verification (§7A "Governed apply protocol").

### 2.1 Canonical contract identity is validated by the database [v1.3: F28.a; re-based v1.7: F41]

**Problem (F28.a).** v1.2 guaranteed the canonical form of `contract_address_canonical` only through one TypeScript function. A registration-path defect that stored a second spelling of one contract would defeat `ux_ast1_instrument_token_identity` and make the resolver miss the row.

**Contract.** The database owns a versioned, deterministic canonicaliser and refuses any value that is not already in its output form. It never rewrites a supplied value.

```sql
-- MIGRATION-OWNED, VERSION-SPECIFIC RULE FUNCTIONS: ONE per registered (address_format, canonicalisation_version) pair [v1.6: F36] —
-- never a shared multi-version function with case arms. Each is IMMUTABLE, STRICT, LANGUAGE SQL with a SQL-standard body,
-- schema-qualified, and SELF-CONTAINED (§2.2.2–§2.2.3). Illustrative names:
ast1.canonicalise_evm_hex40_v1(p_raw text) RETURNS text            -- NULL when p_raw is not a valid address for this exact version
ast1.canonicalise_base58_fixed_v1(p_raw text) RETURNS text
ast1.canonicalise_tron_base58check_v1(p_raw text) RETURNS text
-- … one such function per registered pair, named after the exact rule it implements, never touched again once registered (§2.2)

-- GENERIC DISPATCHER [v1.7: F41; invocation pattern v1.8: F44(b)]: BOOTSTRAP-OWNED (§2.2.1), SECURITY INVOKER, STABLE, SET search_path = pg_catalog (§2.2.1a).
-- It performs ONE generic registry lookup
--   (p_address_format, p_version) → the immutable address_rule_version.rule_function_identity (a schema-qualified TEXT signature — never a stored regprocedure)
-- resolves it with pg_catalog.to_regprocedure, verifies the resolved pg_proc row, and invokes THAT exact function through the pattern below.
-- There is NO format/version CASE table, NO inline regex and NO independent routing semantics inside the dispatcher. An unregistered pair raises
-- AS004 (AST1_ADDRESS_RULE_FREEZE_VIOLATION, reason RULE_NOT_REGISTERED), never NULL. It is used by triggers, the resolver, the freeze assertion
-- and the sweep — and by NO CHECK constraint anywhere (rule 26). The migration identity cannot replace it (rules 25, 27).
ast1.canonicalise_address(p_address_format varchar, p_version varchar, p_raw text) RETURNS text   -- STABLE, bootstrap-owned, SECURITY INVOKER
-- [v1.7: F41] ast1.address_rule_supported() is REMOVED. It only existed to feed a CHECK; the composite FK and
-- trg_network_registry_rule_ready (§2.2.7) replace it. (If an implementation keeps a read-only convenience of that name it must be
-- bootstrap-owned and must not appear in any CHECK.)
```

**Dispatcher invocation pattern — exact [v1.8: F44(b)].** Inside `canonicalise_address` (SECURITY INVOKER; pinned `search_path = pg_catalog`; every reference qualified):
1. **Registry lookup — static SQL.** `SELECT rule_function_identity, registered_owner INTO … FROM ast1.address_rule_version WHERE address_format = p_address_format AND canonicalisation_version = p_version`; the two arguments are bind values of a static statement. No row ⇒ `AS004` `RULE_NOT_REGISTERED`.
2. **Resolve by the catalog, never by caller text.** `v_oid := pg_catalog.to_regprocedure(rule_function_identity)::pg_catalog.oid`. `NULL` ⇒ `AS004` `RULE_FUNCTION_MISSING`.
3. **Verify the resolved `pg_proc` row** (`pg_catalog.pg_proc` where `oid = v_oid`): it exists; signature is exactly `(text) → text`; `provolatile = 'i'`; the owner equals the registered expected owner (`registered_owner`); `prolang` is `sql`; `NOT prosecdef`; `proconfig = {search_path=pg_catalog}` — else `AS004` `RULE_FUNCTION_PROPERTIES`. (Whether the function body stays within the allowed form was verified at registration and is re-verified by the assertion; the dispatcher re-checks the cheap catalog properties on every call.)
4. **Invoke only that resolved identity.** Build the statement from the **OID-derived, identifier-quoted, schema-qualified name** — `v_sql := pg_catalog.format('SELECT %I.%I($1)', n.nspname, p.proname)`, where `n`/`p` are the `pg_namespace`/`pg_proc` rows of `v_oid` — then `EXECUTE v_sql INTO v_result USING p_raw`. (Rendering a `regprocedure` through `%s` would include the argument list and, unless the pinned path qualifies it, could emit an unqualified name; deriving `%I.%I` from the resolved row avoids both. An equivalent OID-derived implementation is acceptable if it never interpolates caller-supplied text.)
5. **Raw input stays a bind parameter.** `p_raw` is passed with `USING`, never concatenated: no SQL-injection route exists. `p_address_format` and `p_version` are only bind values in step 1. The rule function is `STRICT`, so a `NULL` `p_raw` yields `NULL`.

- **Closed rule set, one function per version [v1.6: F36].** `address_format` is a closed vocabulary; each registered `(address_format, canonicalisation_version)` pair is implemented by its **own, separate, immutable function** — never a `CASE` arm inside one multi-version function, and never a function whose body a later migration edits while the version stays registered. Adding a new version is a reviewed migration that **creates a new function** and registers it (§2.2); it never edits an existing registered pair's function. Illustrative rules, fixed by the migration phase against the chain list WLT-01 supports (each row below is, concretely, one dedicated function plus one `address_rule_version` registration):

  | Format (illustrative) | Accepted raw input | Canonical output |
  |---|---|---|
  | `EVM_HEX40` | `^(0x\|0X)?[0-9A-Fa-f]{40}$` | `'0x' \|\| lower(hex40)` — an EIP-55 mixed-case checksum spelling and its lower-case form are **one** identity |
  | `BASE58_FIXED` (e.g. Solana-style) | `^[1-9A-HJ-NP-Za-km-z]{32,44}$` | identical (base58 is case-significant and has one spelling per byte string) |
  | `TRON_BASE58CHECK` | `^T[1-9A-HJ-NP-Za-km-z]{33}$` | identical; the hex `41…` spelling is **not** accepted as an alternative identity |
  | any other | — | **no rule ⇒ no `TOKEN_CONTRACT` instrument can be registered on that network** (fail closed) |

- **Where it is enforced [v1.7: F41 — replaces the v1.6 "two layers"; there is no `CHECK` layer].**
  1. **`trg_instrument_address_canonical` — the authoritative enforcement.** `BEFORE INSERT OR UPDATE` on `instrument`; it executes inside PostgreSQL, so this **is** database enforcement. **`INSERT`** — for `TOKEN_CONTRACT` it (i) reads `network_registry` for `(chain, network)` — the network must be `ACTIVE` and name a registered pair; (ii) resolves the **exact registered rule function** of that pair (`rule_function_identity`, resolved with `pg_catalog.to_regprocedure`) and executes it through `ast1.canonicalise_address` (the exact invocation pattern above); (iii) **overwrites** `instrument.address_format` and `instrument.address_canonicalisation_version` from the registry (application values ignored, as `recorded_environment` is) — i.e. it **stamps** format and version; (iv) **raises `AS005` (`AST1_ADDRESS_NOT_CANONICAL`) when the result is `NULL` or differs from the supplied value**. The supplied value is never silently canonicalised or accepted "as close enough": the registration path must send the canonical value, and a raw spelling is an error. Because it is a `BEFORE` trigger it runs **before** unique-index admission, so a second spelling never reaches `ux_ast1_instrument_token_identity`. **`UPDATE`** [v1.4: F32.a] — compares `OLD` against `NEW` on `chain`, `network`, `contract_address_canonical`, `address_format`, `address_canonicalisation_version` and raises `AS002` if any differ (these columns are already immutable from insert, §4.2, and `trg_instrument_immutable_from_insert` enforces the same thing; this trigger is a second, independent check on the identity columns specifically). It **never re-reads `network_registry`** and never re-validates against the *current* rule or the network's *current* `ACTIVE`/`SUSPENDED` status — an `UPDATE` that leaves these columns untouched (retire, an identity lock, the correction's fingerprint recompute, any other tightening) succeeds regardless of what has since happened to the network row. The stored identity was validated once, at `INSERT`, under the version it names, and stays valid under that version forever (rule 20). **[v1.8: F44(d)] A `BEFORE` trigger cannot assume that no later-named `BEFORE` trigger rewrites `NEW` afterwards, so the STORED final row is re-validated by an `AFTER` backstop, `trg_instrument_address_final` (§2.2.12): an `INSERT` whose address a later `BEFORE` trigger rewrote to a non-canonical value is refused there (T-ADR-31).**
  2. **Existing instrument identity columns are immutable thereafter** (`trg_instrument_immutable_from_insert`, §4.2).
  3. **Exact unique indexes** (`ux_ast1_instrument_token_identity`, `ux_ast1_instrument_native_identity`, §4.2).
  4. **The rule freeze** (§2.2), **the final-row backstop and the trigger inventory** (§2.2.12), **the integrity sweep** (below, S9), **fixed-point validation** of every stored identity (assertion step 7) and **collision validation** (assertion step 8) — the controls that catch a disabled trigger or an index bypass after the fact.
  - **Who can disable the enforcement.** The runtime role holds no `TRIGGER` privilege and owns nothing; the ordinary migration identity (§2.2.0) cannot disable, drop or replace `trg_instrument_address_canonical` — or add an unapproved trigger on `instrument` — without a `ddl_command_end` DDL event that the bootstrap-owned event trigger turns into an abort (§2.2.9: the assertion checks that each enforcement trigger exists, is enabled and calls its inventoried function, and that no unapproved trigger exists on the identity tables, §2.2.12). Any privilege sufficient to disable a trigger outside that path (table owner / superuser) is an elevated owner privilege **outside the runtime role** and outside the ordinary migration identity's day-to-day grants; it is the out-of-band DBA case that sweep S10 inventories. There is no `CHECK` to "survive" a disabled trigger — v1.6's claim that one did is withdrawn (rule 26).
- **Uniqueness operates on validated values only.** `ux_ast1_instrument_token_identity` (§4.2) is created over `(chain, network, contract_address_canonical)`; because every row that reaches the index has passed the trigger above, two spellings of one contract cannot coexist as two rows, and a defect in the application's canonicaliser surfaces as an `AS005` rejection rather than a duplicate identity.
- **One canonicaliser.** The resolver canonicalises a requested reference with the **same SQL dispatcher** (`SELECT ast1.canonicalise_address(nr.address_format, nr.canonicalisation_version, $raw) FROM network_registry nr …`); a reference that yields `NULL` matches nothing (`INSTRUMENT_NOT_FOUND`). The TypeScript `canonicaliseContractAddress` is a **mirror** used for early client-side validation and is parity-tested against the SQL function over one shared vector corpus (T-ADR-03).
- **Versioning is append-only [v1.4: F32.a; per-function model v1.6: F36].** Each instrument stores the `address_canonicalisation_version` it was registered under (immutable). Once **any** instrument references an `(address_format, canonicalisation_version)` pair, that pair's **dedicated version-specific function** is **frozen**: no migration may `CREATE OR REPLACE` it, and the bootstrap-owned event trigger and freeze assertion (§2.2.9, §2.2.8) abort an attempt that tries anyway. The function keeps working for as long as any row names it, so the trigger, the resolver, TypeScript parity and the sweep all keep working against a version nothing has re-defined out from under them. There is no table-reading `CHECK` for a dump/restore to trip over: a restore recreates the FKs and triggers after the data load, and the post-restore assertion and sweep S9 re-verify every identity (T-ADR-27). **New canonicalisation behaviour is always a new `canonicalisation_version` and a new function.** A network row may adopt the new version for **future** registrations (`network_registry.canonicalisation_version` is an ordinary mutable column of that reference table, guarded by the readiness trigger); existing instruments keep the version — and therefore the exact rule — they were registered under. **Migrating existing identities to a new canonical form is a separate governed data task, never automatic**: it must first compute every affected instrument's prospective value under the new rule, fail closed on any collision it would create (never silently split or merge two identities), and only then, as its own reviewed migration, move the named instruments to the new version. The pre-activation sweep check (below) is this task's collision detector, not a routine part of ordinary operation.
- **What the database cannot check.** It has no checksum primitive, so it cannot tell a well-formed but mistyped address from the intended one (a typo that happens to be well-formed registers a wrong identity, which is harmless — OQ-8). Checksum validation, where a chain has one, stays in the TypeScript mirror and in `POST /instruments/validate`; it is advisory and never a precondition the database relies on.
- **Sweep (defence in depth) [v1.4: F32.a — re-canonicalises under each row's own stored version].** The integrity sweep re-canonicalises **every** stored `TOKEN_CONTRACT` identity under **the `canonicalisation_version` that instrument itself stores** — never the network's current version, which may since have moved on — and (a) flags any value that is not a fixed point of its own version's rule (a version is frozen once referenced, rule 20, so this is purely a tamper/corruption check, never a "the rule changed under us" false positive); (b) groups by `(chain, network, canonicalise-under-own-version(value))` **across every version registered on that network** and flags any group with more than one row (the unique index bypassed by a disabled trigger/index, or a cross-version collision a migration task's own check should have caught first); (c) checks the two identity indexes **and the enabled state of `trg_instrument_address_canonical`** exist. A finding places a `SYSTEM` hold on each colliding or non-canonical instrument (`IDENTITY_COLLISION`, `IDENTITY_NOT_CANONICAL`) and emits `ast1.integrity.address_canonical_violation` (critical, worded against **the instrument's own stored version**, never "the current network rule" [v1.5: F32.a]). It never rewrites a row. A **planned** version migration's own pre-activation check (above) is a separate, one-off run over the prospective new values; this sweep rule is the standing, routine one.

### 2.2 Address rule freeze — trust boundary, registry, vectors, assertion [v1.5: F32.a; v1.6: F36; re-based v1.7: F41; identity, name resolution, parsed-body policy, final-row backstop, no `reg*` v1.8: F43/F44]

**Problem history.** Rule 20 and §2.1 state the freeze rule. v1.5 added a registry and an assertion; v1.6 corrected the circular digest, the vector contradiction, the invalid `CHECK … EXISTS` and the "mechanically enforced" overclaim. The round-7 review (`04-review-r7.md` §5, §16 F41) found the boundary of the freeze itself still open: (i) the dispatcher's routing was not frozen; (ii) the freeze machinery (digest helper, assertion, triggers) could be replaced by the very role it constrains; (iii) a rule function's dependency closure was unconstrained, so hashing "the wrapper" did not freeze semantics; (iv) v1.6 put table-reading `STABLE` functions inside `CHECK` constraints; (v) "required vector classes" were prose only; (vi) the readiness trigger was conditional, a dangling `rule_function` was not handled `NULL`-safely, and an author-maintained manifest survived as a fallback; (vii) the PostgreSQL-upgrade story was unpinned. v1.7 adopted one architecture: **bootstrap-owned freeze machinery + migration-owned, versioned, self-contained rule functions.** The round-8 review (`04-review-r8.md` §10–§14, F43/F44, which supersede F41) found that architecture sound in shape but (F43) **not bound to the identity that actually runs migrations** — the platform runs one superuser identity — and (F44) unsound in six mechanisms: unpinned bootstrap name resolution, an unspecified dispatcher invocation, a `pg_depend`-based dependency rule that cannot see pinned built-ins, a `BEFORE`-trigger-order bypass, a `regprocedure` column that blocks `pg_upgrade`, and an unspecified post-upgrade digest. **v1.8 corrects each (§2.2.0–§2.2.13); the architecture is unchanged.**

#### 2.2.0 Identities, the bootstrap install path and the P1 migration-identity gate [v1.8: F43]

v1.7 designed the role separation of §2.2.1 but never bound it to the identity that actually executes AST migrations. The platform's migration runner today is **one** connection (`platform` `migrate:up` = `node-pg-migrate -m infra/migrations --no-check-order up`), and existing migrations record that they execute as a single `postgres` superuser identity "in every environment" (`003_iam_rls_token_lookup.cjs`, `007_iam2_seed_sod_rules.cjs`). A superuser owns every boundary in §2.2.1, so the role separation is void unless the identity that really runs AST migrations is **not** one. This section makes that dependency explicit and defines the identities, the install path and the P1 stop gate. **It changes no platform configuration** — that is a dependency-change request (DCR-AST1-010, file 17), recorded and not made.

This gate is independent of, and in addition to, the event-trigger installation gate of §2.2.9.

- **The bootstrap role is a controlled superuser and outside the ordinary AST migration threat boundary (§2.2.0).** It is the role that already needs elevated privilege for other bootstrap DDL (§10) and — because PostgreSQL requires a superuser to create and own an event trigger — it is a **superuser**, not merely "superuser-equivalent". It is used only by the separate bootstrap install/maintenance procedure; **never** by routine `migrate:up`, CI/CD migration runs or any service. The migration identity's holding `CREATE` on `ast1` is deliberate (it creates the migration-owned objects) and is precisely why every bootstrap function pins its name resolution (§2.2.1a).
- **No infinite regress.** The digest helper does **not** prove its own digest, and no object in the bootstrap set is hashed by another bootstrap object to establish trust. **The security boundary is role separation, bound to the identity that actually runs AST migrations (§2.2.0).** The assertion's step 0 additionally verifies `proowner`/`relowner`/`tgenabled`, the exact `proconfig` of every bootstrap function and the trigger inventory, but this is a *misconfiguration detector* (defence in depth), not the boundary: an actor who could already defeat role separation could defeat that check too.
- **P1 acceptance must prove the privilege model as the ACTUAL deployment migration identity** (T-ADR-24; a test-created substitute role is insufficient): as `AST_MIGRATION_IDENTITY`, every listed bootstrap object refuses `CREATE OR REPLACE`, `ALTER`, `DROP`, `ALTER OWNER`, `ALTER TABLE … DISABLE TRIGGER`, `ALTER EVENT TRIGGER … DISABLE`, and `DROP EVENT TRIGGER`; as the runtime role, likewise and additionally every DDL.

#### 2.2.1a Bootstrap function security mode and name resolution [v1.8: F44(a)]

v1.7 imposed name-resolution hardening only on the rule functions. The migration identity holds `CREATE` on `ast1` and chooses its own session `search_path`, so an unpinned bootstrap function that calls, say, `pg_get_functiondef` unqualified can be made to call an attacker-created `ast1.pg_get_functiondef` under `SET search_path = ast1, pg_catalog` (round-8 probe P3): the digest step then compares forged text and passes, with no bootstrap object replaced. **Every bootstrap-owned function that participates in a security decision therefore obeys all of the following:**

1. it is declared `SET search_path = pg_catalog` (exactly `proconfig = {search_path=pg_catalog}`) — never the ambient path;
2. it **schema-qualifies every non-`pg_catalog` object reference** (`ast1.address_rule_version`, …) and, where a `pg_catalog` name could be captured (relations and types through the implicitly-first `pg_temp` schema; operators), uses the qualified forms — `pg_catalog.text`, `OPERATOR(pg_catalog.=)`, `pg_catalog.format(…)`, `pg_catalog.to_regprocedure(…)`. With the path pinned, an `ast1`-schema function or operator cannot capture a `pg_catalog` call;
3. it **states SECURITY INVOKER or SECURITY DEFINER explicitly** (table below). **v1.8 designates no bootstrap function `SECURITY DEFINER`:** each runs with the invoker's privileges, which suffice for what it reads (`pg_catalog`, the freeze tables it is `SELECT`-granted, instrument rows read by the instrument owner or the runtime role), so the superuser-owned `SECURITY DEFINER` escalation class (CVE-2018-1058) does not arise. **If an implementation nevertheless makes any of them `SECURITY DEFINER`, the pin (1) and qualification (2) are mandatory, `PUBLIC` `EXECUTE` must be revoked, and it is a named implementation-review item;**
4. it has `EXECUTE` **revoked from `PUBLIC`**, and `EXECUTE` is granted only to the roles named below (`CREATE TRIGGER` needs `EXECUTE` on the trigger function at attachment time, not at firing).

Because the dispatcher and the instrument triggers are `INVOKER`, the calling role also needs `EXECUTE` on the version-specific rule function it is dispatched to; the registering migration grants that (a missing grant fails closed with a permission error, never open).

**Bootstrap config self-check (assertion step 0).** `ast1.bootstrap_inventory` (bootstrap-owned, insert-only, §2.2.5) lists every function above with its expected owner, expected `prosecdef` and exact expected `proconfig`. Assertion step 0(b) verifies for each inventoried function: it exists; owner = the bootstrap role; `prosecdef` = the inventoried value; **`proconfig` is exactly `{search_path=pg_catalog}`** (no more, no less); no `PUBLIC` `EXECUTE`. Any mismatch — including an unpinned or differently pinned bootstrap function — **fails closed** (`BOOTSTRAP_CONFIG_DRIFT`, `AST1_ADDRESS_RULE_FREEZE_VIOLATION`). As with the rest of step 0 this is a *misconfiguration detector*, not the boundary (rule 25). **Shadowing test (T-ADR-29):** an attacker-controlled `ast1.pg_get_functiondef(oid)` (and a shadowing operator/function) under `SET search_path = ast1, pg_catalog` must not change what the digest helper or the assertion computes: the freeze assertion still detects the actual rule change and behaves identically to the default path.
#### 2.2.2 Version-specific rule function contract

Each `(address_format, canonicalisation_version)` maps to **exactly one** rule function, identified by the **textual** schema-qualified signature `rule_function_identity` (e.g. `ast1.canonicalise_evm_hex40_v1(text)`; §2.2.5, §2.2.13 — no durable `regprocedure`). It must have exactly the signature `(text) RETURNS text` and be: **`IMMUTABLE`**; **`STRICT`** (a `NULL` input yields `NULL`, matching the dispatcher's "invalid ⇒ `NULL`" convention); **`LANGUAGE SQL` with a SQL-standard body** (`BEGIN ATOMIC … END` / `RETURN expr`, PostgreSQL 14+ — the body is parsed and stored at creation as `prosqlbody`, object references are resolved at creation, and no name is resolved through `search_path` at call time); **schema-qualified** (`ast1.…`) and declared with `SET search_path = pg_catalog`; **not** `SECURITY DEFINER`; **owned by the migration identity** (`AST_MIGRATION_IDENTITY`, §2.2.0); and within the **narrow allowed form and parsed-body policy of §2.2.3**. The PostgreSQL version floor (14) is part of the pinned platform baseline (§2.2.10).

#### 2.2.3 Allowed rule-function form and the registration-time parsed-body inspection [v1.8: F44(c) — rewritten]

**`pg_depend` is not the dependency list.** PostgreSQL records **no** `pg_depend` edge from a function to pinned (initdb) objects. A `LANGUAGE SQL` function that calls `now()`, `random()` or `current_setting()`, reads `current_user`, or selects from `pg_catalog.pg_class` records only a dependency on its schema (round-8 probe P1); PostgreSQL also does not verify an `IMMUTABLE` declaration. v1.7's rule ("walk `pg_depend` … require every referenced object to appear in the allow-list") is therefore **withdrawn**. `pg_depend` is kept only as a **secondary** defence for *unpinned* objects (user functions, extension objects, user relations) and is **never** the authoritative or complete dependency list.

**Allowed form — narrow and mechanically inspectable.** A version-specific rule function must be: `LANGUAGE SQL`; **SQL-standard parsed/stored body** (`prosqlbody IS NOT NULL`); `IMMUTABLE`; `STRICT`; not `SECURITY DEFINER`; exactly `(text) RETURNS text`; `proconfig = {search_path=pg_catalog}`; schema-qualified; and it must contain **no** dynamic SQL, **no** PL/pgSQL or any other procedural language, **no** `EXECUTE`, **no** relation reads, **no** subquery against a relation, **no** unqualified object reference and **no** session/server-state access. **Registration refuses anything outside this form** (`FUNCTION_PROPERTIES` / `DEPENDENCY_POLICY`).

**Inspection of the STORED PARSED BODY.** `trg_address_rule_version_register` (bootstrap-owned, `BEFORE INSERT` on `address_rule_version`) inspects the function's stored parse tree (`pg_proc.prosqlbody`), **not** source keywords. From that representation it enumerates every referenced: **function OID** (`FuncExpr`); **operator OID and its implementing function** (`OpExpr`, `DistinctExpr`, `NullIfExpr` → `pg_operator.oprcode`); **type OID** (every expression, `Const`, coercion, array/domain base); **collation OID** (`inputcollid`, `CollateExpr`, result collations); **relation OID / range-table entry** (`RangeTblEntry`, `SubLink`); and every **`SQLValueFunction`, `NextValueExpr`, `CurrentOfExpr` or other special session/state-dependent construct**. The implementation mechanism — a controlled bootstrap parse-tree walker appropriate to PostgreSQL 17 — is a P1 choice; **the acceptance criterion is the object set above.** **Default-deny:** any node tag the walker does not explicitly classify as allowed refuses registration (`DEPENDENCY_POLICY`), so a special expression form that PostgreSQL represents without a normal dependency is classified or refused, never silently passed.

**Rules applied to that object set** (the caller supplies none of the resulting values):
1. **Functions and operators.** Every referenced function, and every operator's implementing function, must appear in `ast1.approved_primitive` (exact identity, expected owner, expected volatility, approval for the running PostgreSQL major, frozen digest where applicable) **and** have `provolatile = 'i'` at registration.
2. **Types and collations.** Only `pg_catalog` types and approved frozen primitives; a collation-sensitive approved primitive may be used only with `COLLATE "C"` stated explicitly in the body, so a rule never depends on the database default locale.
3. **Relations.** **Any relation reference is refused** — user table, view **or system catalog** (`pg_class`, …) — as is any `SubLink`/subquery, aggregate, window function or set-returning function.
4. **Refused explicitly** (each would also fail rule 1 by not being approved): `current_user`, `current_role`, `session_user`, `current_catalog`, `current_schema`, `CURRENT_DATE`/`CURRENT_TIME`/`CURRENT_TIMESTAMP`, `LOCALTIME[STAMP]` (`SQLValueFunction`); `now()`, `clock_timestamp()`, `statement_timestamp()`, `transaction_timestamp()`; `random()`, `gen_random_uuid()`; `nextval()`/`currval()` (sequence state); `current_setting()`, `set_config()` (GUC state); `pg_backend_pid()`, `txid_current()`; and **every** function that executes SQL text or reads session/server/GUC state (for example the `query_to_xml` family). Exclusion is by the exact allow-list, not by a keyword blacklist.
5. **Approved primitives.** `approved_primitive` is itself bootstrap-owned and insert-only. Each allowed non-`pg_catalog` immutable primitive has an exact identity, expected owner, expected volatility, the approving PostgreSQL major (and, for a frozen primitive, its own dependency closure) and a definition digest where applicable. **No unfrozen user helper can be approved:** a `FROZEN_BOOTSTRAP` primitive must be owned by `role_ast1_bootstrap` and carry a digest and closure; a migration-owned helper is never eligible; an extension primitive records name and version (a version change is a freeze violation).
6. **Recorded, DB-computed attestation.** The trigger stores `dependency_closure_sha256` — a SHA-256 over the sorted list of approved primitive identities (and extension name/version pairs) recovered **from the parse tree** — and `dependency_policy_version`; the assertion **recomputes** it from the stored `prosqlbody` at every check (step 3), so a later change to a frozen bootstrap primitive, a volatility flip of an approved function, or an extension version change is caught although the wrapper function's own text never changed.

**Registration does not claim** that hashing the wrapper covers arbitrary helper dependencies: it covers exactly (wrapper definition, by digest) + (dependency closure of the stored parsed body, by default-deny allow-list and closure hash) + (behaviour, by vectors).

#### 2.2.4 Function digest — scope stated honestly

`ast1.function_definition_digest(p_rule_function_identity text) RETURNS char(64)` (bootstrap-owned, SECURITY INVOKER, `STABLE`, `SET search_path = pg_catalog`, §2.2.1a; reads `pg_catalog` only through `pg_catalog.`-qualified references, never writes) resolves the identity with `pg_catalog.to_regprocedure(p_rule_function_identity)` (a `NULL` result ⇒ the caller fails closed) and computes SHA-256 over a deterministic catalog representation of the **registered version-specific function**: `pg_catalog.pg_get_functiondef(oid)`, its schema-qualified identity/signature (name, argument types, return type), `provolatile`, `proisstrict`, `prosecdef`, `proparallel`, `prolang`, `proconfig` and the owner's role name. `original_definition_sha256` is **DB-computed** by the registration trigger and always **overwrites** any caller-supplied value; the caller cannot supply or override it. **Scope:** it freezes that one function's canonical PostgreSQL definition. Because registration inspects the **stored parsed body** and rejects any reference outside the approved immutable primitives (§2.2.3), *digest + dependency closure* together provide the **rule-definition freeze**. **Which digest an assertion compares after a major-version rebaseline is defined exactly in §2.2.10.** **The digest is NOT claimed to freeze PostgreSQL engine semantics across a major-version upgrade** (§2.2.10).

- **Immutability.** `trg_address_rule_version_immutable`, `trg_address_rule_vector_immutable`, `trg_address_rule_vector_requirement_immutable`, `trg_approved_primitive_immutable`, `trg_address_rule_rebaseline_immutable` and `trg_bootstrap_inventory_immutable` — `BEFORE UPDATE OR DELETE` (row) and `BEFORE TRUNCATE` (statement), bootstrap-owned, for **every** role including the migration identity and the table owner — raise `AS002`. A version can never be re-bound to a different function or digest, and no vector, requirement, primitive, rebaseline or inventory row can be edited or deleted; correcting a wrong vector is itself a new version.
- **Digest, closure, major version and owner are database-derived** (`trg_address_rule_version_register`, `BEFORE INSERT`): a caller-supplied `original_definition_sha256`, `dependency_closure_sha256`, `dependency_policy_version`, `registration_pg_major` or `registered_owner` is **overwritten**; registration is **refused** (`AS004`, `AST1_ADDRESS_RULE_FREEZE_VIOLATION`, reason `DEPENDENCY_POLICY` / `FUNCTION_PROPERTIES` / `IDENTITY_UNRESOLVED`) when §2.2.2–§2.2.3 fail or when `pg_catalog.to_regprocedure(rule_function_identity)` does not resolve, or its canonical rendering (`…::regprocedure::text`) is not exactly the stored text.
- **No durable `reg*` value [v1.8: F44(e)].** The registry identifies a rule function by `rule_function_identity text`, resolved at every use with `pg_catalog.to_regprocedure`; no AST-owned table has a `regproc`/`regprocedure`/`regclass`-style column (§2.2.13, T-ADR-32).

#### 2.2.6 Vector classes and the requirement table

The closed `vector_class` vocabulary: `CANONICAL_FIXED_POINT` (valid, canonical, fixed point), `VALID_NON_CANONICAL` (valid, rewritten to a canonical value — e.g. an `EVM_HEX40` mixed-case or `0X` spelling, accepted and lower-cased), `INVALID_LENGTH`, `INVALID_PREFIX_OR_FORM`, `INVALID_WHITESPACE`, `INVALID_CASE_OR_CHECKSUM`, `FORMAT_SPECIFIC_REJECTION` (e.g. for `TRON_BASE58CHECK`, the `41…` hex spelling, asserted **invalid**). The three structural cases are still non-contradictory: invalid `(false, NULL, NULL)`; valid non-canonical `(true, c, false)`; valid fixed point `(true, raw, true)` — the row-local `CHECK`s of §2.2.5 tie each class to its structure.

**Per-format required classes are machine-readable, not prose.** `address_rule_vector_requirement` carries, for every `address_format`, exactly one row per class in the vocabulary with `required = true` or `required = false` plus a mandatory `not_applicable_reason`. Applicability is encoded **here**: a format that admits exactly one spelling per identity (e.g. `BASE58_FIXED`) records `VALID_NON_CANONICAL` as `required = false` and is not forced to invent a nonsense vector. `CANONICAL_FIXED_POINT` and `INVALID_LENGTH` are a universal floor and can never be marked not applicable. The readiness trigger and the freeze assertion **mechanically** verify that (1) the format has a complete requirement row set (one row per class), and (2) the registered version has at least one vector of every class the format marks `required = true`.

#### 2.2.7 Readiness trigger — always, never conditional

`trg_network_registry_rule_ready` (bootstrap-owned, `BEFORE INSERT OR UPDATE` on `network_registry`; a composite FK to `address_rule_version` already enforces that the row exists). Whenever `network_registry` selects `(address_format, canonicalisation_version)` — on **every** insert and every update, **whether or not any instrument already references the pair** — it verifies that exact pair:

1. the `address_rule_version` row exists (FK) and `rule_function_identity` **resolves** through `pg_catalog.to_regprocedure(...)` (a `NULL` result — no such function — is refused, never assumed present);
2. the definition digest recomputed now, `IS NOT DISTINCT FROM` the **expected digest selected for the running PostgreSQL major** (§2.2.10: the original registration digest when the major equals `registration_pg_major`, else the exact-key rebaseline row's digest);
3. the dependency closure recomputes from the stored parsed body to the expected stored closure (same selection rule) and every referenced primitive is still approved for the running major (§2.2.3);
4. the format's requirement rows are complete and the pair holds every required vector class (§2.2.6);
5. **every** vector of the pair passes **directly** against `rule_function` (validity, canonical value, fixed-point flag);
6. **every** vector also gives the **identical** result through `ast1.canonicalise_address(...)` (dispatcher).

Any failure raises `AS004` (`AST1_ADDRESS_RULE_FREEZE_VIOLATION`) before the row is written. Changing the network's current version affects **future** registrations only (rule 20); it never touches an existing instrument's stored version. **SQL-feasibility test note (T-ADR-19a):** the invalid `CHECK … EXISTS (SELECT …)` and the table-reading-`CHECK` pattern are negative tests: PostgreSQL rejects the former outright and does not support the latter.

#### 2.2.8 The freeze assertion

```sql
ast1.assert_address_rules_frozen() RETURNS void      -- bootstrap-owned; SECURITY INVOKER; SET search_path = pg_catalog (§2.2.1a); VOLATILE; NULL-safe throughout
```
For **every registered** `(address_format, canonicalisation_version)` pair (a superset of "referenced" — an edit to a registered-but-unreferenced pair is caught too), in order; every comparison uses `IS DISTINCT FROM` so a `NULL` from a missing object is a mismatch, never an accidental pass:
0. **Platform, ownership, bootstrap-config and trigger-inventory sanity** (defence in depth, not the boundary, §2.2.1): **(a)** the running PostgreSQL major equals the pair's `registration_pg_major`, or **exactly one** `address_rule_rebaseline` row keyed `(address_format, canonicalisation_version, running major)` exists (§2.2.10; else `PG_MAJOR_UNREVIEWED`); **(b) bootstrap-config self-check [v1.8: F44(a)]** — every `FUNCTION` row of `ast1.bootstrap_inventory` exists with the bootstrap owner, the inventoried `prosecdef`, **exactly** `proconfig = {search_path=pg_catalog}` and no `PUBLIC` `EXECUTE` (otherwise `BOOTSTRAP_CONFIG_DRIFT`, fail closed); **(c) trigger inventory [v1.8: F44(d)]** — every `TRIGGER` row exists, calls its inventoried function and has its inventoried `tgenabled` (the enforcement triggers `trg_instrument_address_canonical`, `trg_instrument_address_final`, `trg_network_registry_rule_ready` and the immutability triggers are `'A'`, `ENABLE ALWAYS`), and `pg_trigger` for `ast1.instrument` and `ast1.network_registry` holds **no non-internal trigger outside the inventory** (`UNAPPROVED_TRIGGER`); **(d)** every bootstrap object has the bootstrap owner;
1. a matching `address_rule_version` row exists **and** the rule function **resolves**: `pg_catalog.to_regprocedure(rule_function_identity)` returns non-`NULL` and the resolved `pg_proc` row has signature `(text) → text`, `provolatile = 'i'`, owner = `registered_owner`, language `sql` and `NOT prosecdef`. A missing/dropped function makes `to_regprocedure` return `NULL` ⇒ **fails closed** with reason `RULE_FUNCTION_MISSING` — it is not left for a later step to fail accidentally. (No stored OID is used, so nothing dangles across restore or `pg_upgrade`; a `DROP` + re-`CREATE` under the same name resolves again by name and the new function is judged by step 2's digest, never assumed to be the old one.);
2. **digest [v1.8: F44(f)]:** `expected_digest := original_definition_sha256` when the running major = `registration_pg_major`, **otherwise** the `definition_sha256` of the one exact-key rebaseline row (§2.2.10); `expected_digest IS DISTINCT FROM ast1.function_definition_digest(rule_function_identity)` (recomputed now from catalog state) ⇒ fail (reason `DIGEST_MISMATCH`). No "latest rebaseline", no timestamp ordering;
3. **closure:** re-run the parsed-body inspection of §2.2.3 over the stored `prosqlbody`, recompute the closure, and compare `IS DISTINCT FROM` the expected closure (the registration's, or under the same selection rule the exact-key rebaseline row's `dependency_closure_sha256`) ⇒ fail (`DEPENDENCY_DRIFT`); every referenced primitive is still approved **for the running major** with unchanged owner and volatility; every `FROZEN_BOOTSTRAP` primitive's digest and every extension name/version still equals its recorded value;
4. the format's requirement rows are complete and every `required` vector class has ≥ 1 vector for the pair (`VECTOR_CLASS_MISSING`);
5. **every** vector is executed **directly** against the resolved rule function **and** through `ast1.canonicalise_address(address_format, canonicalisation_version, raw_input)`; each must reproduce `expected_valid` / `expected_canonical_value` / `expected_fixed_point`, and the direct result and the dispatcher result must be **exactly equal** — validity **and** canonical result (`IS DISTINCT FROM` ⇒ `DISPATCHER_MISROUTE`). **A dispatcher misroute is detected here only where the wrongly routed function differs from the registered one on at least one frozen vector; prevention rests on bootstrap ownership and the immutable routing architecture (rule 25; see the paragraph after this list);**
6. the dispatcher's definition is not silently different in behaviour: step 5 covers routing behaviour for every registered pair; the dispatcher's definition itself is bootstrap-owned and not replaceable by the migration identity;
7. **every** stored `ast1.instrument` row with that pair is a fixed point of the rule under its own version (validation of stored identities);
8. no collision exists among the instruments captured under the pair's rule set (the same check as sweep S9, run here as a migration gate).

Any failure `RAISE`s `AST1_ADDRESS_RULE_FREEZE_VIOLATION` (`AS004`) with the reason above, and the calling DDL/migration transaction **aborts** — nothing partially applies.

**Dispatcher routing — prevented, and detected only where a vector differs [v1.7: F41; precision v1.8: F44].** The dispatcher performs the generic registry lookup and invokes the registered function (no `CASE` table) through the exact pattern of §2.1. It is **prevented** from being re-routed by bootstrap ownership and the fixed generic architecture (the migration identity cannot `CREATE OR REPLACE` it). Step 5 **detects** a misroute **only where the wrongly routed function differs from the registered one on at least one frozen vector**; it cannot detect a misroute to a function that agrees with the registered one on every vector — for that case **prevention (ownership + immutable routing architecture) is the control, not detection** (§2.2.11). Because the dispatcher is no longer used in any `CHECK`, reading the registry is safe.

#### 2.2.9 Automatic DDL enforcement — one mechanism

**The one normative mechanism is a bootstrap-owned DDL event trigger.** (v1.6's optional migration-runner fallback and its "source-scans or manifests" wording are **withdrawn**: an author-maintained manifest moves "forgot to call" to "forgot to list".) Implementation: `role_ast1_bootstrap` creates two event triggers over one bootstrap-owned function, `ast1.freeze_ddl_guard()` — a `ddl_command_end` trigger and a `sql_drop` trigger (**[v1.8: F44 precision]** `ddl_command_end` **does** fire for `DROP` of the supported object types — round-8 probe P4 observed both `sql_drop` and `ddl_command_end` for `DROP FUNCTION` — and `sql_drop` is installed in addition because it exposes the dropped-object details through `pg_event_trigger_dropped_objects()`; they are complementary, not alternatives. On either, the dropped objects are already gone from the catalogs, so the assertion cannot resolve `rule_function_identity` and fails closed). It watches every DDL command that touches: the ast1 version-specific canonicaliser functions; the `canonicalise_address` dispatcher; `address_rule_version`, `address_rule_vector`, `address_rule_vector_requirement`, `address_rule_rebaseline`, `approved_primitive`; the `network_registry` canonicalisation columns; the `instrument` identity/canonicalisation columns and their enforcement triggers; any freeze-related migration-owned rule object; and any `ALTER … OWNER`, `ALTER TABLE … DISABLE/ENABLE TRIGGER`, `CREATE/ALTER/DROP EXTENSION` affecting those objects (identified through `pg_event_trigger_ddl_commands()` / `pg_event_trigger_dropped_objects()`; when in doubt the guard fails closed by running the assertion). On a relevant command it calls `ast1.assert_address_rules_frozen()` **inside the DDL transaction**; any violation aborts that transaction. It fires on the DDL itself, so **omitting a manual assertion call cannot bypass it**.

- **The migration identity cannot disable, drop, replace or alter** the event triggers or `ast1.freeze_ddl_guard()` (rules 25, 27; PostgreSQL restricts event-trigger creation and `ALTER EVENT TRIGGER` to superusers/owners; the trigger and its function are bootstrap-owned).
- **Deployment gate.** If the target deployment **cannot** install this event trigger because of platform privilege restrictions (e.g. a managed service that denies event triggers), **P1 implementation must STOP and return for a separately reviewed equivalent deployment gate.** It must **not** silently fall back to an author-maintained manifest or any other mechanism. This gate is **in addition to** `AST-P1-MIGRATION-IDENTITY-GATE` (§2.2.0): both must pass. Installing and proving this trigger (T-ADR-22) and the privilege model as the actual deployment migration identity (T-ADR-24) are **P1 acceptance criteria**, checked at implementation-review time and not asserted here as already built; today's `node-pg-migrate` harness has no post-migration hook (05 §12), and this pack does not claim otherwise.

#### 2.2.10 PostgreSQL major version and digest selection [v1.8: F44(f)]

The PostgreSQL **major version in force at registration** is pinned per registration (`registration_pg_major`, DB-derived). A PostgreSQL major-version change is a **governed platform migration**; the assertion **fails closed** (`PG_MAJOR_UNREVIEWED`) on an unreviewed major. **Which digest and closure an assertion compares is defined exactly, per `(address_format, canonicalisation_version)` [v1.8: F44(f)]:**

- **If the running major = `registration_pg_major`:** expected digest = the ORIGINAL registration's `original_definition_sha256`; expected closure = the registration's `dependency_closure_sha256`.
- **Otherwise:** require **exactly one** accepted, append-only `address_rule_rebaseline` row keyed by the exact triple `(address_format, canonicalisation_version, running major)`; expected digest / closure = **that row's DB-computed** `definition_sha256` / `dependency_closure_sha256`. Zero rows ⇒ `PG_MAJOR_UNREVIEWED`. A running major *lower* than the registration major is not a supported state and fails closed the same way.
- **No "latest rebaseline", no timestamp ordering, exact key only.** The historical original digest is never updated.
- **The caller cannot supply the rebaseline digest or closure.** A bootstrap-owned `BEFORE INSERT` trigger, `trg_address_rule_rebaseline_register`, **computes** `definition_sha256` and `dependency_closure_sha256` under the running engine (overwriting any supplied value), accepts a row only for the running major, re-runs the vector corpus, fixed-point and collision validation for the pair (so `vectors_verified`, `fixed_points_verified`, `collisions_verified` are database-derived, not attested by the inserter), and refuses the insert unless all pass.

The future upgrade task also inspects every function definition under the new engine and validates every stored instrument. **The digest is not claimed to freeze PostgreSQL engine behaviour**: engine, library and locale semantics across a major version are covered by the vectors, fixed-point and collision validation, not by the digest.

#### 2.2.11 What is actually proven — no stronger claim

The mechanism proves, and only proves: (1) the registered version-specific function's definition is unchanged from what was frozen (digest); (2) its **dependency closure**, computed from its **stored parsed body** (not from `pg_depend`), is exactly the approved immutable set recorded at registration (closure hash, per-major allow-list, frozen-primitive digests) — so the digest is not vacuous over hidden helpers; (3) the frozen, class-classified vector corpus reproduces exactly, **directly and through the dispatcher** (a misroute is detected only where the routed function differs from the registered one on at least one vector; otherwise routing is protected by ownership and the immutable architecture); (4) every stored identity remains a fixed point under its own version; (5) no collision has appeared; (6) all of the above is enforced by machinery the ordinary migration identity cannot replace (role separation, bound to the actual deployment migration identity by the P1 gate, §2.2.0) and triggered automatically on every relevant DDL; (7) the STORED final row of every address identity is re-validated by an `AFTER` backstop, so a later `BEFORE` trigger cannot leave a non-canonical value (§2.2.12). It does **not** prove semantic equivalence over inputs the vectors do not exercise except through (1)+(2) (an unchanged, self-contained function cannot change behaviour), and it does **not** freeze PostgreSQL engine semantics across a major upgrade (§2.2.10). Rule 20, rule 25 and INV-23 (01 §3.7) state the property in exactly these terms.

**Old-instrument updates are unaffected (unchanged from v1.4).** A retire, an identity lock, or a correction's fingerprint recompute validates against the instrument's **stored** rule version only; it does not re-read `network_registry` or re-derive the instrument's identity against the network's **current** state (`trg_instrument_address_canonical`'s `UPDATE` arm, §2.1). A network becoming `SUSPENDED`, or its `canonicalisation_version` being bumped, changes nothing about an existing instrument's validity.

#### 2.2.12 Final-row canonical validation and the trigger inventory [v1.8: F44(d)]

**Problem (round-8 probe P6).** `trg_instrument_address_canonical` validates in a `BEFORE INSERT` trigger. PostgreSQL fires same-event triggers in name order, and a later-named `BEFORE INSERT` (or `BEFORE UPDATE`) trigger can rewrite `NEW` **after** that validation ran; the stored value is then the rewritten, non-canonical one. A `BEFORE` trigger can never assume no later trigger will change `NEW`.

**Final-row backstop — `trg_instrument_address_final`.** The `BEFORE INSERT OR UPDATE` trigger `trg_instrument_address_canonical` is **kept** for rule resolution, format/version stamping and early validation (§2.1). **Added:** a bootstrap-owned `AFTER INSERT OR UPDATE` row **constraint trigger**, `DEFERRABLE INITIALLY IMMEDIATE`, created `ENABLE ALWAYS` (`tgenabled = 'A'`), `trg_instrument_address_final`. It fires after every `BEFORE` trigger has run and **re-reads the STORED final row** (`NEW` in an `AFTER` trigger is the stored tuple):
- **`INSERT`, `instrument_form = 'TOKEN_CONTRACT'`:** the stored `contract_address_canonical` must be non-`NULL` and **exactly the canonical fixed point** under the row's **own stored** `address_format` and `address_canonicalisation_version`: `ast1.canonicalise_address(NEW.address_format, NEW.address_canonicalisation_version, NEW.contract_address_canonical)` is not `NULL` and `IS NOT DISTINCT FROM NEW.contract_address_canonical`; the stored `(address_format, address_canonicalisation_version)` must equal the registered pair of `(chain, network)` and the network must be `ACTIVE` (the registration conditions, re-read after the `BEFORE` phase). Any violation ⇒ `AS005` (`AST1_ADDRESS_NOT_CANONICAL`) and the statement aborts.
- **`UPDATE`:** the five identity columns (`chain`, `network`, `contract_address_canonical`, `address_format`, `address_canonicalisation_version`) must be `IS NOT DISTINCT FROM` their `OLD` values, else `AS002`. A rogue `BEFORE UPDATE` trigger that rewrites `NEW` after `trg_instrument_immutable_from_insert` and the canonical trigger's `UPDATE` arm ran is therefore refused on the stored final row. The `UPDATE` arm never re-reads `network_registry` (the v1.4 independence is unchanged).

Identity columns remain immutable after insertion. **Reproduction (T-ADR-31):** early validation passes; a later-named `BEFORE INSERT` trigger rewrites `NEW.contract_address_canonical`; the `AFTER` backstop refuses the insert.

**Bootstrap-owned trigger inventory.** `ast1.bootstrap_inventory` rows of kind `TRIGGER` enumerate every approved non-internal trigger on `ast1.instrument` and `ast1.network_registry` (its name, the exact function it calls, its `tgenabled`). The DDL event triggers (§2.2.9) fire on `CREATE TRIGGER`, `DROP TRIGGER` and `ALTER TABLE … DISABLE/ENABLE TRIGGER` and run the assertion, whose step 0(c) refuses an **unapproved** trigger on either table (`UNAPPROVED_TRIGGER`), a missing or disabled inventoried trigger, and an inventoried trigger that calls a different function. Adding a legitimate later trigger on the identity tables is therefore a **bootstrap-procedure** action (a new inventory row, §2.2.0), never an ordinary migration side effect. **What this proves and what it does not:** the guard detects the migration identity (or a table owner) adding, dropping or disabling a trigger through DDL; it does not stop a superuser, and it does not prove that a *listed* trigger's function body is benign — that function is bootstrap-owned or covered by review and T-ADR-31. The `AFTER` backstop, not the inventory, is what makes the stored value canonical.

#### 2.2.13 `pg_upgrade` safety — no durable `reg*` values [v1.8: F44(e)]

`pg_upgrade` refuses a cluster whose user tables contain certain `reg*` column types (round-8 probe P7: the check lists `regprocedure`; the exact list is per PostgreSQL release). v1.7's `rule_function regprocedure` column would therefore have blocked the standard in-place upgrade path of the **whole platform database**. v1.8 stores **no** `reg*` value in any AST-owned table: the registry keeps `rule_function_identity text` (a schema-qualified signature such as `ast1.canonicalise_evm_hex40_v1(text)`), validated at registration (`pg_catalog.to_regprocedure(...)` resolves and its canonical rendering equals the stored text) and **re-resolved at every use** (dispatcher, digest helper, assertion, readiness trigger). **Historical authority** for a registered rule is the textual qualified signature + the definition digest + the dependency closure + the engine-major / rebaseline record — all text-, hash- or integer-valued and stable across dump/restore and `pg_upgrade`. An implementation may keep a same-cluster OID cache only if it is explicitly non-authoritative, regenerated after any restore or upgrade, never read *instead of* `to_regprocedure`, and never treated as historical identity. **P1 schema test (T-ADR-32):** a catalog query over the columns of every `ast1` table (`pg_attribute` ⨝ `pg_class` ⨝ `pg_namespace`, including domains and arrays whose base/element type is a `reg*` type) finds **zero** columns of type `regproc`, `regprocedure`, `regoper`, `regoperator`, `regclass`, `regcollation`, `regtype`, `regconfig`, `regdictionary`, `regnamespace` or `regrole` — deliberately broader than any one release's `pg_upgrade` list.

## 3. Lineage [v1.1: F06; v1.3: F27, F28.c]

```sql
ast1.lineage (                                  -- [v1.3: F28.c] INSERT-ONLY; no column is ever updated
  lineage_id uuid PK DEFAULT gen_random_uuid(),
  synthetic boolean NOT NULL,                   -- fixed at INSERT; a real and a synthetic lineage never merge; NO default, NO update route
  created_at_utc timestamptz NOT NULL           -- [v1.3] trigger-filled (clock_timestamp()); an application value is overwritten
);
```
**`lineage.synthetic` is immutable from `INSERT` [v1.3: F28.c].** `trg_lineage_immutable` is a `BEFORE UPDATE OR DELETE` (row) and `BEFORE TRUNCATE` (statement) trigger that raises `AS002` for **every** role — the runtime role, the migration role and the table owner (the same model as `deployment_environment`, §2; disabling or dropping the trigger is an out-of-band DBA action that the sweep's trigger inventory check detects, T-SCH-12). The runtime role holds `INSERT, SELECT` only, so no `UPDATE` route exists even before the trigger. **Source of the value (clarification; v1.2 did not state one):** `trg_asset_lineage_on_insert` sets it once — for `SAME_ECONOMIC_SUBJECT` from the predecessor root's `synthetic`, and for `NONE_DECLARED` from the create-asset request's explicit `lineage_synthetic` boolean (04 §2.1; required for `NONE_DECLARED`, and it must equal the predecessor root's value otherwise, else the asset insert is rejected). The instrument insert already requires `lineage.synthetic = instrument.declared_synthetic` (§4.2), so a wrongly flagged lineage can only ever fail closed (its instruments are rejected); it can never be flipped afterwards. **Real and synthetic histories therefore cannot be converted into one another by editing the lineage row, and the merge and underlying-link "same kind" rules (below, §4.3) rest on an immutable value.**

```sql
ast1.lineage_gate (                             -- [v1.3: F27] singleton; exists only to be locked (§7A level 0); never carries data
  singleton boolean PRIMARY KEY DEFAULT true CHECK (singleton),
  lock_token boolean NOT NULL DEFAULT true
);
```
Seeded with its one row by the migration. `trg_lineage_gate_immutable` raises `AS002` on any `UPDATE`, `DELETE` or `TRUNCATE` for every role; a row lock taken through `lock_lineage_gate_shared/exclusive` fires no such trigger, so the row is lockable but never changeable.

```sql
ast1.lineage_merge (                            -- append-only, irreversible; governed change (maker-checker)
  merge_id uuid PK, surviving_lineage_id uuid NOT NULL REFERENCES ast1.lineage,
  merged_lineage_id uuid NOT NULL REFERENCES ast1.lineage,
  change_id varchar(64) NOT NULL,
  merge_global_seq bigint NOT NULL UNIQUE,     -- [v1.3: F27] DB-assigned by trigger from ast1.classification_global_seq; NO caller-supplied value
  recorded_at_utc timestamptz NOT NULL,         -- [v1.3: F28.b] trigger-filled; audit only, never used for ordering
  CHECK (surviving_lineage_id <> merged_lineage_id),
  UNIQUE (merged_lineage_id)
);
```
`ast1.lineage_root(lineage_id)` follows merges to the root; **all lineage reads go through the root**, so a merge extends the history seen by every member — **in both directions**: the members of the surviving tree see the merged tree's history, and the members of the merged tree see the surviving tree's.

**`lineage_root()`'s contract [v1.4: F30.b].** It follows `merged_lineage_id → surviving_lineage_id` edges to a fixed point. It **raises** `AS004` (`AST1_LINEAGE_CYCLE`, the identity/lineage-invariant family that already covers "merge argument not a current root") — never returns `NULL`, an arbitrary lineage id or any other partial value — if it does not reach a fixed point within a bounded number of hops (a generous governed bound, illustratively 4096: merges are rare, governed, human-paced events, so a real lineage chain is always far shorter) or if it encounters an edge whose `surviving_lineage_id` does not itself resolve to a valid `lineage` row. Every caller of `lineage_root()` — the derivation, `authoritative_state()`, the resolver, the sweep, and `trg_lineage_merge_apply` itself — therefore either gets a definite, well-formed root or the whole calling statement fails closed; no caller can silently treat a corrupted or cyclic ancestry as "no merge history".

**[v1.2: F19.D] Lineage assignment is immutable from creation.** No role can `UPDATE` `asset.lineage_id`, `predecessor_declaration`, `predecessor_ref` or `predecessor_attested_by` (§4.1), and a merge does **not** update asset rows: it appends a `lineage_merge` row and `lineage_root()` follows it. The merge is the only governed lineage operation. There is **no un-merge and no loosening correction**: a wrongly *separate* lineage is fixed by a merge (tightening); a wrongly *merged* lineage is never split, and its members take the elevated path (fail-closed).

**`trg_lineage_merge_apply` [v1.3: F27; reordered v1.4: F30.b]** — `BEFORE INSERT` on `lineage_merge`. Its order is fixed, and it is what makes the sequencing rule non-optional even for a caller that skipped the application's own steps. **The gate is taken first, and every root/cycle/compatibility decision is made only after it is held** — a caller that skips the application's own locking (the exact case this trigger exists to cover) therefore never gets to make a security-relevant decision from a pre-gate, potentially stale read:

1. **Take the gate first:** `ast1.lock_lineage_gate_exclusive()` (§7A level 0). No decision below this line is made from a read taken before this lock.
2. **Only now, under the gate, resolve** both arguments to their **current** roots via `lineage_root(...)` (which itself fails closed on a cycle or malformed ancestry — above). A raw caller may have supplied original lineage/instrument references, not pre-resolved roots; resolution happens here, not before the gate. **[v1.5, editorial — F30.b residue]** `NEW.surviving_lineage_id` and `NEW.merged_lineage_id` are **overwritten to the resolved roots** before insert: the stored row records what was actually merged (the two trees' roots at the moment the gate was taken), not whatever non-root reference the caller may have originally named. This is what the reader needs to reconstruct history from `lineage_merge` alone, and it is what `UNIQUE (merged_lineage_id)` and the same-root refusal (step 3) actually operate on. The caller's original (possibly non-root) argument, if it differs, is preserved only in the governed change's payload, for audit of what was requested versus what was applied.
3. **Reject same root** (`AS004`): if both arguments resolve to one root — because they already are the same lineage, or because a concurrent merge (now committed and visible under this gate) already joined them — the insert is refused. This is what stops two opposite concurrent merges (`A→B` raw, `B→A` raw) from both committing: whichever commits second re-resolves under the gate to find both arguments already share a root, and is refused here, before it could form a cycle.
4. Require `lineage.synthetic` equal on both (now-resolved) roots (`AS004` otherwise).
5. Require the referenced `governed_change` (`change_id`) to be of kind `LINEAGE_MERGE`, `applied` **by this transaction** (the row's `xmin` is the current transaction id), targeting exactly these two roots (matched against the change's payload target identifiers, not the resolved roots, since the payload names what was approved).
6. **Lock the affected set:** `ast1.lock_merge_affected_instruments(surviving, merged)` — every instrument of both merge trees **and** every instrument whose transitive underlying chain reaches an instrument of either tree, locked ascending by `instrument_id` at mode `UPDATE` through `lock_instruments` (the application takes the same locks as its first statements; the trigger's re-lock skips ordering bookkeeping and changes no tracker state, but its physical row-lock requests are still issued and return immediately — [v1.8: F42]). The set is re-derived after the locks are held and the trigger raises `AS006` (`AST1_LOCK_SET_CHANGED`, retry) if it grew.
7. **Only now** assign `NEW.merge_global_seq := nextval('ast1.classification_global_seq')` and `NEW.recorded_at_utc := clock_timestamp()`. The value is never read from the caller; an application-supplied `merge_global_seq` is overwritten. Because steps 1–6 precede the draw and the gate is exclusive, two lineage-wide events (a real `SECURITY` record, a merge) are ordered by sequence in the same order in which they commit, and any classification writer is ordered against them by the gate (§7A).

The **narrowing** that follows the insert (identify affected instruments, revoke tokens, audit) is the merge apply transaction, §7A.

### 4.1 `asset`

```sql
ast1.asset (
  asset_id uuid PK DEFAULT gen_random_uuid(),
  asset_code varchar(16) NOT NULL UNIQUE CHECK (asset_code ~ '^[A-Z0-9]{2,16}$'),
  asset_name varchar(128) NOT NULL,
  asset_class varchar(24) NOT NULL CHECK (asset_class IN
     ('FIAT_CURRENCY','DIGITAL_CURRENCY','STABLECOIN','SECURITY','SECURITY_TOKEN','RWA_TOKEN',

  issuer_ref_id uuid REFERENCES ast1.issuer_reference,
  origin_jurisdiction char(2),
  lineage_id uuid NOT NULL REFERENCES ast1.lineage,                       -- [F06]
  predecessor_declaration varchar(24) NOT NULL
     CHECK (predecessor_declaration IN ('NONE_DECLARED','SAME_ECONOMIC_SUBJECT')),
  predecessor_ref varchar(64),                                            -- instrument/asset id when declared
  predecessor_attested_by varchar(64) NOT NULL,                           -- proposer attestation
  created_by varchar(64) NOT NULL, created_at_utc timestamptz NOT NULL DEFAULT now(),
  CHECK (predecessor_declaration <> 'SAME_ECONOMIC_SUBJECT' OR predecessor_ref IS NOT NULL)

```
Triggers **[v1.2: F19.D, F22]**:
- `trg_asset_lineage_immutable` — rejects `UPDATE` of `lineage_id`, `predecessor_declaration`, `predecessor_ref`, `predecessor_attested_by` in **every** status, for every role (`AS002`). This replaces v1.1's "frozen once an instrument locks", which left the fields editable while `DRAFT`.
- `trg_asset_lineage_on_insert` — `SAME_ECONOMIC_SUBJECT` forces `lineage_id` to the predecessor's lineage **root** at insert; `NONE_DECLARED` creates a new lineage.
- `trg_asset_class_frozen` **[F22; v1.3: F26, F28 note; v1.4: F29; v1.5: F33]** — `asset_class` may be updated only (a) while the asset has **no** instrument, or (b) inside the transaction that has just marked an `ASSET_CLASS_CORRECTION` governed change `applied` (the change row's `xmin` is the current transaction id) for exactly this asset and (from, to) — the correction path for a mislabelled class (AST-P-3; 01 §3.4). **Both branches first call `ast1.lock_asset(OLD.asset_id, UPDATE)` [v1.7: F38 — the helper, never raw SQL; rule 22] and only then evaluate "no instrument exists" / the correction preconditions** (§7A level 1). **[v1.7: F38; physical request v1.8: F42] On the protocol path this trigger call is an *idempotent re-lock*:** the application already took exactly this key at exactly this mode at step 2 of "Asset class correction apply", so the tracker shows it held; under rule 1 the trigger's call skips **every level check**, changes no tracker state, performs no downward-level check (level 1 after level 2 would otherwise look like a descent) and **does not raise `AS006` — but it still issues the `FOR UPDATE` request on the asset row, which PostgreSQL grants immediately because this transaction genuinely holds that lock** (the tracker is advisory ordering state, never proof of possession, §7A "The tracker is advisory"); the `lock_asset_instruments(...)` call that follows likewise skips ordering bookkeeping for the already-tracker-held instrument rows yet still issues the physical row-lock request for **every** instrument of the asset, which returns immediately (§7A "Re-lock sites"). On a raw writer path that took nothing first, the same calls are genuine new acquisitions at level 1 then level 2 in the total order. **[v1.5: F33] Branch (b) then itself calls `ast1.lock_asset_instruments(asset_id)`** — the same helper the application calls at its own step 3 (§7A "Asset class correction apply") — **before it evaluates any further correction precondition or permits the class change.** The helper enumerates **every** existing instrument of the asset (record-less ones included), treats any instrument the tracker already shows held at the required mode as an idempotent re-lock (ordering bookkeeping skipped, tracker untouched — rule 22/§7A — but the physical `FOR UPDATE` request is **still issued** and returns immediately when the application genuinely took these locks), and acquires every other one at `UPDATE`, ascending `instrument_id` (the row-lock SQL lives only inside the helper), all in one ascending pass. **This makes "every instrument is locked before the class changes" a property the trigger itself enforces, not an application convention a raw or defective writer could skip**: trigger 4's justification for its unlocked `asset_class` read (§5.1, below) now holds for **any** writer that reaches `UPDATE asset SET asset_class`, not only one that followed the documented protocol. **[v1.8: F42] That includes a writer that forged the advisory tracker**: the helper's row-lock requests are physical, so a forged claim that the asset and its instruments are already held still results in every instrument row being genuinely locked before the class changes (T-LOK-12, T-FPR-12). A correction (i) never crosses the FIAT boundary once an instrument exists (`FIAT_CURRENCY` ⇔ `instrument_form = 'FIAT'`), (ii) when it moves a class **out of** `SECURITY`/`SECURITY_TOKEN` needs ≥ 2 attested approvers (`COMPLIANCE_OFFICER` + `MLRO`), because it loosens, (iii) leaves `lineage_id` untouched (lineage preserved), and (iv) **[v1.3: F26]** in the same transaction (a) recomputes the cached `instrument.identity_fingerprint` of **every** instrument of the asset (the fingerprint's `underlying[]` component hashes link descriptors only — never the linked instrument's class or fingerprint — so the correction changes the fingerprints of the corrected asset's instruments and of no other) — the only permitted post-lock write to that column — (b) inserts one `class_correction_marker` per instrument that has a classification record (§5.3), and (c) revokes every outstanding token of those instruments (`asset_class_corrected`). The old records stay in the ledger unchanged but can no longer be used: SQL sees the mismatch (`record_fingerprint_matches = false`, rule **B12**, §7) and the TypeScript derivation collapses them (`CLASSIFICATION_REQUIRED_AFTER_CORRECTION`, 01 §4.4). A new governed classification is mandatory before any eligibility can return. The trigger refuses branch (b) unless the marker rows and the token revocation for every instrument of the asset are present at the end of the transaction (a deferred constraint trigger, so the writer's statement order is free but the outcome is not optional). **[v1.4: F29]** That deferred constraint additionally requires, for every instrument of the asset that has a current record: `instrument.identity_fingerprint <> that record's superseded_record_fingerprint` (the correction's fingerprint write actually took effect — a writer that left the cached value unchanged cannot commit); `instrument.identity_fingerprint = ` the `class_correction_marker` row's `new_instrument_fingerprint` (the marker chains to what was actually written, not to some other value); and `class_correction_marker.asset_id = instrument.asset_id` for every marker the transaction wrote (a marker can never be attributed to the wrong asset). **[v1.6: F39(a) — scoped]** For an ordinary single-hop class change, this assertion is a **correctness backstop on the writer**, not the security control — B12 (§7, below) denies independently of it, by comparing the record's stored `asset_class_at_record` with the asset's **live** `asset_class`, which the correction is defined to change whether or not the fingerprint recompute is implemented correctly. **For round-trip revival prevention specifically, the deferred constraint IS additionally security-critical** (below): the live class-binding half of B12 is satisfied again the moment a round trip returns the class label to its original value, so for that one case the fingerprint-based deferred constraint is the only thing still denying.
- **[v1.5: F33] First-classification race, adjudicated.** With branch (b) locking every instrument of the asset — including a record-less one — before the class changes, the race the round-5 review found (`04-review-r5.md` §7) is closed at the lock, not by hoping the two statements interleave safely. For a record-less instrument X and a concurrent (correction C, first classification W of X), whichever of C's `lock_asset_instruments` call and W's `lock_instrument(X)` call (record-insert trigger 2) reaches X's row lock first is strictly ordered before the other by PostgreSQL's row-lock queue. **Either** (A) W locks X first: W's record commits under the **old** class (trigger 4 stamps the pre-correction `asset_class_at_record`); C then locks X, sees the committed record under its own locks, and its deferred constraint (above) covers X; once C commits, B12's `class_binding_matches` denies W's record, exactly as F29 intends. **Or** (B) C locks X first (and every other instrument of the asset) and commits: W's `lock_instrument(X)` then waits, and once granted, W's fresh `READ COMMITTED` read of `asset.asset_class` (trigger 4) sees the **corrected** class, so trigger 6 (`SECURITY_LABELLED`) evaluates against the new class and a `NON_SECURITY` proposal into a `SECURITY`-labelled class is refused. **Neither interleaving produces a `NON_SECURITY` record stamped with a `SECURITY`/`SECURITY_TOKEN` `asset_class_at_record`** — the specific outcome F29's property is required to survive — because X's row lock admits exactly one holder at a time and both writers take it before doing anything else that matters to this decision.
- **[v1.5: F33; invariant restated v1.6: F39(a)] Round-trip correction (`A → B → A`), stated.** A correction back to a class an asset previously held, with **no** intervening classification, recomputes each affected instrument's `identity_fingerprint` back to its pre-`A→B` value (the fingerprint depends on `asset_class` among other fields). **SQL invariant:** after every committed `ASSET_CLASS_CORRECTION`, each instrument whose current record predates the correction remains fingerprint-**incompatible** with that current record — the deferred constraint (`identity_fingerprint <> superseded_record_fingerprint`) refuses **any** commit, including a second correction's, that would make the stale record's fingerprint match again. For the round trip specifically, this is not merely a writer-correctness backstop: it is what denies after the live class-binding half of B12 (§7) has already gone back to matching (class `A` again = the stale record's stamped class `A`), so **for round-trip revival prevention the deferred fingerprint constraint is the security control**, not a supporting one. This is fail-closed and intended: an old record does **not** become usable again merely because the live class label has returned to its original value — the fingerprint check, the marker chain (§5.3), lineage/security history (§4.7A) and the current-record requirements of §5.1/§7 are all still evaluated exactly as for any other state. **[v1.6: F39(a)]** The live `asset_class` binding remains independently sufficient for an ordinary single-hop class change (where no revival question arises); it is the round-trip case specifically that needs the deferred fingerprint half, and none of this is satisfied by "the class matches again" alone. The operator route for a genuine `A → B → A` correction is the one T-FPR-05 already exercises for `A → B → C`: record an `UNRESOLVED` (or otherwise superseding) outcome between the two correction hops, so the second correction's deferred constraint has an actually-changed fingerprint to compare against — **for every instrument that is `IDENTITY_LOCKED`**. **[v1.8 editorial: `RETIRED` members] That route does not exist for a `RETIRED` instrument that has a current record.** Classification-record insertion requires `IDENTITY_LOCKED` (rule 24, §5.1 step 2A), so no intermediate `UNRESOLVED` (or any other superseding) record can be appended to a retired instrument, and `ASSET_CLASS_CORRECTION` **does not attempt to restore a retired instrument's eligibility through a new classification**. B6 already denies `RETIRED` on every subject, and the deferred fingerprint rule keeps preventing stale-record revival. If a round-trip correction would return a retired member's `identity_fingerprint` to the value of its stale current record, the second hop's deferred constraint refuses the commit — **fail-closed, and permanently so for that asset** — and such a case requires a separate governed asset/instrument replacement strategy, which this blueprint neither designs nor implies (no new state, action or classification path is introduced here). Where any ambiguity would otherwise arise, the design fails closed rather than silently reviving a pre-correction record.
- **Race with the first instrument insert [v1.3; review §13 note].** The FK from `instrument.asset_id` to `asset` takes only `FOR KEY SHARE`, which does **not** conflict with the `UPDATE` of a non-key column, so the FK alone would let "no instrument exists" (branch a) race a concurrent first insert. `trg_instrument_asset_lock` (§4.2) therefore calls `ast1.lock_asset(NEW.asset_id, SHARE)` before an instrument is inserted, and every asset-class writer calls `ast1.lock_asset(asset_id, UPDATE)` on the same row before it decides. `SHARE` and `UPDATE` (PostgreSQL `FOR SHARE` / `FOR UPDATE`, taken inside the helper) conflict, so exactly one order occurs: the class writer first (the insert then waits, and sees the final class and form rule), or the insert first (the class writer then waits, then sees an instrument and refuses branch a / takes the correction path). No class/form interleaving is possible, so it does not need a later control to deny it.
- `issuer_ref_id` is frozen once any instrument of the asset is `IDENTITY_LOCKED`.

### 4.2 `instrument`

```sql
ast1.instrument (
  instrument_id uuid PK DEFAULT gen_random_uuid(),
  instrument_code varchar(48) NOT NULL UNIQUE CHECK (instrument_code ~ '^[A-Z0-9][A-Z0-9._:-]{1,47}$'),
  asset_id uuid NOT NULL REFERENCES ast1.asset,
```

`asset_code` is **not** an identity key: several instruments (contracts) may share an asset and network. It is a label used only as an optional consistency assertion (04 §6.1). `network_registry` holds one row per real network; aliasing one network under two keys would defeat native-identity uniqueness and is a registry-content error, not a supported state.

**A canonical identity is registered exactly once, ever.** A retired, abandoned-draft, or replaced instrument keeps its identity permanently; a second instrument with the same identity is rejected by the index (`AST1_INSTRUMENT_DUPLICATE_IDENTITY`, `AS004`). There is no retire-and-recreate on the same contract or native identity, and no continuity trigger for it (v1.1's `trg_instrument_on_chain_continuity` is **removed**: it could never fire). A replacement contract has a **new** address and enters through a declared predecessor or the asset's lineage (01 §3.9). A real and a synthetic instrument can never share an identity either: the second registration collides.

Triggers **[v1.2: F19.B, F19.D; consolidated v1.7: F40]**:
- `trg_underlying_immutable` — `BEFORE UPDATE OR DELETE` (row) and `BEFORE TRUNCATE` (statement) on `instrument_underlying`: `AS002` for every role (no `UPDATE`, no `DELETE` grant). The instrument-to-instrument link feeds `elevated` and the lineage conjunct, so it cannot be edited away.
- **`trg_underlying_insert_guard` [v1.7: F40, new — the one authoritative ordered `BEFORE INSERT` trigger function, replacing v1.6's separately-firing `trg_underlying_insert_only`, `trg_underlying_target_locked`, `trg_underlying_no_cycle` and `trg_underlying_same_kind`].** PostgreSQL does not guarantee the firing order of separate triggers on one event, and a correctness-bearing order must not depend on trigger names, so these checks are **steps of one function**, in this order (T-LIN-36…):
  1. **First security-relevant action — lock through the governed helper (F40.1).** For `underlying_type = 'INSTRUMENT'`: `ast1.lock_instruments({NEW.instrument_id, NEW.underlying_instrument_id}, UPDATE)` — the general helper (§7A "Lock helper family"): it asserts `READ COMMITTED` (`AS007`) as its literal first operation, deduplicates, sorts the ids **ascending**, partitions them into ids the advisory tracker shows held at `UPDATE` or stronger (ordering bookkeeping skipped) and new ids (level-2 ascending guard applied), **physically acquires every requested id `FOR UPDATE` ascending** (a tracker-held id returns immediately when genuinely held), and updates the tracker for the new ids only. **When the application already locked both endpoints** (the protocol path, §7A "Underlying link insert") the trigger's request is an idempotent re-lock: **no wait, no new conflicting lock, no tracker change, zero false `AS006`** — the physical request itself still executes (rule 22, PHYSICAL-LOCK-ALWAYS). For any **other** `underlying_type` (`COMMODITY`, `FIAT_CURRENCY`, …) the trigger calls `ast1.lock_instrument(NEW.instrument_id, UPDATE)` — the source-`DRAFT` rule applies to every underlying row, so the source must be locked before its status is read on every path. An endpoint id that does not exist is refused (`AS004`) rather than skipped, so no unlocked path remains for a not-yet-visible row.
  2. **Only after the locks are held**, read (fresh `READ COMMITTED` statements): source `lifecycle_status`, target `lifecycle_status`, source/target synthetic kind, lineage/basis compatibility, the cycle/depth condition and the other immutable-link constraints.
  3. **Source rule (unchanged in substance, now under the source's own SQL-taken lock):** `source.lifecycle_status = 'DRAFT'`, else refuse with the `AST1_INSTRUMENT_IMMUTABLE_FIELD`-family error (`AS004`).
  4. **Target rule (F37, now under the target's own SQL-taken lock):** `target.lifecycle_status IN ('IDENTITY_LOCKED','RETIRED')`; the target must **not** be `DRAFT`, else `AST1_UNDERLYING_TARGET_NOT_LOCKED` (`AS004`).
  5. Same-kind: a synthetic instrument may link only a synthetic underlying instrument and a real one only a real one (`AST1_UNDERLYING_CYCLE` family, `AS004`).
  6. Cycle / depth: reject a link that closes a cycle or any chain deeper than 8 (`AST1_UNDERLYING_CYCLE`). Structurally redundant after step 4 (§4.3 proof) but kept.
  **This is SQL-enforced, not protocol-dependent.** A raw `INSERT` that bypasses the application protocol still locks both endpoints first, in the module's one ascending order, so it is serialised against a concurrent identity lock of either endpoint (T-LIN-36, T-LIN-37) and cannot form a lock cycle with any other writer (T-LIN-40). **[v1.8: F42] Not even a forged tracker changes this:** the trigger's helper call always issues the row-lock request for both endpoints, so a session that used `set_config` to claim both endpoints held — while holding neither — still physically acquires both (T-LOK-12, T-LIN-42); at worst the forged claim turns the insert into an ordinary PostgreSQL lock wait or deadlock, which PostgreSQL aborts fail-closed.
- **FK checks are subsumed implicit locks [v1.7: F40.2].** Because the trigger has already locked **both** endpoint instrument rows strongly (mode `UPDATE`, through `lock_instruments`), the two FK `KEY SHARE` checks that follow during the `INSERT` (`instrument_id`, `underlying_instrument_id` → `ast1.instrument`) are against rows this transaction already holds at a **stronger** mode: they are implicit locks *subsumed* by the helper-taken locks (§7A "Tracker scope", case A), they wait on no one and create no edge another transaction can wait on. **No unordered raw-link FK acquisition remains in the supported/runtime role;** v1.6's "raw link insert — unordered FK `KEY SHARE`, deadlock-abort, not stated" path is closed.

**Why this closes F37 — and, after F40, without depending on application discipline [v1.7: F40.4].** The recursive claim needs exactly three premises, each now **enforced by SQL under a lock the trigger itself takes**:
- **(P1) "An underlying link can only be added while its source is `DRAFT`"** — `trg_underlying_insert_guard` step 3, evaluated after `lock_instruments`, i.e. serialised with the source's identity-lock `UPDATE` (which takes `lock_instrument(source, UPDATE)` via `trg_instrument_lock_on_write`). Either the identity lock commits first — the link then reads `IDENTITY_LOCKED` and is refused — or the link's locks come first — the link commits while the source is genuinely `DRAFT`, and the later identity lock sees a frozen link set.
- **(P2) "An instrument used as an underlying target is already non-`DRAFT`"** — step 4, under the target's lock. `DRAFT → non-DRAFT` is monotone (SM-1: nothing returns to `DRAFT`), so a non-`DRAFT` read is permanent.
- **(P3) "A classified instrument is non-`DRAFT`"** — rule 24: the record trigger refuses any record unless `lifecycle_status = 'IDENTITY_LOCKED'` (§5.1 step 2A).

*Recursive basis-tree proof.* Claim: for every instrument Y that is non-`DRAFT` at time *t*, the set reachable from Y through `instrument_underlying` is fixed forever after *t*. By induction on link-insert order: (1) Y's own out-links are frozen once Y is non-`DRAFT` (P1) and Y never returns to `DRAFT` (SM-1); (2) every direct target T of Y was non-`DRAFT` when its link was inserted (P2) and is non-`DRAFT` at every later time; (3) by the induction hypothesis T's reachable set was fixed at that insert; (4) hence Y's reachable set is a union of fixed sets over a fixed out-link set. ∎ Since a record exists only for a non-`DRAFT` instrument (P3), the basis tree of any *classified* instrument is fixed at or before its classification (aside from lineage merges, which change merge-tree roots, not the link graph, and are gate-serialised, clause (b), F27). The proof therefore depends on **SQL-enforced** premises P1–P3 and on **no** application step, on the protocol path or a raw path, **with the integrity sweep disabled** (T-LIN-41) — **and on the actual PostgreSQL row locks the trigger takes, not on the advisory tracker: it holds for a raw writer that forges the tracker too (F42; T-LIN-42).** Concretely, for the F37 sequence (X links to U while both `DRAFT`, X classifies `NON_SECURITY`, U later — while still `DRAFT` — links to older-`SECURITY` V): X's link to U is refused unless U is already non-`DRAFT` (P2), and U cannot then add V (P1); and X cannot classify while `DRAFT` (P3).

Triggers on INSERT (all read authoritative rows; none trusts the supplied values). **[v1.5: F33] Steps 2–8 below are one ordered `BEFORE INSERT` trigger function, not several independently-firing trigger objects** — PostgreSQL does not guarantee the firing order of separate triggers on one event (it is alphabetical by trigger name, which the design must not rely on for a correctness-bearing order), so a step that must see another step's result reads it from `NEW`, set within this same function, never from a second independent read:
1. Reject UPDATE/DELETE/TRUNCATE.
2. **Locks [v1.2: F18, F20; v1.3: F27, F28.b; reordered v1.4: F31].** In the order of §7A: (a) `ast1.lock_lineage_gate_shared()` — or `ast1.lock_lineage_gate_exclusive()` for a **real** instrument and `outcome = SECURITY_OR_SECURITY_TOKEN`; (b) for the **shared**-gate case (every non-`SECURITY`, non-elevated-apply record) simply `ast1.lock_instrument(instrument_id, UPDATE)` — no wider set exists to lock. (c) For the **exclusive**-gate case (a real `SECURITY` record), **the instrument is never locked on its own first**: under the gate, `ast1.lock_affected_instruments(instrument_id)` first **derives** the full affected set — the instrument itself, plus every instrument of its lineage merge tree, plus every instrument whose transitive underlying chain reaches that tree — entirely from `asset`/`instrument_underlying` rows read under the gate — **[v1.6: F37 — corrected; supersedes the v1.5 editorial reasoning]** stable not because the gate blocks *every* new instrument or underlying link (it does not: an instrument insert takes only the asset row, `lock_asset(…, SHARE)`), and **not** because "any newcomer is necessarily record-less" (that v1.5 claim was false: a **classified** wrapper could previously become a newcomer to a tree through a late `DRAFT` underlying link on an intermediate instrument, F37). Stability now rests on §4.3's SQL-enforced `trg_underlying_insert_guard` (**[v1.7: F40]** it locks both endpoints itself before it reads either lifecycle status, on every path): for a classified (non-`DRAFT`) instrument, its own underlying set is frozen (the source rule), and every instrument it targets was already non-`DRAFT` when linked (the new target rule), so each target's own underlying set was therefore already frozen when the link was added. Recursively, the transitive underlying graph reachable from any instrument is immutable **except through a lineage merge** — and a merge is gate-serialised and already covered by clause (b) below (F27). Therefore `B(X)` for a classified/non-`DRAFT` X cannot grow from a late link after X's classification; the set the trigger derives here is stable for the ordinary reason (every underlying reachable from an identity-locked tree is itself already `IDENTITY_LOCKED` or `RETIRED` — a **lifecycle state**, not a PostgreSQL row lock [v1.7 editorial]), not the discredited "record-less newcomer" reasoning. The set is still unconditionally **re-derived once every lock is held**, raising `AS006` if it somehow grew (defence in depth); no instrument lock is needed to read the rows this derivation reads — and only then locks the **whole set, including the instrument itself, ascending `instrument_id` in one pass through `ast1.lock_instruments(set, UPDATE)` (the helper performs the ordered acquisition; the trigger issues no raw `… FOR UPDATE`)**, re-derived after the locks are held (`AS006` if the set grew). This is what makes the pairing with `ASSET_CLASS_CORRECTION` and evidence-standard retirement — which also lock an asset's/tree's instruments purely ascending — free of the lock-order inversion a self-first acquisition would otherwise create (§7A cycle analysis). All of this precedes anything read below. The application's apply transaction takes the same locks as its first statements; the trigger makes the rule non-optional (§7A).
2A. **[v1.7: F40, new — the DRAFT-classification invariant, rule 24]** Immediately **after** the instrument row lock of step 2 is held (for the exclusive-gate case: after the whole affected set, the instrument included, is locked) and **before** any classification semantics below is evaluated, read the instrument's `lifecycle_status` (a fresh `READ COMMITTED` statement under the lock) and **refuse unless it is `IDENTITY_LOCKED`** — `AST1_INSTRUMENT_NOT_IDENTITY_LOCKED` (`AS004`, 422; reason `DRAFT` or `RETIRED`). **Valid lifecycle for a *new* classification record: `IDENTITY_LOCKED` only.** `DRAFT` is refused (no identity lock has occurred, so no case could legitimately exist; case submit identity-locks first, 06 SM-1). `RETIRED` is **not** newly classifiable: the existing semantics are that retirement is terminal and every subject denies (`INSTRUMENT_RETIRED`, 06 SM-1, B6), and this blueprint defines no governed historical-classification action for a retired instrument — v1.7 makes that existing policy SQL-visible and **does not change it**. (A record that was appended while the instrument was `IDENTITY_LOCKED` legitimately remains in the ledger after a later retirement.) Because SM-1 forbids any return to `DRAFT`, the result is the database invariant **"a classified instrument is non-`DRAFT`"** (§4.3 premise P3). This check adds no lock and no lock-order edge: the row is already held.

### 5.2 `instrument_hold` — a narrowing conjunct, not an outcome [F07]

```sql
ast1.instrument_hold (
  hold_id uuid PK, instrument_id uuid NOT NULL REFERENCES ast1.instrument,
  hold_origin varchar(8) NOT NULL CHECK (hold_origin IN ('SYSTEM','HUMAN')),
  reason_code varchar(48) NOT NULL, detail text,
  placed_by varchar(64) NOT NULL, placed_change_id varchar(64),
  placed_at_utc timestamptz NOT NULL DEFAULT now(),
  status varchar(10) NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','RELEASED')),
  release_change_id varchar(64), released_at_utc timestamptz,
  CHECK (hold_origin = 'SYSTEM' OR placed_change_id IS NOT NULL),          -- a HUMAN hold requires an approved governed change
  CHECK (hold_origin = 'HUMAN' OR placed_by = 'system'),
  CHECK (status = 'ACTIVE' OR release_change_id IS NOT NULL)                -- release is always governed
);
```
A hold writes **no** `classification_record`. `SYSTEM` holds are inserted by the integrity sweep/derivation guard, or by the application in a **separate controlled transaction after it catches a backstop error** (§7) — never by the raising trigger itself, because a raise rolls back everything the trigger did, including a hold insert. `SYSTEM` holds are inserted with no human approval.

**[v1.2: F24]** `instrument_hold`'s key columns (`instrument_id`, `hold_origin`, `reason_code`, `placed_by`, `placed_change_id`, `placed_at_utc`) are immutable from insert; only `status` (`ACTIVE → RELEASED` once), `release_change_id`, `released_at_utc` change. Hold insert and release call `ast1.lock_instrument()` first (§7A).

A hold is **not** the mechanism for lineage-linked security history: that is a **derived conjunct** (§7, `lineage_review_required`; 01 §4.7A), so it needs no rows, cannot be forgotten and takes effect at the commit of the triggering record.

### 5.3 `class_correction_marker` — an explained fingerprint change [v1.3: F26]

A governed `ASSET_CLASS_CORRECTION` changes every instrument's cached `identity_fingerprint` **on purpose**. SQL rule B12 must deny on the resulting mismatch (§7), and the derivation and the sweep must be able to tell this **expected, governed** state from an **unexplained** drift, without a `SYSTEM` hold and without calling the correction an integrity attack. The distinction is data, not judgement:

```sql
ast1.class_correction_marker (                     -- INSERT-ONLY; written only by the correction transaction
  marker_id uuid PK DEFAULT gen_random_uuid(),
  instrument_id uuid NOT NULL REFERENCES ast1.instrument,
  asset_id uuid NOT NULL REFERENCES ast1.asset,
  change_id varchar(64) NOT NULL REFERENCES ast1.governed_change (change_id),   -- the GOVERNING change reference
  from_class varchar(24) NOT NULL, to_class varchar(24) NOT NULL,
  superseded_record_id uuid NOT NULL REFERENCES ast1.classification_record,     -- the instrument's current record at correction time
  superseded_record_fingerprint char(64) NOT NULL,                              -- that record's identity_fingerprint
  new_instrument_fingerprint char(64) NOT NULL,                                 -- the instrument's cached fingerprint after the correction
  marker_global_seq bigint NOT NULL UNIQUE,                                     -- from ast1.classification_global_seq, after the locks
  recorded_at_utc timestamptz NOT NULL,                                         -- trigger-filled; audit only
  CHECK (from_class <> to_class),
  UNIQUE (instrument_id, change_id)
);
```
- **Explained drift** ≡ ∃ a marker *m* for the instrument with `m.superseded_record_fingerprint = current record's identity_fingerprint` **and** `m.new_instrument_fingerprint = the instrument's current identity_fingerprint`, whose `change_id` is an `applied` governed change of kind `ASSET_CLASS_CORRECTION` targeting the marker's asset with payload (`from_class`, `to_class`). This is exposed by `authoritative_state()` as `drift_explained_by_correction` (§7) and mirrored by the TypeScript derivation. Two corrections in a row without a reclassification each add a marker whose `superseded_record_*` is still the same current record, so the newest marker explains the newest fingerprint.
- **Unexplained drift** ≡ `record_fingerprint_matches = false` and no such marker. It keeps the v1.2 behaviour: `CLASSIFICATION_IDENTITY_DRIFT`, a `SYSTEM` hold, the critical `ast1.instrument.identity_drift_detected`.
- **A marker never permits anything.** B12 denies in both cases; the marker only selects the reason code (`CLASSIFICATION_REQUIRED_AFTER_CORRECTION` versus `CLASSIFICATION_IDENTITY_DRIFT`), the audit event and whether the sweep places a hold. A forged marker can therefore mislabel a tamper but cannot make anything eligible; the sweep verifies each marker's governing change (§7 sweep rules) and treats a marker whose change does not verify as **no** marker.
- **A marker stops explaining anything once the instrument receives a new record** whose `identity_fingerprint` equals the instrument's current fingerprint (`record_fingerprint_matches` becomes true). Markers remain as history.
- Written only by `trg_asset_class_frozen` branch (b)'s transaction (the insert trigger checks the change is `applied` by the current transaction for this asset and (from, to), and that `superseded_record_id` is the instrument's newest record). `INSERT, SELECT` grants only.
- **[v1.5: F35.c] One sequence source, stated once.** `marker_global_seq` is drawn from **`ast1.classification_global_seq`** — the **same shared** sequence as `classification_record.global_seq`, `lineage_merge.merge_global_seq` and `classification_evidence.evidence_global_seq` (§1 rule 12) — after the locks of §7A, never a sequence of its own. (`securities_market_admission_attestation.attestation_seq`, §6, remains its own dedicated sequence: that domain is unrelated to classification/lineage ordering, §1 rule 20.) `marker_global_seq` belonging to the shared domain does **not** by itself give it the commit-order guarantee for an arbitrary pair: that guarantee (§7A "Scope of the ordering guarantee") holds only for a pair serialised by a shared instrument lock or the exclusive gate. The one comparison this pack makes — "the newest marker explains the newest fingerprint" (above) — is always between two markers **of the same instrument**, drawn under that instrument's lock throughout the correction transaction, so clause (i) of the scope statement already covers it. A marker's sequence is never compared against a different instrument's event or against a gate-serialised event for a security decision.

## 7. The authoritative SQL backstop [v1.1: F04; v1.2: F18, F19, F20, F21, F23, F25; v1.3: F26, F27; v1.4: F29, F30]

v1.0 CHECKed `effective_outcome` etc. on the row being inserted — values written by the very code being guarded. v1.1 replaced that with a SQL function that **reads the ledger**. v1.2 keeps that design and extends the same function (a) to **token consumption**, not only mint, and (b) to the lineage, MYR, service-identity and real-instrument-basis conditions. **v1.3** (c) redefines the lineage condition so a **lineage merge** narrows exactly as a newer `SECURITY` record does (F27), and (d) adds the **record-to-instrument fingerprint comparison** and rule **B12**, so `ASSET_CLASS_CORRECTION` is visible to SQL (F26). **v1.4** (e) adds a **second, independent** input to B12 — the record's asset class at write time compared with the asset's live class — so B12 no longer depends on the correction writer having recomputed the cached fingerprint correctly (F29), and (f) makes the isolation level the whole function's safety rests on an asserted, fail-closed precondition rather than a documented assumption (F30.a).

```sql
ast1.authoritative_state(p_instrument_id uuid) RETURNS TABLE (
  instrument_form, declared_synthetic, synthetic_emulates, lifecycle_status,
  current_record_id, current_record_seq, current_global_seq, latest_outcome,   -- newest record only
  record_env_matches boolean, on_hold boolean, canonical_environment,
  standard_production_applicable boolean,   -- [F25] the newest record's standard is APPROVED and PRODUCTION-applicable
  record_fingerprint_matches boolean,       -- [v1.3: F26] newest record's identity_fingerprint = instrument.identity_fingerprint; see below
  class_binding_matches boolean,            -- [v1.4: F29] newest record's asset_class_at_record = the asset's LIVE asset_class, independent of the cached fingerprint; see below
  drift_explained_by_correction boolean,    -- [v1.3: F26] a verified class_correction_marker explains the mismatch (§5.3); label only, never a permission
  lineage_review_required boolean,          -- [F20; v1.3: F27] see below
  attr_myr_denominated boolean)             -- [F21]
```
**[v1.4: F30.a] Isolation precondition, asserted first.** Every one of the properties below — including the ordinary "current record" read — is a security guarantee only if this session runs `READ COMMITTED`, because a `REPEATABLE READ`/`SERIALIZABLE` snapshot taken before a concurrent writer's commit would let this function see a state older than what the lock protocol has already serialised against. Accordingly, `authoritative_state()`'s **first statement**, before any lock or read below, is `IF current_setting('transaction_isolation') <> 'read committed' THEN RAISE EXCEPTION … SQLSTATE 'AS007'; END IF` (`AST1_UNSUPPORTED_TX_ISOLATION`). v1.4 supports `READ COMMITTED` only; a session or pool that defaults to a stronger level fails every mint, consume, classification apply, evidence insert, lineage merge and `ASSET_CLASS_CORRECTION` closed, rather than silently running with a weaker guarantee than the design claims. The same assertion is the **literal first operation of every lock helper** — the complete family of §7A "Lock helper family": `lock_governed_change`, `lock_lineage_gate_shared`, `lock_lineage_gate_exclusive`, `lock_asset`, `lock_instrument`, `lock_instruments`, `lock_affected_instruments`, `lock_merge_affected_instruments`, `lock_asset_instruments`, `lock_token`, `lock_tokens`, `lock_instrument_tokens` **[v1.7: F38 — list made complete; T-ISO-04 tests exactly this list]** — so a caller that reaches SQL through any path is covered, not only through `authoritative_state()`. A helper added later must be added to that list and to T-ISO-04, or the static scan T-LOK-07(m) fails. This is a connection/pool-configuration requirement: the runtime pool must not set a session default above `READ COMMITTED` for any AST-01 connection.

It then calls **`ast1.lock_instrument(p_instrument_id, SHARE)`** [v1.7: F38 — the helper, not raw SQL] (inside a transaction that already holds the row at `SHARE` or `UPDATE`, rule 1/2 of §7A skips ordering bookkeeping and the physical `FOR SHARE` request returns immediately against the writer's own lock — it is still issued [v1.8: F42]; a request that would need a stronger mode than a held one never arises here because `SHARE` is the weakest), then reads `ast1.instrument`, `ast1.asset` (for the **live** `asset_class`, F29), `ast1.classification_record` (max `record_seq`), `ast1.evidence_standard`, `ast1.instrument_hold`, `ast1.deployment_environment` and the lineage tables. It contains **no** matrix, only the minimum needed to decide the forbidden set. **[v1.3, review §7 implementation note]** `authoritative_state()`, `backstop_permits()`, `assert_token_consumable()` and every trigger function that takes a row lock must be declared `VOLATILE` (PostgreSQL rejects `FOR SHARE/UPDATE` in non-volatile functions, and under `READ COMMITTED` each statement must see commits made while it waited for a lock); **[v1.6: F36; v1.7: F41]** `canonicalise_address` is `STABLE` (it resolves the registered `rule_function_identity` from the `address_rule_version` registry, so it is not a pure function of its arguments alone) and is bootstrap-owned and used in **no** `CHECK` (rule 26); `address_rule_supported` is removed; the per-version rule functions it dispatches to (e.g. `ast1.canonicalise_evm_hex40_v1`, §2.1) are the `IMMUTABLE`, self-contained functions.

**`record_fingerprint_matches` [v1.3: F26].** Derived inside the function from two stored values: `current record.identity_fingerprint = instrument.identity_fingerprint`, where the record is the newest by `record_seq` and the instrument row is the one read under the lock. It is `true` when there is no current record (B2 handles that case), and it is **never** a parameter, a column of the log or token, or any application-supplied value. The database cannot recompute the fingerprint from the live identity columns (it is a canonical-JSON hash computed in TypeScript); it does not need to for the cases it must cover: identity columns are trigger-immutable after lock, so the **only** governed way the cached fingerprint changes is `ASSET_CLASS_CORRECTION` (§4.1 iv), and any change to that cached value is visible as a mismatch. A cached value that disagrees with the live columns (raw tampering) is the sweep's and the TypeScript derivation's job (T-INT-01), unchanged from v1.2. `drift_explained_by_correction` is `true` only when `record_fingerprint_matches = false` **and** a verified `class_correction_marker` explains it (§5.3); it selects a reason code and sweep behaviour and is **not** read by `backstop_permits` (B12 denies either way).

**`class_binding_matches` [v1.4: F29 — independent of `record_fingerprint_matches`].** Derived from two stored values, neither of them a cache the correction writer must remember to update correctly: `current record.asset_class_at_record = asset.asset_class`, where `asset_class_at_record` is trigger-filled at record insert (§5.1 trigger 4) from the asset's class **at that time**, and `asset.asset_class` is read **live**, under the lock, at evaluation time. Unlike `record_fingerprint_matches`, this comparison needs nothing cached on the instrument to have been correctly recomputed: `ASSET_CLASS_CORRECTION` is *defined* as `UPDATE asset SET asset_class` (§4.1), so the moment a correction commits, `asset.asset_class` has changed and `class_binding_matches` goes `false` for every instrument of that asset with a current record — **whether or not** the same transaction's fingerprint recompute (§4.1 iv(a)) ran correctly. This is what closes the R3→R4 gap: a defective correction writer that leaves the cached `identity_fingerprint` untouched (so `record_fingerprint_matches` stays `true`) cannot also leave `asset.asset_class` untouched, because changing it *is* the correction. It is `true` when there is no current record (B2 handles that case) and is never application-suppliable.

**`lineage_review_required` [F20; v1.3: F27 — one definition, stated identically in TypeScript (C0b) and here].** Let *c* be X's current record and `c.global_seq` = `current_global_seq`. For an instrument X define its **basis trees** *B(X)*: the lineage merge tree (identified by its root, `lineage_root(...)`) of X's own asset, and the merge tree of each **transitive underlying instrument** of X (`instrument_underlying`, depth ≤ 8). For a tree *G*: **SEC(G)** = the real (non-synthetic) `classification_record`s with `outcome = 'SECURITY_OR_SECURITY_TOKEN'` and `lineage_root(record.lineage_id) = G`; **MERGES(G)** = the `lineage_merge` rows with `lineage_root(merged_lineage_id) = G` (every edge of the tree). Then `lineage_review_required(X)` is **true** iff X is real, `latest_outcome = 'NON_SECURITY_DIGITAL_ASSET'`, and (`depth > 8` on any underlying chain, fail-closed) **or** ∃ *G* ∈ *B(X)* such that

- **(a) newer `SECURITY` record:** ∃ *r* ∈ SEC(*G*), `r.instrument_id ≠ X`, **`r.global_seq > c.global_seq`**; **or**
- **(b) merge after X's review that joined security history:** ∃ *m* ∈ MERGES(*G*) with **`m.merge_global_seq > c.global_seq`** and ∃ *r* ∈ SEC(*G*) with **`r.global_seq < m.merge_global_seq`**.

Clause (b) is the **documented fail-closed over-approximation**. Read with the merge tree already formed, it says: *a merge newer than X's current record whose tree holds a real `SECURITY` record recorded before that merge.* (If such a record entered the tree only through a **later** merge, that later merge is itself a clause-(b) event for X, so nothing is missed.) It covers, without needing to know which side each instrument came from, all four cases of F27: (1) an older `SECURITY` record joined to a newer `NON_SECURITY` instrument; (2) a newer `SECURITY` record and an older `NON_SECURITY` instrument that a merge then puts in one tree (clause (a) also fires); (3) a merge of an **underlying's** tree (*G* ∈ *B(X)* through the underlying chain); (4) a `SECURITY` record that lands in the tree later (clause (a)). It over-approximates when a merge joins an unrelated clean tree into a tree whose members were already elevated-reviewed: those members become `NOT_ASSESSED` until re-reviewed. That is a deliberate availability cost (12 AR-24) and never a safety gap. Because `global_seq` and `merge_global_seq` come from **one** sequence drawn under the lock protocol of §7A, "after X's current record" is a comparison of two DB-assigned values; no timestamp and no caller value is involved.

**Clearing.** The condition clears when X's `current_global_seq` exceeds every triggering value, i.e. when X receives a **newer** record. Because the merge tree now holds a `SECURITY` record, that record can only be appended by the elevated path (§5.1 trigger 7: two attested checkers, `lineage_reviewed_attested`, evidence with `evidence_global_seq` newer than the review floor **and** the explicit `follows_event_*` binding to the newest triggering event, merges included). A pre-merge `NON_SECURITY` record has a lower `global_seq` than the merge, so it can **never** clear a post-merge requirement, and a reaffirmation that does not meet the elevated requirements is refused by the trigger and therefore never becomes a record. The classification of X is **not** rewritten and is **not** made `SECURITY`: eligibility becomes `NOT_ASSESSED` / `LINEAGE_SECURITY_REVIEW_REQUIRED` (01 §4.7A). Nothing else — no hold release, admission, flag, role or configuration — clears it.

## 7A. Locking protocol, the global lock order, and the consumption, merge and correction transactions [v1.2: F18; v1.3: F26, F27; v1.4: F29, F30, F31]

**Principle.** The instrument row lock *is* the classification/hold/admission/operational lock for that instrument. Every writer of an eligibility input takes it through `lock_instrument(id, UPDATE)`; every reader that must be stable (mint, consume) takes it through `lock_instrument(id, SHARE)`. **[v1.4: F30.a] Reads are `READ COMMITTED`, and this is an asserted precondition, not a documented assumption**: `authoritative_state()` and every lock helper raise `AS007` (`AST1_UNSUPPORTED_TX_ISOLATION`) if the session is not `READ COMMITTED` (§7). Correctness rests on the locks plus that assertion, not on `SERIALIZABLE`. **[v1.4: F30.c] Scope of the ordering guarantee.** Sequence order is proven to equal commit order **only** for a pair of events that (i) lock a common instrument, or (ii) are both serialised by the exclusive lineage gate (§below, level 0) — for example a real `SECURITY` record versus a sibling's later record, or two lineage-wide writers against each other. It is **not** a property of the sequence in general: two ordinary records or two evidence items on **different**, unrelated instruments can commit in either order relative to their sequence draws, and no security predicate in this pack compares such a pair. `class_correction_marker.marker_global_seq` participates in this guarantee only in the one case the pack actually uses it — comparing two markers **of the same instrument** (§5.3, "the newest marker explains the newest fingerprint"), which clause (i) already covers because the correction holds that instrument's lock throughout; a marker is never compared against a different instrument's events or against a gate-serialised event for a security decision. **[v1.3]** Two lineage-wide writers (a real `SECURITY` record, a lineage merge) and one asset-wide writer (`ASSET_CLASS_CORRECTION`) change the eligibility of instruments other than the one they are addressed to. They therefore take locks **above** the instrument level, and every path in the module is placed in one total order below.

**Notation [v1.7: F38].** Throughout this section and the rest of the pack, "`X`" / "`UPDATE`" means the mode requested from a lock helper, and "`SHARE`" likewise. `SHARE` and `UPDATE` are *implemented inside the helpers* as PostgreSQL `FOR SHARE` and `FOR UPDATE` respectively; those are the **only** places raw row-lock SQL appears (rule 22). No writer step and no trigger in this pack is specified as raw `SELECT … FOR …`.

### Governed apply protocol — IAM-02 outside the transaction [v1.8: F45]

**The platform rule** (SEC-01 `alerts.ts`, CLT-01 `client-profiles.ts`, AML-01 `matches.ts`): a Postgres lock and an open transaction are **never** held across the IAM-02 `execute-verify` network call. v1.7 placed `execute-verify` inside the apply transaction, after `lock_governed_change` — holding the G row lock and an assigned transaction id for the whole IAM latency (availability and xmin-horizon cost only, no safety effect). Every governed maker-checker apply — a classification record (incl. real `SECURITY`), a lineage merge, an `ASSET_CLASS_CORRECTION`, and every governed hold / admission / custody / operational-state / retire / risk-profile / evidence-standard-retirement change — now runs in two phases. **No step of any AST flow calls IAM-02 between `BEGIN` and `COMMIT`.**

**PHASE A — OUTSIDE any database transaction** (no AST row lock is held, no transaction is open on the AST connection):
1. Read the change/request **without** a row lock (a plain `SELECT`).
2. Verify the local shape and preconditions that need no lock (change kind, target ids, status shown `requested`, required-checkers derivation inputs).
3. Recompute the current immutable **payload hash** from the stored payload.
4. Call IAM-02 `execute-verify` bound to that recomputed `payload_hash`.
5. Require positive authorisation and capture: `verified_payload_hash`; the verified decision / policy / **attested approver** evidence (`approval_policy_id`, approver identities — DCR-AST1-001(d)); and the other IAM evidence the existing contract requires (04 §3).

**PHASE B — the apply transaction:**
6. `BEGIN` (`READ COMMITTED`; the first helper asserts it, `AS007`).
7. **`lock_governed_change(change_id)` — level G**, the first lock in the transaction.
8. **Re-read the authoritative change row under the lock.**
9. Require, from that locked read: status still `requested`; payload still immutable (the stored payload recomputes to the stored `payload_hash`); **recomputed `payload_hash` = IAM `verified_payload_hash`**; the captured IAM evidence still matches the required policy and authority (the attested approvers satisfy `required_checkers`, `maker ∉ approvers`, the policy identity is the required one); and no state precondition changed in a way the apply contract prohibits (the decisions that depend on state under later locks — merge roots, affected sets, correction `(from, to)` against the live class, approval strength — are re-made under those locks in step 10 onward).
10. Take levels `0 → 1 → 2 → 3 → writes` exactly as the specific operation requires (below).
11. Apply.
12. `COMMIT`.

**If anything changed between IAM verification and the locked re-read, the apply fails closed** (`AST1_CHANGE_STATE_INVALID` when the change is no longer `requested`; `AST1_APPROVAL_INVALID` when the hash or attested evidence no longer matches) and the transaction rolls back with nothing applied; **a retry requires fresh IAM-02 verification**, as for every apply (unchanged from v1.7).

**Why the unlocked window widens no eligibility.** Phase A takes no eligibility decision; its only output is IAM evidence bound to a payload hash. Every authoritative precondition is re-read after G is locked, and every security-bearing read (roots, affected sets, classes, fingerprints, `lineage_review_required`, review floor) is made only under levels 0–2 in Phase B. Two concurrent applies of one change contend on G: the first commits `applied`; the second, on obtaining G, finds the change no longer `requested` and fails closed. **The lock order is unchanged: G → 0 → 1 → 2 → 3 → 4, and G remains the FIRST lock inside the actual apply transaction.**
### Lock helper family [v1.7: F38.1 — the complete, normative list]

Every governed protocol lock at levels **G, 0, 1, 2, 3** is acquired **only** through one of these helpers. Each is `VOLATILE`, its **literal first operation is `assert supported transaction isolation = READ COMMITTED`** (`AS007`, `AST1_UNSUPPORTED_TX_ISOLATION`; §7), and each consults the **advisory** transaction-local tracker below for ordering decisions and updates it only for genuinely new keys. **[v1.8: F42] On every call, every helper issues the PostgreSQL row-lock statement for each requested key it does not refuse (rule 22, PHYSICAL-LOCK-ALWAYS): the tracker decides only ordering bookkeeping and refusals, never whether a lock is taken.** The helper implementations are the only code that may contain raw `SELECT … FOR SHARE` / `FOR UPDATE` against these objects.

`authoritative_state()` is not a lock helper but calls `lock_instrument(id, SHARE)` and asserts `READ COMMITTED` first (§7). The **static helper-exclusivity scan** (T-LOK-07(m)) covers levels **G, 0, 1, 2, 3** with the helper implementations themselves excluded; T-ISO-04 asserts the isolation check on exactly the helpers in this table.

Within a level a transaction takes several locks in ascending key order (`instrument_id`; for level 3 the composite key `(instrument_id, token_hash)` — a token's `instrument_id` is immutable, so this is a deterministic total order over token rows); a level is never re-entered after a higher level has been taken, except the idempotent re-lock of a key the transaction already holds. **[v1.5: F34] The tracker, mechanically defined.**

- **Transaction-local state, exactly.** Every tracked value is set with `set_config('ast1.…', value, true)` — the third argument `is_local = true` is what makes it transaction-local. Such a value **disappears/reverts automatically** at `COMMIT` and at `ROLLBACK`; a `ROLLBACK TO SAVEPOINT` reverts it together with every row lock taken since that savepoint, because both are ordinary transaction/subtransaction state to PostgreSQL — absent tampering, the tracker and the actual row locks revert together with no separate bookkeeping to keep in sync — but **no safety decision assumes they agree**: the tracker is advisory (F42, below) and a forged entry is not a lock. No pooler action and no `BEGIN` are needed or relied on to reset it: a new transaction on the same session simply has never set these keys. **[v1.6: F38 — corrected `current_setting` semantics.]** `current_setting('ast1.…', true)` returns **`NULL`** for a genuinely fresh/unset key that this session has never placed a value for, and returns `''` only after an earlier `set_config` in this session created the placeholder and a later revert (transaction/subtransaction end) cleared its value back to empty — the two are different PostgreSQL states, not the same string. Every helper's parsing rule is: **`NULL` or `''` both mean "nothing held / empty tracker"** — no helper depends on one representation over the other, and none casts the raw result to a non-text type before checking for both (a helper that cast `''::bigint` directly would fail on the fresh-session case, since `''` never actually occurs there — only `NULL` does — but a helper that checked only for `''` and treated `NULL` as "zero" or "unset in a different sense" would be the one at risk of a three-valued-logic slip; v1.6 states the rule exactly so neither mistake is made). This is also what a connection-pool session-mode reuse or PgBouncer transaction-mode reuse produces — no special-case handling is needed either way, and no state ever leaks from one transaction into the next.
- **What is tracked.** The **highest lock level** reached in the transaction (`G`/`0`/`1`/`2`/`3`); the **lineage-gate mode** held, if any (`SHARE`/`EXCLUSIVE`); the **set** of asset ids held, each with its mode (`SHARE`/`UPDATE`); the **set** of instrument ids held, each with its mode (`SHARE`/`UPDATE`); the **highest `instrument_id`** successfully acquired at level 2 in this transaction (the intra-level ascending-order guard, rule 19/F31); and, **[v1.7: F38.5]** the **set** of token keys held at level 3 (each with its mode) with the highest `(instrument_id, token_hash)` acquired there (the level-3 ascending guard), plus the `governed_change` key held at level G. The tracker knows the **set** of held instrument ids (and their modes), not only the last one — this is what makes the idempotent-re-lock and upgrade rules below decidable at all.
- **Lock strength and the PHYSICAL-LOCK-ALWAYS rule [v1.8: F42].** `SHARE < UPDATE` (PostgreSQL `FOR SHARE` / `FOR UPDATE` on the same row). A request for a key is classified against what the tracker shows for that exact key. **The tracker is ordering state only; it is never evidence that PostgreSQL granted a lock.**
  1. **Tracker shows the key held at the same mode.** Skip the level/order check for that key, **do not** add or advance tracker state, raise no `AS006` — **and still issue the PostgreSQL row-lock statement for the requested key at the requested mode.** If the transaction genuinely already holds that lock, PostgreSQL returns immediately: no wait is expected and no new conflicting lock is introduced. If the tracker entry was forged, the helper has just genuinely acquired the lock.
  2. **Tracker shows the key held at a stronger mode.** The same: skip ordering bookkeeping, no tracker change, no `AS006`, **and still issue the row-lock statement at the requested (weaker) mode**, which returns immediately when the stronger lock is genuinely held.
  3. **Tracker shows a weaker mode, stronger now requested.** **Fail `AS006`** (case 3) before any new lock statement is issued. In-transaction lock **upgrade is never permitted** by AST-01's protocol (two transactions each holding `SHARE` and both then asking for `UPDATE` is exactly the two-sharer deadlock pattern this refusal exists to prevent). Writers must request the strong mode **first**: a writer never calls `authoritative_state()` (`SHARE`) before `lock_instrument(…, UPDATE)` on the same row in one transaction, and never places an evidence insert (gate `SHARE`) ahead of a real-`SECURITY` record (gate `EXCLUSIVE`) in one transaction. Where a path's natural order would need `SHARE → UPDATE`, the path is reordered to take `UPDATE` first (below). This is a *refusal*: it can only make a forged tracker fail closed; it can never skip a lock.
  4. **Key not in the tracker (a new key).** Apply the level/order guard, acquire the lock, and record the key in the tracker only after the acquisition succeeded.
  **Consequently the tracker cannot remove a lock.** No path in this pack lets a tracker entry replace the row-lock statement. The only tracker-dependent outcomes are (a) an `AS006` refusal, (b) skipped ordering bookkeeping and (c) skipped tracker mutation. The properties that follow for a same/stronger re-request are: **no additional conflicting lock is introduced when the lock is genuinely held; no wait is expected for a lock already owned at sufficient strength; no tracker mutation; no false `AS006`; and the physical PostgreSQL lock statement still executes.** (v1.7's normative claim that an idempotent re-lock issues **zero** `SELECT … FOR …` is **withdrawn**.)
- **The tracker is advisory — what a forged tracker can and cannot do [v1.8: F42].** The tracker lives in `set_config('ast1.…', …, true)`, which any session can call (round-8 probe P2); **the tracker is not tamper-proof and this pack does not claim it is.** A session that forges it can make the helpers' *bookkeeping* inaccurate: (i) skip a level/order check (so a genuine acquisition may then occur out of order), (ii) provoke a spurious `AS006` in its own transaction, (iii) skip a tracker update. It **cannot** make any security check run without the physical row lock, because every helper — and therefore every trigger site below — issues the row-lock statement regardless. At worst a malicious or defective raw writer converts its own situation into an **ordinary PostgreSQL lock wait or deadlock, which PostgreSQL aborts fail-closed** (`55P03` under `lock_timeout`, `40P01`), or into an `AS006`. **Runtime safety therefore rests on the actual PostgreSQL row locks plus the database constraints and triggers, not on the tracker.** An optional static scan (T-LOK-13) may flag direct `set_config`/`current_setting` access to the `ast1.*` tracker keys outside the helper implementation and the test harness; safety does not rely on it.
- **Multi-row set lock** (a lineage-wide or asset-wide writer locking many instrument ids at once): (1) deduplicate the requested ids; (2) sort ascending; (3) **partition** them into H — ids the tracker shows held at the requested mode or stronger — and N — new ids; (4) if N is non-empty, the **smallest new id must be strictly greater than the highest new id previously acquired at level 2 in this transaction** — if not, **`AS006` before any database row-lock statement is attempted**, not after a wait; (5) **physically acquire every requested id — H and N — ascending**, one statement per id or a single `ORDER BY … FOR SHARE|UPDATE` scan over the whole set; **an id in H that the transaction genuinely holds returns immediately** (no wait, no new conflict; this is what makes a re-lock of an already-held subset free without ever trusting the tracker), and an id in H that the transaction does *not* hold (a forged entry) is genuinely acquired here; if N is empty this is a pure re-lock and step 4's check is skipped; (6) update the held-set and the highest-new-id marker **for N only, and only after** every acquisition in the batch has actually succeeded — a batch that fails partway (lock timeout, `AS006` from a nested call) leaves the tracker exactly as it was before the batch, matching that no row lock was actually gained by the failed member and every prior member's lock is still held (PostgreSQL does not release earlier row locks on a later statement's failure within one transaction; only a full transaction or subtransaction rollback does, which is covered by the transaction-local semantics above). Requesting an already-held **lower** id after a higher one is legal (it is in H, never reaches step 4); requesting a **new** lower id after a higher one is the exact case step 4 is written to refuse.
- **Re-lock sites — the formal enumeration [v1.7: F38.4].** Every site below is either an **idempotent re-lock** (the exact key is already tracker-held at the same or a stronger mode: rule 1/2 — it performs **no level or downward-level check**, changes **no tracker state** and does **not** raise `AS006`, **and still issues the PostgreSQL row-lock request, which returns immediately because the transaction genuinely holds the lock** [v1.8: F42]) or is itself a genuine new acquisition that follows the total order:
  1. the application's set lock at a writer's start, followed by that writer's own trigger re-locking the same set (real `SECURITY` apply's record-insert trigger 2(c) `lock_affected_instruments`; lineage merge's `trg_lineage_merge_apply` step 6 `lock_merge_affected_instruments`);
  2. **`ASSET_CLASS_CORRECTION` — the site that decides no-op versus false `AS006` (F38.4).** The application takes `lock_asset(asset_id, UPDATE)` (level 1) and then `lock_asset_instruments(asset_id)` (level 2, every instrument, ascending). Later, `trg_asset_class_frozen` — on the `UPDATE asset SET asset_class` — calls **`lock_asset(asset_id, UPDATE)` again**: the tracker already holds **exactly this asset key at exactly this mode**, so the trigger call is an **idempotent re-lock** (level 1 requested while the transaction is at level 2 is *not* a descent because rule 1 skips the level check for a tracker-held key; the physical `FOR UPDATE` request on the asset row is still issued and returns immediately). It then calls `lock_asset_instruments(asset_id)` again, which partitions every already-held instrument row into H before its ordering checks (set-lock step 3), has no new id to check (step 4), and physically re-requests every instrument row, all of which return immediately (step 5). **This works only because both the application step and the trigger use the helper**: were step 2 a raw `SELECT`, the tracker would never have seen the asset key and the trigger's `lock_asset` would be a *new* level-1 acquisition at level 2 — a false `AS006` on every correction. (T-LOK-07(i) asserts on both the asset key and the instrument set.) `ASSET_CLASS_CORRECTION`'s per-instrument fingerprint `UPDATE`s each fire `trg_instrument_lock_on_write` → `lock_instrument(id, UPDATE)`, also idempotent;
  3. `authoritative_state()`'s `lock_instrument(id, SHARE)` from inside a writer that already holds `UPDATE` on the same row (rule 2);
  4. the token-consume trigger's `lock_instrument(id, SHARE)` after the token lock at level 3 — an idempotent re-lock of a row already held `SHARE` from the consume protocol's own step 2 — and the token-revocation trigger's `lock_instrument(id, UPDATE)` / `lock_token(hash, UPDATE)` after the revoker's own calls (§7 token trigger (3));
  5. **the underlying-link insert trigger's `lock_instruments({source, target}, UPDATE)`** [v1.7: F40] after the application's own step-3 call — an idempotent re-lock (physical request returns immediately) on every id already held, a genuine ascending acquisition on any it does not (a raw insert, or a forged tracker);
  6. every hold/admission/custody/operational-state writer's `lock_instrument()` call, which is a fresh acquisition unless the same transaction already holds the row; case submit's identity-lock `UPDATE`, which is the transaction's first and only level-2 acquisition on its own instrument; the integrity sweep's multi-instrument `SYSTEM`-hold placements, which lock ascending in one pass through `lock_instruments` or use one transaction per instrument — never an unordered acquisition across several instruments in one transaction.
- **`authoritative_state()` and lock order.** If the calling writer already holds `UPDATE` on the instrument row, `authoritative_state()`'s internal `lock_instrument(id, SHARE)` request falls under rule 2: no ordering bookkeeping, and the physical `FOR SHARE` request returns immediately against the writer's own `UPDATE`. If a path's natural call order would need `authoritative_state()`'s `SHARE` **before** the writer's own `UPDATE`, the path is reordered so the `UPDATE` (`lock_instrument()`) is taken first and `authoritative_state()` is called afterwards, from inside the same transaction, where its `SHARE` request is then a same-key re-lock (physical request, immediate) rather than an upgrade.
- **Savepoint semantics, worked through.** `BEGIN; lock A; SAVEPOINT s; lock B; ROLLBACK TO s;` — after the rollback, PostgreSQL has released row lock B (savepoint rollback releases locks acquired since the savepoint) and the tracker's record of B (added via `set_config(…, true)` inside the now-rolled-back subtransaction) reverts with it, because `is_local` settings are themselves subtransaction-scoped state; the tracker's record of A, set before the savepoint, is untouched. Locking a valid next row (for example, some `C > A`) afterwards behaves exactly as if B had never been requested: the highest-new-id marker is still at A's value, so `C > A` succeeds normally. **Transaction-mode connection pooling** (e.g. PgBouncer in transaction mode) carries no tracker state across transaction boundaries either, for the same reason: the state lives inside the PostgreSQL transaction/session's local settings, and a pooler that hands the physical connection to a different logical transaction after `COMMIT`/`ROLLBACK` inherits no `is_local` state from the one before it.
- **Privilege note (unchanged):** PostgreSQL requires `UPDATE` privilege to lock a row `FOR SHARE/UPDATE`; `ast1_app` therefore holds `UPDATE` on `instrument`, `asset`, `governed_change` and a column-level `UPDATE` on `lineage_gate.lock_token` only, while the immutability triggers reject any actual data change (a lock statement fires no `UPDATE` trigger).
- **AS006 — the four cases, enumerated identically everywhere [v1.7: F38.6].** `AS006` (`AST1_LOCK_SET_CHANGED`, the umbrella database error, 09) is raised for **exactly** these cases and a request for a key already held at the same or a stronger mode is **none** of them: **(1)** the affected lock set changed (grew) after it was locked; **(2)** a **new lower** `instrument_id` (or, at level 3, a lower `(instrument_id, token_hash)`) was requested **after a higher new** one in the same transaction — descending order; **(3)** a **prohibited weaker→stronger upgrade** on a key already held — including the lineage gate, `SHARE` → `EXCLUSIVE` on the same gate row [v1.8 editorial: a second gate mode is classified here, once]; **(4)** an **invalid lock-level acquisition or order** — a level requested out of the total order G→0→1→2→3→4 for a genuinely **new** key (e.g. a new level-1 key while at level 2, a token before its instrument, a second `governed_change` key after level 0/1/2); case (4) is only for a new level/order acquisition, never for a same-key mode change. The tracker treats `NULL` **or** `''` as the empty/unset tracker (§7A "What is tracked"; `current_setting(…, true)` semantics above).
- **Tracker scope — stated explicitly [v1.6: F38; restated v1.7].** The tracker governs locks acquired **through the named AST-01 lock helpers only** (rule 22). The PostgreSQL executor and constraint machinery also take locks the tracker never records: an `UPDATE`'s own tuple lock on the row it writes; a `FOREIGN KEY` reference's `FOR KEY SHARE` on the row it points to; and index/unique-constraint locking during insert. For each such implicit lock, one of two things is true, and this pack does not call an implicit lock "tracked" when it is not: **(A) subsumed** — the transaction independently holds a stronger helper-taken lock on the same row for the whole window the implicit lock exists (e.g. `trg_instrument_lock_on_write`'s `UPDATE` tuple lock on the instrument row where `lock_instrument()` already holds it; **the underlying-link insert's two FK `KEY SHARE`s on every path, because `trg_underlying_insert_guard` has locked both endpoint rows `UPDATE` first [v1.7: F40.2]**; the token `UPDATE` tuple lock under the revoker's instrument-and-token helper locks [v1.7: F38.5]); or **(B) unsupported / raw**, where safety relies on PostgreSQL's deadlock detector aborting one side (the raw-SQL consume and raw revoke paths below — **not** the underlying-link insert any longer).

- **Security-bearing lock sites — physical verify-or-acquire, never "the GUC says held" [v1.8: F42].** Every site below calls a governed helper, and the helper **always issues the PostgreSQL row-lock statement** (rule 22). **No trigger may skip its physical lock merely because a GUC says the key is held.**

  | Security-bearing site | Helper call(s) (always physical) |
  |---|---|
  | `trg_underlying_insert_guard` step 1 | `lock_instruments({source, target}, UPDATE)` (any other underlying kind: `lock_instrument(source, UPDATE)`) |
  | `trg_asset_class_frozen`, both branches | `lock_asset(OLD.asset_id, UPDATE)`; branch (b): `lock_asset_instruments(asset_id)` |
  | `trg_instrument_asset_lock` | `lock_asset(NEW.asset_id, SHARE)` |
  | `trg_instrument_lock_on_write` (retire, identity lock, draft edit, correction fingerprint write) | `lock_instrument(id, UPDATE)` |
  | classification-record trigger, step 2 (a)–(c) (incl. real `SECURITY` apply: gate + affected set) | `lock_lineage_gate_shared/exclusive()`, `lock_instrument(id, UPDATE)` / `lock_affected_instruments` → `lock_instruments(set, UPDATE)` |
  | classification-evidence trigger | `lock_lineage_gate_shared()`, `lock_instrument(id, UPDATE)` |
  | real `SECURITY` apply, lineage merge (`trg_lineage_merge_apply` step 6) | `lock_lineage_gate_exclusive()`, `lock_merge_affected_instruments(surviving, merged)` |
  | token consume trigger (2), token revocation trigger (3) | `lock_instrument(id, SHARE)` / `lock_instrument(id, UPDATE)`, then `lock_token(hash, UPDATE)` |

**Why instrument before token (unchanged from v1.2).** The recommended review sequence starts with the token row. That order **inverts** against every mutator that must revoke tokens: a mutator holding an instrument lock then needs the token rows, while a consumer holding a token row then needs the instrument lock — a deadlock. The coherent order takes the instrument first everywhere. The token's `instrument_id` is immutable after mint (trigger), so reading it *unlocked* to find which instrument to lock cannot be stale. **Why gate and asset above the instrument (v1.3).** A lineage-wide or asset-wide writer must know its full set of instruments before it locks them; locking that set requires the set to be stable, which requires a lock **above** it. No path acquires level 0 or 1 while holding level 2 or 3, so adding them creates no inversion with the accepted v1.2 order (instrument(s) first, then token(s)), which is preserved without change.

**No supported path takes a lower level after a higher one, a lower new key after a higher new key within a level, or a weaker→stronger upgrade; every re-request of a held key skips ordering bookkeeping but still issues the physical lock request, which returns immediately.** The only wait edges are therefore between transactions acquiring in the same total order, so the waits-for graph is acyclic (the pairwise table above, extended by the link-insert row). A **classification record for a `DRAFT` (or `RETIRED`) instrument is refused** at step 2A, after the instrument lock and before any other read, so it adds no edge. Unsupported and fail-closed: the raw consume and raw revoke `UPDATE`s (executor tuple lock before the trigger's instrument lock).

The one remaining out-of-order path is the **raw-SQL consume** (and, likewise, a raw revoke `UPDATE`) (below): unsupported, fail-closed on deadlock. `lock_timeout` bounds every wait (≤ 5 s).

**Forged-tracker note [v1.8: F42].** A raw writer that forges the tracker cannot create a *supported* cycle and cannot remove a lock: the underlying-link trigger and every other site of "Security-bearing lock sites" remain safe because their helper calls are physical. The forged writer can only change *which* acquisitions the helpers treat as ordering-checked; any resulting out-of-order acquisition is an ordinary PostgreSQL wait that `lock_timeout` bounds and the deadlock detector aborts (`40P01`), fail-closed — the same status as the unsupported raw consume/revoke paths. **The IAM-02 call is not in the graph:** it happens in Phase A with no AST lock and no open transaction, so no wait edge can involve a remote call.

**Lock-set re-derivation (review §7 note, folded in).** A lineage-wide or asset-wide writer enumerates its affected set **after** taking levels G/0/1 (where the set of *classified* instruments cannot change: classification and evidence writers wait on the gate; instrument inserts wait on the asset row), locks it ascending, **re-derives it once every lock is held, and raises `AS006` / `AST1_LOCK_SET_CHANGED` (the transaction rolls back and the apply is retried) if the set grew.** An instrument that exists without a record at that moment has no token and nothing to narrow, and cannot obtain a record until the gate is released, at which point its first record sees the committed ledger.

### Lineage merge apply — one transaction [v1.3: F27; reordered v1.4: F30.b]

The application takes its locks in the **same order the trigger now enforces** (§3): the gate first, root resolution and cycle/compatibility checks only under it.

1. **Phase A (outside any database transaction), then G [v1.8: F45].** *Phase A* (§7A "Governed apply protocol", steps 1–5): unlocked read of the change; local prechecks; recompute the payload hash; IAM-02 `execute-verify` bound to the recomputed `payload_hash`; require IAM-02-attested approvers satisfying `COMPLIANCE_OFFICER` with `maker ∉ approvers` (as every apply, 04 §3) and capture `verified_payload_hash` and the approval evidence — **no transaction is open and no AST lock is held during this call.** *Phase B:* `BEGIN`; **`lock_governed_change(change_id)`**; re-read the change row under the lock; require it still `requested`, its payload immutable, the recomputed `payload_hash` = `verified_payload_hash`, and the captured evidence still satisfying the policy (steps 6–9 of that protocol). No remote call is made in this transaction. Nothing at levels 0–3 has been taken yet.
2. **Level 0:** `lock_lineage_gate_exclusive()`. **[v1.4: F30.b] Taken before any root or cycle decision below.**
3. **Resolve, under the gate,** the lineage roots of the two arguments (`lineage_root(...)`, which itself fails closed on a cycle or malformed ancestry, §3); require both to resolve to a definite, distinct root and `lineage.synthetic` equal on both. If the arguments now resolve to **one** root — because a concurrent merge committed and joined them while this transaction waited for the gate — refuse (`AS004`): this is what stops two racing opposite merges from ever forming a cycle (§3).
4. **Level 2:** enumerate the **affected instruments** — every instrument whose asset lineage lies in either (now-resolved) merge tree, plus every instrument whose transitive underlying chain reaches an instrument of either tree (wrappers, transitively, depth ≤ 8) — and lock them through `ast1.lock_merge_affected_instruments(surviving, merged)` (mode `UPDATE`, ascending `instrument_id`, via `lock_instruments`); re-derive; `AS006` if the set grew.
5. **Authorised.** Only now, with the change verified, the gate held and every affected instrument locked, is the merge applied: mark the change `applied`, then `INSERT lineage_merge`. `trg_lineage_merge_apply` (§3) re-runs the same gate/root/lock sequence (an idempotent re-lock on the protocol path: the physical requests are still issued and return immediately) and assigns **`merge_global_seq`** from `ast1.classification_global_seq`; the caller cannot supply it.
6. **Identify the narrowed instruments.** Evaluate `lineage_review_required` (§7) — the same function B8 and the TypeScript conjunct use — for every affected **real** instrument. The narrowed set is every instrument for which it is now true, which is exactly the set whose current record predates the security history the merge introduced (older `SECURITY` joined to newer `NON_SECURITY`, the reverse, and wrappers through their underlying trees). Instruments for which it was already true stay true.
7. **Level 3 — revoke** (§"Token revocation") every outstanding (unconsumed, unrevoked) token of every narrowed instrument (`revoked_reason = lineage_security_determination`): each narrowed instrument is already held `UPDATE` from step 4, and its tokens are taken through `lock_instrument_tokens` in ascending `(instrument_id, token_hash)` order before the `UPDATE`.
8. **Audit, same transaction (outbox):** `ast1.lineage.merged` (critical; metadata: both roots, `merge_id`, `merge_global_seq`, `change_id`), `ast1.lineage.security_determination_propagated` (critical; `trigger = MERGE`, narrowed count and ids, wrapper ids) and `ast1.eligibility.instrument_revoked` per instrument.
9. **COMMIT.** From the commit onward every narrowed instrument derives `NOT_ASSESSED` `LINEAGE_SECURITY_REVIEW_REQUIRED` and SQL rule B8 denies. **The merge itself narrows; nothing later — no sweep, no second transaction — is required for safety.** Any token that somehow survives is rejected at consumption (B8 inside `assert_token_consumable`), which is tested by forcing the consume in SQL (T-LIN-19).

A failure at any Phase B step rolls back the whole transaction (no merge row, no revocation, no event); the change stays `requested` and the apply is retriable **only with fresh IAM-02 verification** (Phase A again), as for every apply. A change of state between Phase A and the locked re-read (step 1 above) fails closed.

### Token revocation — the helper-managed level-3 acquisition [v1.7: F38.5]

Every supported token-revocation path (record/merge narrowing, `ASSET_CLASS_CORRECTION`, holds, evidence-standard retirement, standalone revoke) follows one shape, and **no token row acquisition is outside the helper contract**:
1. **Instrument first:** the revoker holds every affected instrument at `UPDATE` through the level-2 helpers (ascending), as its own protocol already requires.
2. **Then the tokens, through the helper, in deterministic key order:** `lock_instrument_tokens(instrument_id)` per instrument (which calls `lock_tokens`), or `lock_tokens(token_hashes)` for a set. Deduplicated and sorted ascending by `(instrument_id, token_hash)` — a token's `instrument_id` is immutable, so this is a total order over all token rows; the level-3 ascending guard rejects a lower key after a higher one (`AS006` case 2). `lock_token` requires the token's instrument to be already tracker-held (`SHARE`/`UPDATE`), else `AS006` case 4 — **`lock_token`, `lock_tokens` and `lock_instrument_tokens` require the corresponding instrument row(s) already held at the required mode; there is no token-before-instrument supported path** [v1.8 editorial]. The tracker check is ordering bookkeeping only; the security-bearing token triggers always call `lock_instrument` (physical) first.
3. **Then** `UPDATE … SET revoked_at_utc, revoked_reason` (the executor's tuple lock is on a row already held: subsumed, case A). The token trigger's own `lock_instrument`/`lock_token` calls are idempotent re-locks.

*Why no reverse acquisition exists.* The only writers that lock a token row are consumers (instrument `SHARE` → token) and revokers (instrument `UPDATE` → tokens). A revoker holds the instrument exclusively, so no consumer can hold a token of that instrument while the revoker takes its tokens; two revokers of one instrument are serialised at the instrument. Token rows are therefore only ever contended **under** an instrument lock — this is both the deterministic-order argument and the instrument-guard argument (F38 residue), and neither depends on the other.

### Underlying link insert — one transaction [v1.6: F37, F38; SQL-enforced v1.7: F40]

An `INSTRUMENT`-kind `instrument_underlying` insert (04 `POST …/instruments/{id}/underlyings`) is a governed lock-order path in its own right. **[v1.7: F40] The application protocol below is a convenience that takes the locks early; it is no longer what makes the insert safe.** `trg_underlying_insert_guard` (§4.3) takes the same two locks itself as its first act, so every step from 4 onward holds on a raw `INSERT` too.

1. **Assert `READ COMMITTED`** — the first operation of every lock helper (§7, `AS007`).
2. **Resolve** the source instrument id (the path parameter — the linking, currently-`DRAFT` instrument) and the target instrument id (the request body's `underlying_instrument_id`), unlocked (both ids are immutable once assigned, so an unlocked read of "which two rows" cannot be stale).
3. **Lock both endpoints via the helper**, `ast1.lock_instruments({source, target}, UPDATE)` (§7A "Multi-row set lock"), in **canonical ascending `instrument_id` order**. A self-link is already rejected by the table's own `CHECK`, so the set has exactly two distinct members. No raw `SELECT … FOR UPDATE` is issued outside the helper (rule 22).
4. **Require source = `DRAFT`** (source rule, §4.3 step 3) — else the `AST1_INSTRUMENT_IMMUTABLE_FIELD`-family refusal.
5. **Require target ≠ `DRAFT`** (`IDENTITY_LOCKED` or `RETIRED`; §4.3 step 4), **under the target's own lock**, so a concurrent identity lock or retirement of the target cannot race the check: the row lock orders them, and the later sees the earlier's commit.
6. **Verify real/synthetic compatibility and no cycle / depth ≤ 8** (§4.3 steps 5–6).
7. **Insert** the row. The trigger re-locks both endpoints (idempotent: the physical requests return immediately against the locks already held, the tracker is unchanged, zero `AS006`). The two FK checks each take `FOR KEY SHARE` on a row this transaction already holds at `UPDATE` — subsumed implicit locks (case A), no new wait, no edge.
8. **Audit**, same transaction: `ast1.instrument.underlying_linked` (metadata: source, target, `underlying_type`, target's lifecycle status at link time).

No gate is taken: a link insert cannot join security history to an already-classified instrument late (steps 4–5 foreclose it), so it is not a lineage-wide event.

**Mint (`evaluate`, allow path) — one transaction.**
1. `ast1.lock_instrument($i, SHARE)` [v1.7: F38 — helper call; `READ COMMITTED` asserted first].
2. Read all inputs (record, holds, admissions, custody, operational state, attestation, lineage state, client facts supplied by the caller).
3. Derive (TypeScript) and compute the authoritative backstop (`backstop_permits`).
4. `INSERT` log row and token row (both re-run the backstop by trigger).
5. `COMMIT`. A concurrent writer's `UPDATE` lock (`lock_instrument(id, UPDATE)`) waited for step 5, so a mutation either commits **before** the mint transaction reads (and the mint denies) or **after** it commits (and the writer then revokes the newly minted token).

**Consume (`verify-decision`) — one transaction.**
1. Read `token.instrument_id` **unlocked** (immutable). Unknown token ⇒ `AST1_DECISION_NOT_FOUND`.
2. `ast1.lock_instrument(<token.instrument_id>, SHARE)` (blocks while any writer holds the instrument, including a lineage-wide writer that locked it as an affected sibling) [v1.7: F38 — helper call].
3. `ast1.lock_token($h, UPDATE)` [v1.7: F38 — helper call; it requires the instrument of step 2 to be tracker-held, else `AS006` case 4]; check unexpired (DB `clock_timestamp()`), unconsumed, unrevoked.
4. Check the bindings against the request: authenticated service = `consumer_service`; stated `subject` and `instrument_id` equal the token's; environment = own; `payload_hash` recomputed from the **bound facts** the consumer re-supplies (client facts, caller reference, payload binding — 04 §6.2).
5. Resolve the **current** classification record (newest by `record_seq`) — stable because record inserts need `UPDATE` on the row this transaction holds at `SHARE`. Read the hold, admission, custody, operational, attestation and lineage state under the same lock. (Lineage siblings and wrappers are covered because a `SECURITY` writer locks them as affected instruments.)
6. **Recompute the authoritative backstop** (`backstop_permits`) and the TypeScript re-derivation. Require `token.classification_record_id = current record`.
7. `UPDATE … SET consumed_at_utc = clock_timestamp() WHERE token_hash = $h AND consumed_at_utc IS NULL AND revoked_at_utc IS NULL`. The `BEFORE UPDATE` trigger **independently** re-runs `assert_token_consumable()` (steps 3, 5, 6 in SQL), so a consumer that skipped or mis-implemented them still cannot consume a stale or security-bound token. `SECURITY → MB/PSO` is therefore blocked at consumption by SQL, not only by TypeScript.
8. `COMMIT` (consumption and the audit outbox row commit together, or neither does).

`lock_timeout` is set to a short constant (≤ 5 s) for both transactions. A lock timeout (`55P03`) or deadlock (`40P01`) aborts the transaction: the token is **not** consumed and the caller receives `AST1_DECISION_UNAVAILABLE`, which a consumer treats as deny (it may retry the same unconsumed token within its TTL).

**Raw-SQL path.** A raw `UPDATE … SET consumed_at_utc` outside the protocol takes the token row lock first, then the trigger takes the instrument lock — the inverted order (level 3 before level 2). That path is unsupported; if it deadlocks against a writer, PostgreSQL aborts one side and the consume fails (fail-closed). The trigger's checks still apply to it.

**Failure behaviour at consumption** (the failed transaction always stays rolled back; the token is not consumed):

| Condition | Where detected | Caller sees | Follow-up (separate transactions) |
|---|---|---|---|
| Token expired / consumed / revoked | steps 3, DB clock | `AST1_DECISION_EXPIRED` / `_CONSUMED` / `_REVOKED` | audit (replay of a consumed token: H) |
| Binding mismatch (service, subject, instrument, environment, payload) | step 4 | `AST1_DECISION_BINDING_MISMATCH` | audit H (C for a cross-domain subject); token **not** burned, so another service cannot deny a legitimate consumer |
| Record superseded or a conjunct now denies; TypeScript and SQL agree | steps 5–6 | `AST1_DECISION_STALE` | revoke the token (`instrument_reclassified` / `hold_placed` / `lineage_security_determination` / …); audit H |
| TypeScript says `ELIGIBLE` but SQL denies (divergence), or the SQL trigger raises `AS003` after the app saw no problem | step 7 | `AST1_DECISION_STALE` (fail-closed) | revoke; **`SYSTEM` hold `BACKSTOP_TRIPPED`** and `ast1.eligibility.consume_backstop_triggered` (C) |
| SQL hard rule B1 (`SECURITY` → MB/PSO) at consumption | steps 6–7 | `SECURITY_INSTRUMENT_NOT_ADMISSIBLE_TO_MB_PRODUCT` (422) | revoke; `SYSTEM` hold; critical event — a token existed for a security outcome, which the mint backstop should have prevented, so data or code is wrong |
| SQL rule B12 at consumption (the token's instrument had its class corrected, or its cached fingerprint no longer matches the token's record) **[v1.3: F26; v1.4: F29]** — denies whether the correction writer updated the cached fingerprint correctly or not, because `class_binding_matches` reads the live `asset.asset_class` | steps 6–7 | `AST1_DECISION_STALE` | the correction transaction already revoked the token (`asset_class_corrected`); if it is somehow still live: revoke; **no `SYSTEM` hold when `drift_explained_by_correction`**, a `SYSTEM` hold (`BACKSTOP_TRIPPED`) when the drift is unexplained; audit |
| Lineage review required (B8 clause (a) or (b)) at consumption **[v1.3: F27]** | steps 5–7 | `AST1_DECISION_STALE` | revoke (`lineage_security_determination`); the merge/record transaction already revoked it, so a live token means propagation failed: `SYSTEM` hold and `ast1.integrity.lineage_gap_found` |
| Lock timeout / deadlock | anywhere | `AST1_DECISION_UNAVAILABLE` | none; token unconsumed |

```sql
  approver_actor_ids text[],                              -- [F05] IAM-02-attested only
  approval_policy_id varchar(64),                         -- [F05] IAM-02-attested only
  status varchar(10) NOT NULL DEFAULT 'requested'
     CHECK (status IN ('requested','approved','applied','rejected','cancelled','failed','rolled_back')),
```
