## Deliberate choices and departures — for the re-reviewer

1. **F37's fix is Option 1 (the recommended, simpler architecture), not Option 2 (treating a link as a lineage-wide ledger event).** The review offered both and marked Option 1 recommended: "the simpler, safer architecture." v1.6 implements exactly that — a target-lock precondition — rather than giving link inserts their own sequence, gate and `lineage_review_required` clause, because Option 1 achieves the same safety property (no late-link basis growth) with a strictly smaller surface: no new ordering domain, no new clause to keep in parity between TypeScript and SQL, and no new lock level. Option 2 remains available to a future version if a use case needs a link to be insertable onto a still-`DRAFT` target under review (none is known today).
2. **F36's digest mechanism uses `regprocedure` identity plus `pg_get_functiondef()`, not a hand-maintained hash input.** The review's required correction offered "sha256 of `pg_proc` source and signature" as the recommended form; v1.6 states this via `pg_get_functiondef()` (which already serialises the function's full definition, including its signature and declared properties) rather than concatenating `pg_proc` columns by hand, because `pg_get_functiondef()` is the same primitive PostgreSQL itself uses for `pg_dump` fidelity and is less likely to silently omit a property a hand-rolled concatenation might miss.
3. **F36 relaxes `canonicalise_address`/`address_rule_supported` from `IMMUTABLE` to `STABLE`.** The v1.5 text called these `IMMUTABLE`; once they became registry-driven dispatchers (reading `address_rule_version`), they are no longer pure functions of their arguments alone, so `IMMUTABLE` would be a false declaration. `STABLE` is the correct PostgreSQL volatility category for a function that reads table state but performs no writes and returns a consistent result within one statement — and it remains usable in a `CHECK` constraint (PostgreSQL permits non-`IMMUTABLE` functions in `CHECK`; the discouragement is about planner assumptions, not validity). The per-version rule functions themselves stay `IMMUTABLE`, since each is pure regex/case logic with no table read.
4. **F36's automatic-enforcement mechanism is *named*, not built.** The review's required correction offered two mechanisms (a `ddl_command_end` event trigger, or a CI/migration-runner gate) and said "either is acceptable if stated as what it is." v1.6 states both, explains the trade-off (privilege requirement vs. deployment-specific fallback), and makes installing and testing **one of them** a P1 implementation-acceptance criterion — because no migration exists yet to attach a working trigger or gate to, and inventing one here would be implementation work this remediation is not authorised to do.
5. **F38's tracker scope statement classifies every known implicit lock, per the required correction's own instruction ("for every known implicit lock, state whether (A) already subsumed or (B) unsupported/raw").** v1.6 does this generically (tuple locks of an `UPDATE`, FK `KEY SHARE`) rather than enumerating every individual site a second time, because §7A's "Re-lock sites, enumerated" and "Who takes what" already do the per-site enumeration; the scope statement's job is to state the *rule* those enumerations already follow, not repeat them.
6. **F39(a)'s wording keeps both true statements rather than picking one.** The review allowed "You MAY say: the live asset_class binding is independently sufficient for ordinary single-hop class change; the deferred fingerprint constraint is additionally security-critical for round-trip revival prevention" as an acceptable form. v1.6 states exactly this, in both 05 and 01, because it is the most precise statement available and matches the review's own suggested phrasing closely enough that a re-reviewer can check it word-for-word.
