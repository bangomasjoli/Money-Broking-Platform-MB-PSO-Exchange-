## What changed from v1.5

| Finding | Sev | v1.6 |
|---|---|---|
| **AST-01-F36 (supersedes F32(a))** — The canonicaliser-freeze mechanism was only partly mechanical: a circular, self-reported "semantic digest" comparing a migration declaration against itself; a required vector that contradicted the canonicaliser's own accept-and-lower-case rule; a `network_registry` `CHECK … EXISTS (SELECT …)` that is not valid PostgreSQL; a migration hook described as "mechanically enforced, not a migration-author promise" while today's `node-pg-migrate` harness has no such hook at all | LOW | **One immutable function per registered `(address_format, canonicalisation_version)` pair** (never a shared multi-version function). The registry's digest (`function_definition_sha256`) is **computed by the database itself at registration and recomputed from `pg_catalog` state at every freeze check** — never migration-supplied, never caller-overridable. The vector model distinguishes invalid / valid-non-canonical / valid-canonical(fixed-point) inputs as three non-contradictory cases; a mixed-case `EVM_HEX40` vector is `expected_valid = true`, not `false`. `network_registry`'s readiness check is a **composite foreign key** plus a `BEFORE INSERT OR UPDATE` trigger — no `CHECK` references another table. The property actually proven is restated exactly: an unchanged registered function, a reproducing vector corpus, fixed-point stability of every stored identity, and no collision — not complete semantic freeze over every conceivable input. Automatic enforcement (a `ddl_command_end` event trigger, or an equivalent mandatory migration-runner gate) is named as a **P1 implementation-acceptance criterion**; the pack does not claim either is already installed |
| **AST-01-F37 (new)** — A `SECURITY`-history tree could join an already-classified wrapper's basis through a **late underlying link** added on a still-`DRAFT` intermediate instrument, with no new record and no merge to trigger B8/C0b's narrowing — only a sweep (defence in depth) would ever notice | **MEDIUM** | **Option 1 (recommended) adopted.** An `INSTRUMENT`-kind underlying link's **target** must already be `IDENTITY_LOCKED` or `RETIRED` — never `DRAFT` — checked under the target's own lock (`trg_underlying_target_locked`, new). The link insert takes helper-managed locks on **both** endpoints, ascending, before writing. Recursively: a `DRAFT` instrument may add links; every instrument it targets is already non-`DRAFT`; every non-`DRAFT` target's own link set is therefore already frozen; so the transitive underlying/basis tree of a classified instrument grows only through a gate-serialised lineage merge (clause (b), already covered), never through a late link. The false "any newcomer is necessarily record-less" reasoning (v1.5 editorial) is withdrawn and replaced with this argument, in both 05 and 02 W11 |
| **AST-01-F38 (supersedes F34's residue)** — v1.5 deleted, without replacement, the rule that lock helpers are the only code taking governed locks; the tracker's guarantees hold only for locks it saw. The one new re-lock site F33 introduced (`trg_asset_class_frozen`'s asset re-lock after level 2) was unlisted; `current_setting(…, true)`'s `NULL`-vs-`''` semantics were misstated; the tracker's scope (helper-taken locks only) was unstated; the underlying-link insert's FK `KEY SHARE` was an unlisted, deadlock-abort-only path | LOW | The helper-exclusivity rule is **restored** (rule 22, §1), naming the helper set explicitly, including a general ascending `lock_instruments()` multi-row helper. The asset re-lock site is explicitly enumerated with a dedicated test. `NULL`-for-fresh-key / `''`-for-reverted-key is stated exactly, and both are treated identically as "nothing held." The tracker's scope is stated: executor-implicit locks are either subsumed by an already-held stronger helper lock, or left to PostgreSQL's deadlock detector — never called "tracked" when they are not. The underlying-link insert (F37's new path) now takes helper-managed locks on both endpoints ascending, closing the unlisted FK-vs-`FOR UPDATE` deadlock-prone pair the review found |
| **AST-01-F39 (new)** — Text precision: (a) the round-trip `A → B → A` protection was called "a correctness backstop on the writer, not the security control," when for that case the deferred fingerprint constraint is the only thing still denying once the live class binding matches again; (b) trigger 4 cited only the application's step-3 discipline, not the trigger-enforced lock that actually makes its unlocked read safe; (c) 01 §4.7 item 2 and 02 W3 worded the elevated-evidence exclusion differently from 05 trigger 7(iii)'s exact statement | LOW | **(a)** The round-trip sentence is scoped: the live class binding is independently sufficient for an ordinary single-hop change; the deferred fingerprint constraint is additionally security-critical for round-trip revival prevention specifically. **(b)** Trigger 4's justification now cites `trg_asset_class_frozen` branch (b) / INV-26. **(c)** 01 §4.7 item 2, 02 W3 and 05 trigger 7(iii) are pinned to one identical wording — `SEC(G)` for every `G ∈ B(X)` — cross-referenced rather than independently restated |
