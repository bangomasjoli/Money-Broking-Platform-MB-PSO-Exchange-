## AIX-PAR-001 — one-time two-worktree pilot exception (conditional; state in Issue #18)

This is a **time-limited, one-time proposal for AIX-PAR-001** (Issue #18). Merely merging this text, seeing `document_status: APPROVED`, or passing CI **does not permit concurrent implementation**. The default remains one controlled repository writer and **one module/task per Claude Code session**. All `CLAUDE.md` repository, product-scope, approval and Git protections remain in force. `NOT_ACTIVE`, `ACTIVE`, `LANE_PAUSED` and `STOPPED` are *pilot-control labels only*, not module/task status-vocabulary changes.

### Owner authentication and authoritative state — PAR-N1

- **Default `NOT_ACTIVE`:** no two-writer permission, including after this policy is accepted or merged. Two-writer activation requires all three independent gates below.
- **Only the project owner personally using the GitHub browser UI** may create an authoritative pilot state comment in **Issue #18**. A connected agent using the same GitHub account must **never** post a state-token comment, even if quoting the owner or writing on their behalf; agent-authored ledger, review and issue comments are not activation authority. GitHub username/account ownership **alone is insufficient proof** of personal authorship.
- The owner's new comment must begin with **exactly** `AIX-PAR-001 STATE: ACTIVE` or `AIX-PAR-001 STATE: STOPPED`. The ACTIVE comment must contain explicit `policy_merge_sha`, `ui_approval_ref`, `ci_approval_ref`, `ui_owner`, `ui_branch`, `ui_base_sha`, `ui_allowlist`, `ci_owner`, `ci_branch`, `ci_base_sha`, `ci_allowlist`, `effective_at_utc`, `expires_at_utc` and a reason. The STOPPED comment may instead contain its first-line token, the ACTIVE comment ID and a reason; a serious breach or expiry stops the pilot even before a STOPPED comment is posted. No agent post may begin with either state prefix; no lane ledger may use them. **The owner must separately confirm the exact state comment ID inside the supervised session at every session start/resume**, and the reviewer/agent must verify the comment and required approvals. **PAR-N10:** read back each STATE and LANE-RESUME comment via the GitHub REST API: `performed_via_github_app` must be `null`, and an absent/unreadable field or non-null value fails closed. `null` is a necessary supporting check, **not proof of browser authorship** (CLI/token posts may also return null); owner's in-session ID confirmation and personal browser-posting rule remain mandatory. Without that confirmation, do not activate or resume, even under the owner account. This is procedural corroboration, **not cryptographic proof**.
- If a cited owner state comment is deleted, edited (GitHub `updated_at` differs from `created_at`), inaccessible, has incorrect/missing fields, was not personally confirmed, is contradicted by a later authentic STOPPED decision, or its effective/expiry time does not permit work, **fail closed to `NOT_ACTIVE` or `STOPPED`** as applicable. A stale ACTIVE never overrides STOPPED/expiry. Ambiguous chronology or authenticity means no concurrent work. An agent cannot change any state through a comment or a local file.
- **Pilot `STOPPED` is terminal for this one-time exception.** A separate reviewed and approved policy is needed before any later two-writer session; a new ACTIVE comment alone cannot restart it.

Normal Git object/reflog writes and each lane's own assigned branch ref update during an authorised local commit are allowed. **PAR-N8:** only the sole supervised operator may perform a specifically owner-authorised `git fetch` (which may update the expected `refs/remotes/origin/main`) or a separately owner-authorised push of a named lane branch (which may update that lane's matching `refs/remotes/origin/<branch>`); first STOP both implementation sessions and use an exclusive serial publish/integration window. No other shared-ref updates, branch switches, force-pushes, rewrites or agent-initiated fetch/push. Compare refs before and after and record them in the Issue #18 lane ledger. These specifically authorised operator Git updates are not a shared-Git safety incident.

### Required fail-closed file evidence — PAR-N3/PAR-N4/PAR-N5

Before **each local commit**, and again before any separately authorised push or PR, recheck the current personally confirmed ACTIVE decision, its REST origin evidence, pause/STOPPED status, exact UTC expiry and all lane approvals; **do not commit after expiry or an unapproved pause**. Then record the following per-lane proof against the **currently owner-approved base SHA**, from that lane's correct worktree (all path-output parsers must handle `-z`/NUL delimiters, with no word-splitting):

- Confirm branch, origin, worktree root and base; run `git cat-file -e <approved-base>^{commit}` and `git merge-base --is-ancestor <approved-base> HEAD`. If either fails, STOP; never silently substitute a new base SHA.
- **PAR-N11 — exact NUL-delimited commands:** capture `git status --porcelain=v1 --no-renames -z --untracked-files=all --ignored=matching`, `git diff --raw -z --no-renames`, `git diff --cached --raw -z --no-renames`, `git ls-files --others --exclude-standard -z`, `git ls-files -v -z` and `git diff --raw -z --no-renames <approved-base>...HEAD`. Parse the complete NUL-separated records, not whitespace-delimited file names. For `git ls-files -v -z`, **any tracked-file tag other than uppercase `H` requires STOP**, including `h` (assume-unchanged), `S`/`s` (skip-worktree or combined hidden flag) and unknown tags. Do not treat ignore/flag changes as clean evidence.
- Inspect **all tracked, staged, unstaged, untracked, renamed, deleted, type-changed and ignored paths** with case-sensitive matching and raw modes: permit regular file mode `100644`; require separate explicit approval for executable regular file mode `100755`; reject symlinks (`120000`), gitlinks/submodules (`160000`), unexpected modes, path traversal, unmatched paths and unapproved hidden changes. Ignored `node_modules` or build output is permissible **only** under a specific preapproved per-lane output inventory, never as permission to modify ignored source, credentials, env/config or other shared files. If an ignored path cannot be classified safely, STOP.
- Every proposed UI file must be absent from the validated approved base: use `git ls-tree -r -z --name-only <approved-base> -- <repo-relative-path>`, verify command success and an **empty NUL-delimited result** for that exact path (any error or result means STOP). A failing `git cat-file -e <base>:<path>` by itself cannot distinguish an absent path from an invalid base. CI changed paths must match the two exact filenames. No gitignore exclusion or automatic cleaning may conceal exceptions.
- **Generated `AGENTS.md` rule (PAR-N7):** the nested `platform/apps/web/AGENTS.md` instruction to commit its `next dev` regenerated block **does not authorise a concurrent UI writer to commit it**. Because that file is excluded, a dirty `AGENTS.md` or other unexpected generated file is `LANE_PAUSED` at minimum: report it without auto-commit, auto-revert, ignore, reset, clean or expanding the allowlist. Resolve, if authorised, in a separate exclusive governance/implementation window when both implementation sessions are stopped.
- Record command outcomes, changed-path inventory, base ancestry result, allowed ignored outputs and exceptions in the Issue #18 lane ledger. Agent ledger comments are **informational only** and may never use the state-decision prefix.

### Pause, resumption, integration and automatic sunset — PAR-N2/PAR-N3/PAR-N6

- **`LANE_PAUSED` (recoverable, not pilot STOPPED):** before any unapproved edit/commit, if one worktree has an **isolated, automatically regenerated** excluded file (e.g. `AGENTS.md` from `next dev`), needs a shared-file change, or has a remediable **isolated** unclear file inventory, immediately stop **that lane** and record why. An automatically regenerated file **without an agent's forbidden manual write or commit** follows this specific LANE_PAUSED rule, not the general forbidden-write STOPPED rule below. The other lane may continue only if the operator proves the incident is confined to the paused worktree and shared Git/DB state is unaffected. No edits to fix it during parallel writing. To resume, the **owner personally posts** a new Issue #18 comment starting with exactly `AIX-PAR-001 LANE-RESUME: UI` or `AIX-PAR-001 LANE-RESUME: CI`, identifying the original ACTIVE comment ID, paused lane, reason, corrective serial-work approval/evidence and current branch/base; agent ledger comments may not use this prefix. The supervising human confirms that exact RESUME comment ID in-session and the REST origin check above must pass. Recheck the original unedited/unexpired ACTIVE decision and every gate. A resume does not extend expiry or restart STOPPED.
- **`STOPPED` (terminal for this pilot):** immediately stop **both** writers for wrong/excluded repository access, an agent's forbidden manual write/commit (distinct from isolated generated-file PAUSE), overlapping ownership, **unauthorised** shared Git/DB mutation, an unapproved writer, scope/guard breach, failure of containment, owner cancellation or another material safety violation. The state is STOPPED **even if no STOPPED comment has been posted yet**; owner should personally post the STOPPED token promptly, and ledger text may record the incident without pretending to be state authority. **Ordinary deadline expiry is not a safety incident**, but it also permanently ends this one-time parallel exception as set out below.
- **PAR-N9 — normal expiry and unfinished work:** this one-time concurrent permission expires automatically when **both original slices** reach owner disposition (accepted or stopped) or when `expires_at_utc` is reached, **whichever comes first**. Ordinary expiry is an administrative end, not an incident; its pilot state is terminal `STOPPED` for concurrent work even without a STOPPED comment. A paused lane cannot resume after expiry. Stop both sessions, preserve any unfinished local commits or pending PRs **without resetting, discarding or rewriting** them, and record the outcome. The owner may separately authorise finishing such work **serially under the default one-writer rule** with ordinary reviews, CI and fresh push/merge approvals, or decide to abandon it; that later serial work is not pilot continuation. The sole operator may remove worktrees only serially, after recording their status, checking all changes and obtaining separate owner authorisation; no automatic deletion.
- Each lane stops at **one focused local implementation commit**, plus independent review; a separately owner-authorised, non-rewriting **integration merge commit** into a lane branch is permitted in addition to that implementation commit. Explicit, separate owner authorisations remain mandatory for push, PR, acceptance and merge. `PR verification result` must succeed at the current head, but **green CI is not independent approval**. CI guard changes require an independent control review. Only **one merge-commit PR merge at a time**. Following the first merge, STOP both writers for the serial integration window until the owner records a **new approved-base SHA** in Issue #18 and separately approves the operator's fetch and a **non-rewriting merge commit** bringing updated protected `main` into the remaining task branch. Rerun ancestry checks and all changed-path checks with `git diff --raw -z --no-renames <new-base>...HEAD`, then current-head required CI before any further approved push/merge; no silent rebase/force push or informal base swap. **If the pilot has already expired, do not resume the parallel pilot**; any remaining integration follows separately approved serial one-writer work.
- **Governance record checkpoints are exclusive** and run only with both implementation writers stopped, as specified in `docs/03_implementation/tasks/README.md`. Any status, register, decision or master change requires its own approval and serial checkpoint. No implementation writer may write `docs/**` during the pilot.
- The policy reverts to the **default one-writer rule immediately** at STOPPED or expiry. Restarting concurrency requires a newly reviewed and approved exception. This pilot does not confer deployment, regulatory, licence or production readiness permission.
