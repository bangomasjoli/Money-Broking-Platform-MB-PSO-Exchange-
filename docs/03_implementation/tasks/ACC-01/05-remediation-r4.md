## 6. Design choices the reviewer may want to test

These are v0.5 authoring decisions inside the approved decisions, not new decisions:

1. **Reusing `closure_seal_pin_readiness` as the required-attester-set pin**, rather than inventing a separate table. It already carries one row per attester consulted at seal time; this remediation only makes explicit that this row set — not live configuration — governs completion. If the human prefers a dedicated, differently-named table, that is a documentation-only relabelling, not a design change.
2. **`family_completion_unattainable` requires a *persistent* `blocked`/`unavailable` latest row**, not a single failed attempt. The blueprint does not specify a retry count before this ground is admissible — left to the implementation task, consistent with how `ACC1_CLOSURE_NOT_READY`/`ACC1_CLOSURE_BLOCKED` retries are already left unspecified.
3. **`checker_rejected_seal`'s evidence is honestly weaker than its name suggests.** Today's IAM-02 does not tell ACC-01 that an approval was rejected (only that it was never applied). The design does not pretend otherwise; it relies on the abort's own independent checker approval as the real control, and states this plainly rather than inventing an IAM-02 signal that does not exist. If the human wants a genuine "IAM-02 confirms this approval was rejected" seam, that is a further DCR against IAM-02, not raised here because the current design does not depend on it.
4. **`closure_initiation_withdrawn` reuses `abort_closure`** rather than a dedicated `withdraw_closure_initiation` change type, to avoid inventing a second governed-recovery mechanism. If the human prefers a distinctly named change type for audit legibility, that is a naming choice, not a control change.
5. **`family_set_hash`'s new definition is a strict subset of the old one** (immutable seal facts, which were already bound); nothing that previously counted as tamper evidence is lost — only the fields that made ordinary operation indistinguishable from tampering are removed.
6. **DCR-ACC-FND-02 is deliberately unspecific about the mechanism** (mTLS vs. signed responses vs. equivalent) — a platform/deployment decision, not an ACC-01 blueprint decision.
